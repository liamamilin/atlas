# Synthetic Monitoring

## Overview

A **Synthetic Monitoring** application continuously executes simulated interactions against user-facing services from measurement points outside the monitored system, evaluates each run against defined expectations, and alerts when the service stops meeting them.

The defining structure is small:

```text
Check (monitor)
└── a persistent, re-runnable definition of one synthesized interaction
    ├── target (URL, API endpoint, host, DNS record, port, user flow)
    ├── interaction content (request, steps, or script)
    ├── expectations (assertions and thresholds that define success)
    ├── schedule
    └── vantage-point selection
        ↓ executed by
Vantage points outside the monitored system
        ↓ producing
Run results → pass/fail verdict + response measurements → history
        ↓ driving
Alerts on failure
```

Everything commonly associated with modern synthetic monitoring — browser-based user journeys, mobile app tests, Web Vitals, SLO computation, monitoring-as-code, AI-generated tests — is widespread in current products but is not part of the defining core. The simplest availability check (an HTTP request to a URL on a schedule, with an alert when it fails) satisfies the same core; the market commonly markets that simple pole as "uptime monitoring" and the deep pole as "synthetic monitoring," but they are one Type at different depths.

The name comes from what the system measures with: **synthetic** interactions — requests and actions generated by the monitoring system itself, not by real users and not by the monitored application. Because the measurement originates outside the serving system, the industry also calls the posture *black box* or *outside-in* monitoring.

## Users & Context

The primary users are the teams accountable for a digital service staying up and working:

- **SRE / DevOps / platform engineers** — define checks for critical endpoints and user journeys, wire alerts into on-call processes, and manage checks as code alongside application code.
- **Web and e-commerce teams** — watch site availability, page load performance, and revenue-critical flows (login, search, checkout) so they learn about breakage before customers report it.
- **IT operations / NOC teams** — monitor internal applications, third-party dependencies, and service endpoints from outside the estate.

Typical working context: the service is already in production and real users depend on it. Synthetic monitoring answers "is it up, is it fast, does the critical flow still work — right now, from where our users are?" continuously, without waiting for a user complaint. A secondary context is pre-production: the same check mechanics run against staging environments and in deployment pipelines to catch regressions before release.

## Core Model

### The Defining Core

Three structures. If any one is removed, the product is no longer recognizable as synthetic monitoring:

- **The check as the unit of record.** A check (many products say *monitor* or *test*) is a persistent, individually named, re-runnable definition of one synthesized interaction. It binds together a target, the interaction content — a single request, a chain of requests, or a script — the expectations that define success (assertions on status, response content, certificates, response time), a schedule, and the vantage points that will execute it. The check is the object users create, edit, enable/disable, and review; everything else in the system hangs off it. Without persistent checks, the artifact is a one-off test script or ad-hoc probing.
- **Recurring execution from vantage points outside the monitored system.** The platform operates measurement points — commonly a managed fleet of probe locations across global regions, optionally supplemented by customer-deployed private probes for internal targets — and runs every enabled check on its schedule, from each selected vantage point, without a real user and without entering the monitored application's runtime. Without outside-in execution, the product becomes in-process instrumentation or real-user observation, which are different Types.
- **The watch loop.** Each run is evaluated against the check's assertions into a pass/fail verdict together with response measurements (duration, per-step timings, error output). Results are retained as history, and a failing check triggers notifications through configured channels. Without the watch loop, the system is a scheduled traffic generator producing data nobody acts on.

### The Check-Type Spectrum

Checks range from simple to deep. The floor simulates no user at all; the ceiling emulates one:

```text
network-level probes      → ping (ICMP), TCP port connect, DNS resolution, traceroute
protocol-level requests   → HTTP/HTTPS, SSL/TLS certificate state, WebSocket, gRPC
multi-step API chains     → several requests in sequence, results of one feeding the next
scripted checks           → general-purpose code executing requests with validations
browser journeys          → a headless browser walking real user flows, with screenshots
mobile app tests          → scripted flows against iOS/Android applications
```

Every mature product covers the floor; how far up the spectrum a product reaches varies and is a market-positioning choice, not a structural boundary.

### One Structure, Many Implementations

The core model is conceptual. Common implementations differ per concept:

```text
Concept:            Check / Monitor
Implementations:    HTTP check, ping check, port check, DNS check, keyword check,
                    multi-step API test, recorded transaction, scripted check
                    (general-purpose code), headless-browser journey check, mobile app test

Concept:            Vantage Point
Implementations:    vendor-operated global probe fleet, customer-deployed private
                    probes/locations, customer data-center locations

Concept:            Result Record
Implementations:    metrics published to a metrics platform, logs, a dedicated
                    results store with per-run drill-down, incident records

Concept:            Expectation
Implementations:    status-code assertions, response-body/keyword checks, header checks,
                    certificate-expiry checks, response-time thresholds, per-step assertions
```

## How It Works

### Define a check

```text
Pick the target (URL / endpoint / host / record / flow)
→ choose the check type and interaction content
  (a single request, a request chain, or a script)
→ set the expectations (assertions, thresholds)
→ choose the vantage points and the schedule
→ save and enable the check
```

Creation happens through a UI, an API, or — increasingly the norm in engineering-led products — as code, so the check population lives in version control and deploys with the application.

### Continuous execution

```text
Schedule fires
→ each selected vantage point runs the check independently
→ the synthesized interaction is sent to the target
→ the run is evaluated against the check's assertions
→ the verdict and measurements are recorded
→ repeat for as long as the check is enabled
```

Vantage points run independently: selecting several locations means the check executes from each of them on the schedule, so a failure visible from one region but not another is itself diagnostic information.

### The watch loop

```text
Run fails its assertions
→ confirm the failure (retry, second check, or corroboration
  across vantage points — products differ in mechanism)
→ open/record the failure
→ notify the configured channels (email, SMS, chat, pager integrations, webhooks)
→ recovery is recorded when runs succeed again
```

Between incidents, the accumulated history is the product's reporting layer: availability and uptime percentages, response-time trends, and per-run detail (step timings, waterfalls, screenshots, error output) used to investigate degradation and to verify that fixes worked.

### Maintain the check population

Checks are long-lived operational artifacts. Ongoing work includes pausing checks during planned maintenance so expected downtime does not trigger alerts or distort availability statistics, updating checks when the application changes, running checks on demand after a deployment, and — in engineering-led products — running the same checks against staging environments and in CI/CD pipelines before release.

## Interfaces

The following surfaces are described conceptually; exact layouts and names vary by product.

### Check list

The primary entry surface.

- lists the check population with type, target, schedule, and current status
- surfaces recent results and failure state at a glance
- primary actions: create a check, enable/disable, edit, run on demand, inspect results

### Check detail / results

The per-check history surface.

- availability/uptime percentage and response-time trend over time
- timeline of runs with pass/fail verdicts
- per-run drill-down: step timings, waterfall, screenshots, response/error detail, which vantage point ran it
- primary actions: investigate a failure, compare runs, adjust the check

### Check editor

The authoring surface.

- target and interaction configuration (request builder, step recorder, or script editor depending on check type)
- assertion/threshold configuration
- schedule and vantage-point selection
- in code-first products, this surface is mirrored by CLI/SDK constructs and version-controlled files

### Vantage-point management

The measurement-fleet surface.

- lists managed global locations and any private/customer-deployed probes
- primary actions: select locations for a check, deploy or configure private probes

### Alerting configuration

- per-check or grouped notification rules, channels, and escalation targets
- maintenance windows that suppress alerts for planned work

### Dashboards and status pages

- aggregate views over the check population (uptime, response time, failures)
- public or internal status pages that communicate check status outward — commonly bundled, sometimes a sibling product

## Important Rules / Behaviors

### Assertions define success

A check's verdict is determined by its expectations, not merely by connectivity. A page can return HTTP 200 and still fail a check whose assertion requires specific content, a valid certificate, or a response under a time threshold. The assertion set is what turns a request into a measurement.

### Failures are confirmed before alerting

Transient failures are routine on the internet, so products commonly confirm a failure before notifying — through an immediate retry, a second check, or corroboration across vantage points. The exact mechanism varies by product; the behavior is standard. Maintenance windows similarly suppress alerting and protect availability statistics during planned work.

### Vantage points are independent witnesses

Each selected vantage point executes the check on its own schedule. Results are attributed per location, which is what lets a team distinguish "the service is down" from "the service is unreachable from one region." This independence is also why concurrent probe traffic is a design consideration for the monitored target.

### The check is long-lived and versioned

Checks persist and accumulate history across application changes. Mature products keep revision history so a team can see what a check looked like when a given result was produced, restore earlier versions, or run a previous version on demand.

### Monitoring posture, not testing posture

The same journey mechanics exist in testing tools, but the loop differs: synthetic checks run continuously against production on a schedule and alert on failure, without a human consuming each verdict. When the same scripts run pre-release in test environments as part of a change cycle, that is the testing loop — related, and a common bridge in modern products, but a different operating rhythm.

## Variants

- **Availability-first services** — the minimal pole: large populations of simple HTTP/ping/port/keyword checks with alerting and status pages, sold at low cost or free tiers; the market often calls this "uptime monitoring."
- **Journey-depth platforms** — recorded or scripted browser transactions and mobile app tests validating complete user flows (login, checkout), commonly marketed as "transaction monitoring" at the mid-depth and "synthetic monitoring" at the deep end.
- **Developer-first platforms** — checks defined as code (CLI, SDK constructs, version control), native integration with CI/CD pipelines, and first-class pre-production (staging) execution alongside production monitoring.
- **Observability-suite modules** — synthetic monitoring as one pillar beside metrics, logs, traces, and RUM in a broader platform, with correlation into backend telemetry as the differentiating behavior.
- **Dependency/Internet-stack emphasis** — monitoring third-party providers and external dependencies from global vantage points, with network-path elaboration (traceroute, packet-route visualization) as a signature layer.
- **Reverse-direction checks** — heartbeat/cron monitors where the monitored system must check in with the monitor on a schedule; silence, not a failed probe, is the failure signal. A variant capability inside some products rather than the center.
- **AI-assisted authoring** — generated test coverage from application exploration and goal-directed agentic checks; era-current, present in the suite pole.

## Related Application Types

| Application Type | Relationship | Distinction |
|---|---|---|
| Digital Experience Monitoring | closest sibling; shares the consumer-side measurement skeleton | DEM's unit of record is the monitored service experience and it adds real-user collection and experience attribution across the delivery path; synthetic monitoring's unit of record is the check, and it never collects from real users' sessions. DEM products bundle synthetic machinery as one collection posture |
| Metrics Monitoring | downstream series layer | probes generate measurements that commonly become metric series; metrics monitoring is the series store/query/alert layer over numeric series from any source, with no probe machinery of its own |
| Network Monitoring | technique overlap, different object | both use active probes (ping, TCP, traceroute), but network monitoring's estate is network devices and links; synthetic monitoring's targets are user-facing services and endpoints |
| Infrastructure Monitoring | different instrument and locus | infrastructure monitoring watches deployed components from inside the estate via agents; synthetic monitoring probes service endpoints from outside |
| Application Performance Monitoring (APM) | correlation partner | APM instruments the serving application's runtime; synthetic monitoring never enters it; products correlate the two views via shared identifiers |
| End-to-end Testing Platform | same journey mechanics, different loop | E2E testing produces pre-release, change-linked verdicts in test environments; synthetic monitoring produces continuous scheduled production availability with alerting; modern products bridge the two by running the same tests as production monitors |
| Load Testing Platform | same script engines, opposite perturbation | a synthetic check simulates a single user performing one iteration, minimally; load testing drives a controlled concurrent population deliberately heavily against a target |
| Status Page Platform | downstream communication | check status feeds status pages; the status page communicates, it does not measure |
| Incident Management / On-call Management | downstream consumer | synthetic alerts feed incident and paging processes; the check record is not an incident record |
| Observability Platform | bundling relationship | synthetic monitoring ships as a suite pillar and equally as standalone products; pillar packaging is not identity |

## Representative Products

- Grafana Cloud Synthetic Monitoring — OSS-lineage cloud service built on the Prometheus blackbox exporter and k6
- Checkly — developer-first platform with native Playwright browser checks and monitoring-as-code
- Datadog Synthetics — observability-suite module spanning API, browser, mobile, and network-path tests
- Pingdom (SolarWinds) — classic SMB/consumer service umbrellaing uptime, page-speed, and transaction monitoring
- UptimeRobot — minimal availability-check pole
- Catchpoint (now part of LogicMonitor) — the pure-play enterprise pole, absorbed into a broader observability platform

The core model was checked against the simple availability pole (UptimeRobot), the classic umbrella (Pingdom), and the suite and pure-play poles to avoid over-fitting to the modern browser-journey pattern.
