## Process

Run the 10-step workflow from `WORKFLOW_v1.1.md`:
1. Understand — initial hypothesis, boundary, closest Types
2. Plan — adaptive Research Questions for this Type
3. Sample — pick 2–5 representative products
4. Research — Tier-1 docs first; record source-access limitations
5. Model — extract the Type's world model
6. Compare — separate Core / Common / Optional / Vendor-specific
7. Synthesize — strip vendor names, form Canonical Model
8. Write — research notes first, then Application Document
9. Review — §24 checklist + §32 Final Canonicalization Check
10. Cite — sources with URLs and research date

## v1.1 hard rules (non-negotiable)

### L0/L1/L2/L3 hierarchy (per WORKFLOW_v1.1.md §22)

- **L0 Defining Invariant** — smallest structure without which the product stops being recognizable as this Type. Aim for 3–5 properties.
- **L1 Common Mature Structure** — common in modern products but not required to define the Type.
- **L2 Variant / Optional** — depends on era, geography, platform, security posture, scale, business model.
- **L3 Vendor-specific** — individual product modules/limits/terminology.

**Anti-overfitting rule**: a shared implementation pattern across the sample is NOT automatically a defining invariant. Example: phone-number identity is L2 for Instant Messaging, not L0.

### Evidence → assertion rule (per WORKFLOW_v1.1.md §23)

Use three evidence layers and tag them in Research Notes:
- **A Direct Product Observation** — supported by an official source for a specific product
- **B Cross-product Commonality** — observed across multiple products
- **C Canonical Inference** — higher-level abstraction derived from cross-product comparison

**Precision rule**: do not state precise numeric limits, edit windows, default settings, state names unless directly researched. Prefer qualified wording: "some products limit...", "vary substantially by product...", "many mobile-first IM products use...".

**Single-source rule**: claims supported by only one product stay product-specific, or are classified Optional / Variant / Unverified.

**Source-access limitation**: if vendor help centers cannot be fetched (network blocks, etc.), record the limitation in Research Notes, reduce assertion strength, avoid precise workflow/rule claims, and do NOT compensate by silently filling detail from model memory.

### §32 Final Canonicalization Check (per WRITING_GUIDE_v1.1.md §32)

Before exiting, verify:
- [ ] Is the definition smaller than the full modern feature set?
- [ ] Did I separate conceptual structure from common implementation?
- [ ] Did I accidentally define the Type using one era, region, or vendor pattern?
- [ ] Does every precise claim have matching evidence?
- [ ] Are single-product findings still marked product-specific/optional?
- [ ] Could the document be shortened without losing the Application's mental model?

If the last answer is yes, shorten it.

### Concept vs Implementation separation (per WRITING_GUIDE_v1.1.md §30)

Whenever possible, write the conceptual layer first and the implementation layer second. Example:
```
Concept:        Personal Addressable Identity
Implementations: phone number, username, platform account, social-graph account
```

### Product pollution check (per WRITING_GUIDE_v1.1.md §21)

For every section, ask: "If I delete the vendor names, does this still hold?" If not, it's vendor-specific and should be in Research Notes only.

### Research Notes vs Application Document (per WRITING_GUIDE_v1.1.md §31)

Three-layer filter:
- **Must understand** → Core Model / How It Works / Boundary → goes in final document
- **Helpful to understand** → Main Interfaces / Important States / Rules → goes in final document if useful
- **Product detail** → exact edit windows, exact group sizes, vendor modules, branded workflow names → Research Notes only

The final Application Document should optimize for understanding, not evidence exhaustiveness.

## Document structure

### Research Notes (`research/<slug>.md`)

Recommended sections (adapt as needed):
- Research Goal
- Initial Boundary
- Research Questions
- Representative Products
- Sources (with source-access limitation if applicable)
- Product Observations (per product, tagged with evidence layer A/B/C)
- Cross-product Comparison matrix
- L0 — Defining Invariant
- L1 — Common Mature Structure
- L2 — Variant / Optional
- L3 — Vendor-specific (long list, not summarized)
- Canonical Model (v1.1)
- Boundary Findings
- Uncertainties
- Final Synthesis

### Application Document (`applications/<slug>.md`)

Recommended skeleton (adaptive, not mechanical):
- Overview (one sentence + compact canonical model)
- Users & Context
- Core Model (L0 + L1 only; L2 becomes Variants section)
- How It Works (workflows + Core/Common/Optional summary)
- Interfaces (with Purpose / Typical information / Primary actions)
- Important Rules / Behaviors
- Variants (lists L2 implementation choices)
- Related Application Types (table with Distinction column)
- Representative Products
- Sources (concise; flag source-access limitation if applicable)

Vendor names appear ONLY in Representative Products and Sources. The Core Model, How It Works, Interfaces, Rules, Variants prose must be vendor-name-free.
