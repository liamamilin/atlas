## Initial Boundary

- Hypothesis: the Model Registry is the **model record system**: named model entries holding versioned model-artifact records with ML-typed metadata (metrics, signatures/schemas, lineage), a promotion/selection layer over versions (stages / approval statuses / aliases), and consumption by deployment/CI-CD by reference. It trains nothing, serves nothing, tracks no runs of its own — those belong to the ML Platform, AI Model Hosting, and MLOps Platform respectively.
- The hardest modeling question: is the promotion/selection layer (stages/aliases/approvals) definitional, or only common? The mlops-platform pass's leg 2 includes promotion and pointed "2 alone" at the registry — exclusion would break cross-pass consistency. Risk case: a sampled registry whose docs realize promotion thinly (Hopsworks). Resolution strategy: canonical concept = the recorded selection/consumption junction; stages-vs-aliases-vs-approval-vs-environment-scoped-registries = implementation variants.
- Likely confusions: MLOps Platform (loop machinery), Machine Learning Platform (build lifecycle center), AI Model Hosting (serving), Artifact Repository (generic custody), Feature Store (feature-data registry), AI Governance Platform (business/risk registry), public model hubs (Hugging Face-class — different contract: public distribution vs org-internal governance).

## Research Questions

1. What exactly is the unit of record — registered model, model version, model package? How do the container levels relate (group/collection/registry)?
2. What does a version carry (metrics, schema/signature, provenance/lineage, sample data, description/tags), and where does it come from (run/job linkage, upload, import)?
3. What lifecycle/selection machinery exists (stages, aliases, approval statuses)? Who may change it, and how do downstream consumers key on it?
4. What is held by the registry itself vs referenced (artifact bytes, external links)? What are the sharing/access-control structures?
5. What does the registry explicitly NOT do (train / serve / track runs / monitor)?
6. What interfaces exist (UI, SDK/API, CLI, webhooks/automations) and which is dominant?
7. What rules govern versions (immutability, metadata editing, deletion, alias uniqueness, environment vs deployment status)?
8. Removal tests in both directions against every §13 sibling + Artifact Repository + AI Governance.
9. Historical check: would pre-registry model management (shared artifact store + metrics log + sign-off before deployment) satisfy the definition?

## Product Observations

### Amazon SageMaker AI Model Registry [A: directly observed]

- Capability list (overview page, verbatim framing): "Catalog models for production. Manage model versions. Associate metadata, such as training metrics, with a model. View information from Amazon SageMaker Model Cards in your registered models. View model lineage for traceability and reproducibility. Define a staging construct that models can progress through for your model lifecycle. Manage the approval status of a model. Deploy models to production. Automate model deployment with CI/CD. Share models with other users."
- Structure: "The SageMaker Model Registry is structured as several Model (Package) Groups with model packages in each group. These Model Groups can optionally be added to one or more Collections." Versioning: "Each model package in a Model Group corresponds to a trained model. The version of each model package is a numerical value that starts at 1 and is incremented with each new model package added to a Model Group."
- "A model package is the actual model that is registered into the Model Registry as a versioned entity." "The Model Registry receives every new model that you retrain, gives it a version, and assigns it to a Model Group inside the Model Registry."
- Marketplace distinction (vendor's own): "There are two types of model packages in SageMaker AI. One type is used in the AWS Marketplace, and the other is used in the Model Registry. Model packages used in the AWS Marketplace are not versionable entities and are not associated with Model Groups in the Model Registry."
- Documented workflow: create a Model Group → an ML pipeline trains → "For each run of the ML pipeline, create a model version that you register in the Model Group" → optionally group Model Groups into Collections.
- Topic list documents (by title): register a model version; restrict artifact access to model package deployments (S3); view groups and versions; update details of a version; compare model versions; tags; delete a version; **Staging Construct for your Model Lifecycle**; **Update the Approval Status of a Model**; **Deploy a Model from the Registry with Python**; deploy in Studio; **Cross-account discoverability** (RAM); **View the Deployment History of a Model**; view model lineage details in Studio.

### Weights & Biases Registry [A]

- Self-definition: "W&B Registry is a curated central repository of W&B Artifact versions within your organization. Users who have permission within your organization can download and use artifacts, share, and collaboratively manage the lifecycle of all artifacts, regardless of the team that the user belongs to."
- Stated uses: "track artifact versions, audit the history of an artifact's usage and changes, ensure governance and compliance of your artifacts, and automate downstream processes such as model CI/CD." Summary list: "Promote artifact versions that satisfy a machine learning task to other users in your organization. Organize artifacts with tags… Track an artifact's lineage and audit the history of changes. Automate downstream processes such as model CI/CD. Manage who in your organization can access artifacts in each registry."
- Structure: each organization gets default **Models** and **Datasets** registries; additional registries for other artifact types possible; "Each registry consists of one or more collections. Each collection represents a distinct task or use case." Artifacts are logged (auto-versioned v0, v1, …) then **linked** to a collection — "link refers to pointers… W&B does not duplicate artifacts when you link an artifact to a collection."
- Model CI/CD course framing: "manage and version your artifacts, track lineage, and promote models through different lifecycle stages. Automate your model management workflows using webhooks. Integrate the registry with external ML systems and tools for model evaluation, monitoring, and deployment."
- Aliases page: default aliases auto-assigned (version number + `latest`); custom aliases; **protected aliases** — "label and identify artifact versions that should not be modified or deleted. For example… a `production` protected alias to label and identify artifact versions that are in use in your organization's machine learning production pipeline. Common protected aliases include: **Production** — the artifact version is ready for production use. **Staging** — the artifact version is ready for testing." Alias-vs-tag rule: "Each alias within a collection is unique. Only one artifact version can have a specific alias at a time. Use tags to organize and group artifact versions…"
- Adding an alias can start a **Registry automation** — "notify a Slack channel or trigger a webhook" (e.g., a webhook fires when a registry artifact gets a specific alias like "production").
- Roles: Member/Admin can add/remove aliases; Viewer/Restricted Viewer cannot; only Registry admin (and Admin service accounts) can create protected aliases, unlink protected versions, or delete collections containing protected aliases. Registry access configured per registry (users/teams/roles).
- Metrics: "If an artifact version logs metrics… you can view metrics for that version from its details page, and you can compare metrics across artifact versions from the collection's page."
- Deployment types: multi-tenant cloud (enabled by default), dedicated cloud, self-managed server.
- Note: the registry is artifact-generic (models, datasets, prompts via Weave link, custom types); models are the flagship use. Version indexing is zero-based (v0) — contrast SageMaker's 1-based numbering (exact conventions vary by product).

### Databricks — Models in Unity Catalog [A]

- Self-definition: "Databricks provides a hosted version of MLflow Model Registry in Unity Catalog. Models in Unity Catalog extends the benefits of Unity Catalog to ML models, including centralized access control, auditing, lineage, and model discovery across workspaces. Models in Unity Catalog is compatible with the open-source MLflow Python client." (MLflow 3: models "directly capture data like parameters and metrics and make them available across all workspaces and experiments.")
- Structure: registered model addressed by three-level name `<catalog>.<schema>.<model>`; versions registered under it ("The registered model will be created if it doesn't already exist, and the model version will contain all parameters and metrics logged with the corresponding MLflow Logged Model"). - Signatures: "New ML model versions in UC must have a model signature." "If a signature is provided, model inputs are checked at inference and an error is reported if the inputs do not match the signature."
- **Aliases**: "Model aliases allow you to assign a mutable, named reference to a particular version of a registered model. You can use aliases to indicate the deployment status of a model version. For example, you could allocate a 'Champion' alias to the model version currently in production and target this alias in workloads that use the production model. You can then update the production model by reassigning the 'Champion' alias to a different model version." Serving endpoints can reference a version by alias.
- Environment vs deployment status (vendor's own separation): "Using the `prod` catalog doesn't necessarily mean that the model version serves production traffic. The model version's enclosing catalog, schema, and registered model reflect its environment (`prod`) and associated governance rules… but not its deployment status. To manage the deployment status, use model aliases."
- Lineage: "When you train a model on a table in Unity Catalog, you can track the lineage of the model to the upstream dataset(s) it was trained and evaluated on"; lineage visible on the model version page (Lineage tab → lineage graph); "Data lineage is also automatically captured for models logged using feature store APIs."
- Tags (key-value, e.g. `validation_status:pending` / `validation_status:approved`), descriptions (incl. AI-generated comments), rename, **copy a model version** (promote across environments by copying between registered models — "Access control is enforced as configured in each environment"), delete ("You cannot undo this action. When you delete a model, all model artifacts stored by Unity Catalog and all the metadata associated with the registered model are deleted."), share across workspaces (same metastore) and across regions/accounts (OpenSharing/Delta Sharing).
- Limitations (vendor's own, showing evolution): "Stages are not supported for models in Unity Catalog. Databricks recommends using the three-level namespace… and using aliases to promote models for deployment." "Webhooks are not supported for models in Unity Catalog." (The legacy Workspace Model Registry supported stages/webhooks/email notifications/comment threads/activity log — the UC registry drops them in favor of catalog governance + audit logs.)

## Canonical Model (L0–L3)

### L0 — Defining Invariant (jointly-held; removal-tested)

1. **The registered model of record.** A persistent, named, organization-shared entry standing for "the model that solves this problem" (realized as a Model Group, registered model, or registry collection), under which versions accumulate over the model's life. It is the shared anchor that outlives experiments, jobs, and team changes. Remove → loose model files and naming conventions; no shared anchor.
2. **The model version as the identified, retained unit of record.** Each registration is a numbered version of the model artifact — the artifact itself stored or referenced by the registry — carrying ML-typed metadata: evaluation metrics, input/output schema (signature), description/tags, and provenance references to what produced it (run/job/code/data). Versions are retained and comparable rather than overwritten. Remove → a mutable current-model file or a generic versioned blob store; the version memory and its metadata are gone.
3. **The selection-and-consumption junction.** The registry is the recorded hand-off point between building models and using them: versions are marked as qualified/current for use (lifecycle stages, approval statuses, or aliases — the dominant realizations), and deployment, batch workloads, and CI/CD pipelines resolve what to run *through* the registry by reference (alias/stage/approval mark, or direct version reference); where marking is not provided in-record, environment-scoped registries plus version-addressable consumption carry the same junction. The act is permissioned where roles exist. Remove → a version archive with no recorded, acted-upon answer to "which version is in production?"

Jointly-held is load-bearing: 1 alone = naming convention over an artifact store; 2 alone = a generic versioned repository holding model files; 3 without 1+2 = marks with nothing to hang on; 1+2 without 3 = a version archive below the Type's governance edge; 2+3 without 1 = aliases on loose files. All three legs together are what makes the product a Model Registry.

**Deliberately NOT in the core** (consistent with the mlops-platform pass's "2 alone" pointer and every sampled product's own exclusions): no run-tracking spine (MLOps Platform), no training execution (Machine Learning Platform), no serving operation (AI Model Hosting), no feature data (Feature Store), no monitoring loop (ML Model Monitoring Platform), no business/risk review context (AI Governance Platform).

### L1 — Common Mature Structure (very common; not definitional)

- discovery/search over the registry (models, versions, aliases, tags) and cross-version comparison (metrics side-by-side)
- provenance/lineage machinery — references from version back to run/job/code/data; automatic capture where the registry is paired with a tracker/catalog
- access control and sharing: per-registry/per-model roles; cross-team, cross-workspace, cross-account/cross-region sharing; artifact-access restriction
- documentation surfaces: descriptions, model cards, evaluation images, input examples
- automation/event machinery: webhooks/notifications on marks (e.g., alias assigned), CI/CD integration, deployment history
- SDK/API parity with the UI (register, transition, alias, search programmatically) — the dominant registration path
- grouping/curation structures above the version (collections, groupings by task/use case)
- audit history of changes and usage

### L2 — Variant / Optional Structure

- packaging pole: standalone OSS machinery (embeddable, often paired with a tracker) vs suite-embedded registry service vs catalog-integrated registry (models as governed securable objects in a data catalog) vs SaaS artifact-generic registry whose flagship type is models
- promotion realization: named stages (classic) vs mutable aliases (modern; stages deprecated in favor of aliases in one sampled product) vs approval-status workflows vs environment-scoped registries with CI/CD between them
- environment topology: one registry with in-record states vs registry-per-environment (dev/staging/production)
- artifact custody: registry-held artifact bytes vs pointer/reference links to external storage
- version-numbering conventions (1-based vs 0-based) and default-alias vocabularies (`latest`, `Champion`, `Production`)
- cross-boundary sharing: same-metastore cross-workspace, cross-account RAM-style sharing, OpenSharing cross-region
- external ingestion: import of externally hosted models into the registry
- marketplace/packaging neighbor (vendor-distributed model packages explicitly kept outside the registry's versioned entities in one sampled product)

### L3 — Vendor-specific (research notes only)

- SageMaker: Model Group/Collection vocabulary; 1-based version numbering; ARN structure `arn:aws:sagemaker:…:model-package-group/version`; Model Cards association; restrict-S3-access deployment control; RAM cross-account discoverability; deployment-history view; Studio as the UI home
- W&B: registries→collections two-level curation; zero-based v-indexing; protected aliases (UI-only creation, admin-gated); alias-vs-tag uniqueness rule; "regardless of the team that the user belongs to" org posture; artifact-type extensibility (datasets, Weave prompts)
- Hopsworks: project-private registries; dev/staging/production registry-per-environment pattern; KServe-coupled model package (sample data for KServe testing; transformer assets); Hugging Face import; model evaluation images
- Databricks: three-level namespace naming; models as FUNCTION-subtype securables; signature-mandatory policy in UC; AI-generated descriptions; "Champion" alias vocabulary; stages/webhooks removed in UC (legacy Workspace Model Registry contrast); OpenSharing/Delta Sharing distribution
- MLflow: stages vocabulary (Staging/Production/Archived); flavors/autologging context; registered-model URI schemes (`models:/…`, `runs:/…`)

## Rejected Findings

- **"A Model Registry is an artifact repository for models"** — rejected: artifact custody (coordinates, checksums, package-manager resolve paths) is the Artifact Repository's center; the registry's records are ML-typed governed objects — evaluation metrics, signatures, training lineage, promotion marks consumed by deployment. Both may hold bytes and both may support promotion; neither property separates them. The separator is the record's semantics and its consumers. (Consistent with the artifact-repository pass's own seam note: "model lifecycle governance vs artifact custody.")
- **"A Model Registry is a mini MLOps platform"** — rejected: no sampled registry tracks runs, executes training, or operates serving; the run-record spine and the operationalization loop are the MLOps platform's other legs. The registry is record machinery the loop flows through.
- **"Aliases/stages/approval workflows are the definition"** — rejected as *specifics*: the machinery's form is era- and product-variable (stages deprecated in favor of aliases in a sampled product; one sampled registry realizes promotion through environment-scoped registries). The invariant is the recorded selection-and-consumption junction, not any one mechanism.
- **"The registry stores the model file, so it is defined by holding artifacts"** — rejected: one sampled product explicitly does not duplicate artifacts when linking (pointer semantics), another restricts artifact access without the record being the custody layer. Custody is a realization variable.
- **"A model hub (public model sharing) is a Model Registry variant"** — rejected for this leaf: public hubs distribute pretrained models to unknown consumers under discovery contracts; the registry is the organization-internal governance record of its own models. A sampled product's marketplace-type model packages are explicitly *not* the registry's versioned entities (vendor's own distinction). Relationship recorded as a boundary, not a variant.
- **"Registry = model catalog (AI governance)"** — rejected: the governance registry holds business/risk/legal context and review state; the model registry holds technical artifact records. The governance pass recorded this seam from its side.

## Final Synthesis

The Model Registry is the organization's record system for its machine learning models: it holds each model as a named, persistent entry; retains every registered version as an identified record of the model artifact with its ML-typed metadata — evaluation metrics, input/output schema, tags/descriptions, and provenance references to what produced it; and serves as the recorded junction between building models and using them — versions are marked as qualified/current (stages, approval statuses, or aliases) and production consumers (deployments, batch workloads, CI/CD pipelines) resolve what to run through the registry by reference. It is the layer where the question "which model version is in production, and where did it come from?" has a recorded, governed, permissioned answer. What it deliberately is not: a trainer, a run tracker, a serving operator, a feature store, a monitor, or a business-risk registry — it is the record machinery around which all of those flow. The Type survives both poles of the market: the OSS record machinery embedded everywhere (MLflow) and the governance-plane registries of enterprise platforms (SageMaker, Unity Catalog), the SaaS org-level artifact registry (W&B), and the feature-store-paired open platform (Hopsworks); and it survives the era check, since the pre-label practice of named stores + metrics logs + sign-offs satisfies the same three legs.
