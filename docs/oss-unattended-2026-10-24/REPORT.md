## 持续恢复

- 模型 5xx、网关错误、超时、连接中断及限流，先执行已有短重试；仍失败时进入 `retry_wait`，保存原因、下次重试时间和未完成目标。
- 自动等待依次为 1、2、4、8 分钟，之后最多每 15 分钟重试一次；不因为达到冷却轮次上限而永久停住。供应商的 `Retry-After` 要求更久时遵守它。连续故障计数在成功处理后重置，历史恢复记录保留。
- GitHub 共享网络故障、5xx、429，以及明确的主配额或次级限流同样进入持续恢复，遵守 `Retry-After` 和 `X-RateLimit-Reset`。临时来源故障不把候选记成终态失败，也不跳过整片叶子；已经成功处理的同组项目先保存。成功读取的公开资料保留缓存或证据。
- 仓库不存在、单个文件缺失、资料过大、某个资源无权限等仍按原规则记录、收录缺项或跳过。无效 Token、模型凭据、永久配置问题、主备额度均耗尽等需要人工处理的错误明确暂停，不进行无效循环。
- 场景准备和项目提取都使用同一恢复机制。重试仅处理未完成目标，不重放已经保存的项目；全局更新锁保证不会重复启动同一任务。

## 服务器监督与页面

API 启动时创建服务器监督器，每 15 秒检查启用自动恢复的 `running`、`retry_wait`、`interrupted` 任务。已有更新锁被持有时不重复启动；进程中断后由服务器自动接回，等待期限跨重启保留，不依赖浏览器轮询或聊天。

监督心跳位于 `application-atlas-production-pack/atlas/oss-catalog.recovery.json`，包含时间、PID、最近接回任务及错误；它是被 Git 忽略的运行数据。任务保存在同目录的 `oss-catalog.sqlite`，恢复字段包括 `auto_recovery`、`recovery.next_retry_at`、`recovery.history`、`heartbeat_at`。模型组的真实并发、回执与计数记录在当前运行的 `concurrency`、`model_tasks` 和 `model_receipts`。

项目库页面显示“临时故障，等待自动恢复”、下次重试时间及原因。等待期间禁止创建重复批次，“立即重试”只唤醒既有等待者。需要改配置的暂停另行显示。
