# U17 — 开发规划与验证安排

日期：2026-09-13  
状态：实施中。M0 的资料读取、OpenCode 核心适配探测和工作区基线能力已经开始落地；本文中的未勾选项仍不代表已经实现。  
产品依据：[U17 设计稿](U17_DESIGN.md)

## 1. 交付目标

首版交付“搜索阅读 → 项目资料 → 关联文档 → 新建或改进计划 → agent 执行 → 成果核对 → 下一轮迭代”的完整流程。

新想法与已有项目改进都是首版路径。开发按下面的里程碑推进，不把中间阶段当成完整首版。

M0 验证关键不确定性，M1 建立项目与资料，M2 形成文档，M3 补齐已有项目流程，M4 打通执行，M5 完成端到端试点。暂不作未经验证的天数和费用承诺。

长期架构决定（2026-09-13）：Atlas 掌握项目知识、编排与验收状态，OpenCode 是首个可替换的执行后端。允许长期复用；扩大自研范围需要真实案例和收益依据，不预设全面重写时间表。详见设计稿 §9.1、§9.4–9.5。

## 2. M0：资料与执行引擎验证

目的：在实现完整界面前，确认可以可靠读取依据、生成文档并核对 agent 的实际工作。

| 任务 | 产出 | 完成条件 |
|---|---|---|
| M0-01 检查全文读取链路（核心能力完成） | 正文、研究笔记、嵌套章节和实例资料的读取方案 | 已实现类型正文与研究笔记的定位、分页和显式截断状态；实例资料深度按实际可用内容标明，界面接入在 M1 |
| M0-02 验证 OpenCode 接入（核心链路完成） | 针对当前已安装版本的能力表与验证记录 | 实际读取/写文档/改代码、异步任务、权限等待与回复、中断、断线/重启恢复及差异限制已验证；已形成适配器和 U17 状态投影，失败与提问边界继续随 M4 集成验证 |
| M0-03 手工走通文档样例 | 一个新想法、一个已有项目的样例文档包 | 产品需求、技术方案、任务和验收能相互对应；不确定信息有标记 |
| M0-04 验证状态与存储边界（核心存储完成） | 项目记录、文档版本、基线及执行记录的持久化设计 | 独立项目库、Atlas 标识、来源、推荐/确认需求、决定、不可变文档版本、任务输入版本、文件基线、执行/验收分离及事务边界已实现；继续补迭代对象并测量大仓库策略 |
| M0-05 验证任务交接材料（核心完成） | 来源、决定、文档版本、代码状态、验收证据和下一项任务的样例包 | 已实现包含确认需求和决定、且不调用旧会话的 JSON/Markdown 包、缺失证据提示、恢复指令及离线完整性校验 |

先以隔离的样例目录验证引擎，分别验证只读分析、文档写入和范围明确的代码改动。进程退出码、agent 自述和测试结果分开记录。

M0 不要求实现完整聊天界面或全部后端接口。如果引擎某项能力不满足，先缩小适配范围或提出替代方案，不能直接把重写通用 agent 作为默认下一步。

当前验证过程与证据记录在 [U17_M0_VALIDATION.md](U17_M0_VALIDATION.md)。

## 3. M1：项目、搜索与资料集

依赖：M0-01、M0-04。

- [ ] M1-01：项目创建、保存、切换；名称与简短想法即可开始。
- [ ] M1-02：统一呈现类型与应用搜索结果；复用类型关键词及向量能力，应用先按现有名称、简介和任务检索。
- [ ] M1-03：阅读类型原文、研究笔记、应用可用资料，保留来源入口及资料深度说明。
- [ ] M1-04：收藏全文或章节，记录借鉴点、用户备注、来源版本及读取状态。
- [ ] M1-05：资料更新提示与固定版本引用；搜索无结果时支持继续项目工作。

验收：用户不填写完整需求就能从搜索进入项目，收集多个类型和应用资料；刷新后资料与备注保留；不同项目互不混用。

复用位置：[搜索页面](../atlas-web/src/routes/search.tsx)、[类型详情](../atlas-web/src/routes/leaf.tsx)、[应用页面](../atlas-web/src/routes/apps.tsx)、[数据层](../atlas-web/src/lib/atlas.ts)、[MCP](../application-atlas-production-pack/mcp_atlas.py)。

## 4. M2：分析、关联文档与版本

依赖：M1，及 M0-02 已验证的文档任务能力。

- [ ] M2-01：资料分析、关键问题和范围取舍；区分 AI 推荐与用户确认。
- [ ] M2-02：按依赖生成调研分析、产品需求、交互说明、技术方案、开发规划与验收方案；支持简化呈现。
- [ ] M2-03：需求稳定标识、来源及验收关联；文档可反查采用理由。
- [ ] M2-04：章节编辑、自然语言修改、版本差异、人工内容保留和关联内容待复核状态。
- [ ] M2-05：范围与一致性检查；明确冲突、需要决定、参考建议分别展示。
- [ ] M2-06：Markdown 文档包导出，附总览、来源、版本和未决问题。
- [ ] M2-07：按需提供价值分析；呈现事实与建议，不设置自动否决逻辑。

验收：修改一项核心需求后，受影响的页面说明、技术内容、任务与验收可被指出并修订；未涉及的人工内容保留；导出文档离开 Atlas 仍可用于开发。

不能依靠各文档独立生成后“看起来相似”保证一致性，也不以 JSON 结构正确代替内容核对。

## 5. M3：已有项目基线与变更规划

依赖：M1、M2；项目只读分析能力可在 M0 后提前验证。

- [ ] M3-01：接入本地项目目录，记录工作区、Git 状态或文件指纹、已有文档与读取范围。
- [ ] M3-02：现状分析区分文档描述、代码线索、运行验证和未知，不把未观察到等同不存在。
- [ ] M3-03：围绕改进目标检索和分析，形成当前/期望行为、影响范围、任务与回归条件。
- [ ] M3-04：检测外部代码与文档变化，比较后更新项目现状；冲突不自动覆盖。
- [ ] M3-05：经 U17 生成的项目复用同一基线及迭代机制，保留产品意图与实现状态的区别。

验收：对一个真实已有项目提出局部改进，能定位已有实现及本次影响；外部修改相关文件后，待执行计划显示需要核对；无关变更不强制重做整个项目分析。

## 6. M4：集成执行与成果回收

依赖：M0-02、M2、M3。

- [ ] M4-01：单引擎适配，支持启动、继续、事件、提问、权限交互、停止及失败状态；实际不支持的能力明确显示。
- [ ] M4-02：每次执行绑定项目、迭代、文档版本、代码基线及工作目录。
- [ ] M4-03：按分析、文档、代码任务配置工具和写入范围；协调同一工作区的写入。
- [ ] M4-04：工作副本、文件差异和产物记录；保护已有未提交变更。Git 工作树不被当成执行沙箱。
- [ ] M4-05：中断或进程重启后核对会话与文件状态，避免盲目重复已经发生的操作。
- [ ] M4-06：记录验证命令与结果、需求覆盖、未完成项及方案偏离；区分执行完成与验收通过。
- [ ] M4-07：成果进入项目现状，用户可开启下一次迭代；文档导出与外部开发路径仍可用。
- [ ] M4-08：按设计稿 §9.4 模拟旧会话不可访问，从 Atlas 记录生成交接材料；全新会话或验证用适配器能够接收下一项任务，记录未核对的操作，避免自动重放。

验收：完成一次范围明确的代码改动，展示差异和验证证据；中断场景不会丢失产物或错误标为完成；用户在其他工具修改后能继续下一轮。无法访问旧会话时仍可核对项目并交接下一项任务，不能只依赖聊天摘要。

M4-08 依赖 M0-05 的材料定义。首版不因此新增第二个正式执行引擎；验证用适配器只证明交接结构可用，跨真实引擎的代码执行效果不得据此宣称已通过。

复用现有[草稿引擎](../application-atlas-production-pack/drafts_engines/__init__.py)的接入经验；不得直接把它的布尔返回值作为 U17 执行结果模型。

## 7. M5：完整试点与质量核对

依赖：M1–M4。

三个案例：

1. 简单新想法：从搜索开始，完成文档、一个可验收的开发范围及后续修改。
2. 已有项目改进：读取真实代码与文档，完成局部改进，并验证受影响旧行为。
3. 多类型需求：引用多个类型，解释数据归属、流程交接和取舍，不依赖强制单一分类。

核对设计稿中的 U17-A1 至 U17-C4 场景，保留发现的问题与处理结果。试点通过意味着两条入口都能持续迭代，不以生成文档数量衡量完成度。

价值评估采用相同输入、相同模型的普通方案生成作为对照，记录：

- 用户发现或开发者指出的重要遗漏与错误建议。
- 开发前仍需追问的关键问题。
- 用户确定范围所需时间及主要修改原因。
- 实际开发中的计划外改动与返工原因。

不以分类打回率、L1 覆盖率或人工改字数量替代产品价值；先记录基线，再决定是否设置量化改进目标。

## 8. 工程验证重点

实现过程中测试真实风险，不为文案和样式修改增加形式化测试。

| 风险 | 必须验证的行为 |
|---|---|
| 来源不足或截断 | 读取完整性与引用定位；未读取链接不被当成证据 |
| 关联文档不一致 | 需求变更影响传播，人工内容保留，旧版本可查看 |
| 基线过期 | 未提交变化与外部修改能触发相关任务复核 |
| 执行中断 | 状态持久化、产物保留、恢复核对、不盲目重复副作用 |
| 引擎会话依赖 | 旧会话不可访问时仍可构建交接材料；项目标识、任务状态及验收证据独立保存 |
| 结果误报 | 会话结束不等于任务验收；失败或未执行的验证不得标为通过 |
| 项目数据混用 | 项目、引用、运行目录及产物关联正确；同工作区写入协调 |

离线行为测试覆盖数据和状态规则；集成验证覆盖真实引擎、工作区与事件；界面验收覆盖从搜索到下一次迭代的实际操作。模型输出质量另用人工样例评估。

现有离线测试、前端类型检查和构建继续作为相关代码修改后的回归检查。当前仅编辑规划文档，不运行模型、创建执行会话或进行业务代码变更。

## 9. 技术约束与待定项

- 沿用当前 React/TypeScript 前端和本地服务形态；首版不因 U17 引入账号、协作或云端执行平台。
- 项目数据是持久化资产，不写入会被重新导出的语料数据库。具体存储位置、事务和版本格式在 M0-04 确定。
- 研究笔记和源码内容按需读取；索引或摘要必须能返回原始依据，不能代替全文。
- OpenCode 优先验证，具体适配方式以本地版本和能力记录决定；不承诺所有引擎具备一致恢复能力。
- OpenCode 会话 ID、专有事件和配置通过适配层关联；Atlas 的任务定义和持久化状态不采用引擎私有格式作为唯一依据。
- 首版验证任务边界上的交接能力；多引擎产品化与运行中长会话迁移不作为首版承诺。
- 无 Git 项目的文档分析与导出可先工作，代码执行前明确工作副本和差异回收方式。
- 生成文档默认跟随项目语言；保留来源原文，界面沿用现有中英文机制。

本轮完成的是产品设计与开发规划。下一项工程工作应从 M0 开始，以验证记录决定接口细节，而不是直接铺开全部页面或重写 agent 运行机制。

## 10. 后续自研范围的决策要求

对具体任务出现行为控制或部署限制，或实测质量、稳定性、总成本存在可改善空间时，按设计稿 §9.5 评估。先记录当前引擎和适配方案的局限及尝试，再比较继续复用、替换后端和局部自研。

优先评估边界明确的分析、文档更新等任务能否直接调用模型和工具完成；这种演进不要求同时重写代码执行引擎。

每次决策记录工作负载、证据、备选方案、自研范围、维护成本与验证办法。未证明收益的全面重写不进入既定排期，长期复用 OpenCode 本身不构成架构失败。
