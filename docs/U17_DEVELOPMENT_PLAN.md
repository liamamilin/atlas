# U17 — 开发规划与验证安排

日期：2026-09-13  
状态：实施中。M0–M4 与核心主线最小真实开发冒烟已完成，M5 评估型完整试点仍未完成。未勾选项不代表已经实现。
产品依据：[U17 设计稿](U17_DESIGN.md)

## 1. 交付目标

首版交付“搜索阅读 → 项目资料 → 关联文档 → 新建或改进计划 → agent 执行 → 成果核对 → 下一轮迭代”的完整流程。

新想法与已有项目改进都是首版路径。开发按下面的里程碑推进，不把中间阶段当成完整首版。

M0 验证关键不确定性，M1 建立项目与资料，M2 形成文档，M3 补齐已有项目流程，M4 打通执行，M5 完成端到端试点。暂不作未经验证的天数和费用承诺。

长期架构决定（2026-09-13）：Atlas 掌握项目知识、编排与验收状态，OpenCode 是首个可替换的执行后端。允许长期复用；扩大自研范围需要真实案例和收益依据，不预设全面重写时间表。详见设计稿 §9.1、§9.4–9.5。

## 2. M0：资料与执行引擎验证

目的：在实现完整界面前，确认可以可靠读取依据、生成文档并核对 agent 的实际工作。

| 任务 | 产出 | 完成条件 |
|---|---|---|
| M0-01 检查全文读取链路（核心能力完成） | 正文、研究笔记、嵌套章节和实例资料的读取方案 | 已实现类型正文与研究笔记的定位、分页和显式截断状态；实例资料深度按实际可用内容标明，界面接入在 M1 |
| M0-02 验证 OpenCode 接入（核心链路完成） | 针对当前已安装版本的能力表与验证记录 | 实际读取/写文档/改代码、异步任务、权限等待与回复、中断、断线/重启恢复及差异限制已验证；已形成适配器和 U17 状态投影，失败与提问边界继续随 M4 集成验证 |
| M0-03 手工走通文档样例（完成） | 一个新想法、一个已有项目的样例文档包 | 两套五文档样例已通过来源指纹、需求—任务—验收关联及不确定信息校验 |
| M0-04 验证状态与存储边界（核心完成） | 项目记录、文档版本、基线及执行记录的持久化设计 | 独立项目库、Atlas 标识、来源、推荐/确认需求、决定、不可变文档版本、迭代、任务输入版本、文件基线、执行/验收分离及事务边界已实现；大仓库策略随 M3 实测 |
| M0-05 验证任务交接材料（核心完成） | 来源、决定、文档版本、代码状态、验收证据和下一项任务的样例包 | 已实现包含确认需求和决定、且不调用旧会话的 JSON/Markdown 包、缺失证据提示、恢复指令及离线完整性校验 |

先以隔离的样例目录验证引擎，分别验证只读分析、文档写入和范围明确的代码改动。进程退出码、agent 自述和测试结果分开记录。

M0 不要求实现完整聊天界面或全部后端接口。如果引擎某项能力不满足，先缩小适配范围或提出替代方案，不能直接把重写通用 agent 作为默认下一步。

当前验证过程与证据记录在 [U17_M0_VALIDATION.md](U17_M0_VALIDATION.md)。

## 3. M1：项目、搜索与资料集

依赖：M0-01、M0-04。

- [x] M1-01：项目创建、保存、切换和安全删除；名称与简短想法即可开始。已提供本地 API、项目页、new/existing 模式和重启持久化验证；类型叶子可预填项目、在创建时固定完整正文并直接进入工作区。删除需要项目 ID 确认，活动生成或执行会阻止删除，本地工作区和源码始终保留。
- [x] M1-02：网页统一呈现类型与应用搜索结果。类型匹配名称、slug 与定义摘要，应用匹配名称、厂商、简介、任务及归属类型；语义检索继续通过现有 MCP 能力提供，不在网页中伪装成已调用。
- [x] M1-03：类型页可读取正式正文与研究笔记的全文或章节，显示行数、字符数、来源指纹和目录；应用明确显示现有资料仅为目录级，可沿归属类型继续阅读。
- [x] M1-04：可收藏类型全文/章节及应用目录记录；服务端重读正式来源，保存完整摘录、借鉴点/备注、读取状态和 SHA-256 版本，同版本同范围拒绝重复。
- [x] M1-05：项目资料集固定旧摘录和版本，比较当前来源并提示新版或来源缺失；可刷新版本状态并回到类型页收藏新版。搜索无结果时不会阻止当前项目继续。

验收：用户不填写完整需求就能从搜索或类型叶子进入项目，收集多个类型和应用资料；刷新后资料与备注保留；不同项目互不混用；项目可安全删除且不会删除本地工作区。

## 4. M2：分析、关联文档与版本

依赖：M1，及 M0-02 已验证的文档任务能力。

- [x] M2-01：资料分析、关键问题和范围取舍；区分 AI 推荐与用户确认。固定输入分析已生成可定位问题、候选需求、冲突和建议；候选逐条采用且不会自动获得用户确认。
- [x] M2-02：按依赖生成调研分析、产品需求、交互说明、技术方案、开发规划与验收方案；支持简化呈现。文档模式可选择核心四件套、完整六件套或自定义集合；Atlas 校验每种目标恰好返回一份，按固定依赖顺序展示并阻止乱序保存。保存下游时引用本轮已保存上游的不可变版本，页面提供生成历史、简要/完整草案视图和项目路径提示。
- [x] M2-03：需求稳定标识、来源及验收关联；文档可反查采用理由。需求、决定、固定资料与上游文档版本均可作为文档依据并保存快照。
- [x] M2-04：章节编辑、自然语言修改、版本差异、人工内容保留和关联内容待复核状态。用户选择唯一 Markdown 标题并描述修改要求；Atlas 固定目标版本，拒绝任何章节外变化，展示候选 diff 后再保存 AI 新版本。完整人工编辑、乐观并发保护和下游待复核传播继续复用现有机制。
- [x] M2-05：范围与一致性检查；明确冲突、需要决定、参考建议分别展示。最新固定输入分析进入一致性信号；没有完成分析时仍明确显示“未检查”。
- [x] M2-06：Markdown 文档包导出，附总览、来源、版本和未决问题。导出为独立目录和 ZIP，含文件哈希及整包 SHA-256。
- [x] M2-07：按需提供价值分析；呈现事实与建议，不设置自动否决逻辑。独立 `value` 模式生成七区价值报告，逐段区分固定依据、未知、推断、假设、风险与建议；服务端拒绝伪造依据、需求状态混淆、候选需求、评分和开发裁决。它不进入默认文档包或一致性信号，也不阻止后续工作。

验收：修改一项核心需求后，受影响的页面说明、技术内容、任务与验收可被指出并修订；未涉及的人工内容保留；导出文档离开 Atlas 仍可用于开发。

不能依靠各文档独立生成后“看起来相似”保证一致性，也不以 JSON 结构正确代替内容核对。

基础闭环的实现与浏览器验收记录见 [U17_M2_FOUNDATION_VALIDATION.md](U17_M2_FOUNDATION_VALIDATION.md)，固定输入分析和文档集合见 [U17_M2_GENERATION_VALIDATION.md](U17_M2_GENERATION_VALIDATION.md)，章节修改见 [U17_M2_REVISION_VALIDATION.md](U17_M2_REVISION_VALIDATION.md)，可选价值分析见 [U17_M2_VALUE_VALIDATION.md](U17_M2_VALUE_VALIDATION.md)。

## 5. M3：已有项目基线与变更规划

依赖：M1、M2；项目只读分析能力可在 M0 后提前验证。

- [x] M3-01：接入本地项目目录，记录工作区、Git 状态或文件指纹、已有文档与读取范围。已提供流式限量读取、不跟随符号链接的快照和本地项目页。
- [x] M3-02：现状分析区分文档描述、代码线索、运行验证和未知，不把未观察到等同不存在。未执行项目命令时运行验证显式为空。
- [x] M3-03：围绕改进目标检索和分析，形成当前/期望行为、影响范围、任务与回归条件。用户通过统一搜索固定资料，`improvement` 模式将本轮目标、资料和工作区证据固定为同一输入，并严格校验改进文档结构。
- [x] M3-04：检测外部代码与文档变化，比较后更新项目现状；冲突不自动覆盖。变化检查不改写基线，采用时同时核对基线 ID 与已审阅内容指纹。
- [x] M3-05：经 U17 生成的项目复用同一基线及迭代机制，保留产品意图与实现状态的区别。`new` 和 `existing` 项目使用同一基线接口，项目目标/需求与工作区观察分开保存。

验收：对一个真实已有项目提出局部改进，能定位已有实现及本次影响；外部修改相关文件后，待执行计划显示需要核对；无关变更不强制重做整个项目分析。

基线实现与变化检查见 [U17_M3_BASELINE_VALIDATION.md](U17_M3_BASELINE_VALIDATION.md)，改进方案、真实 OpenCode 和浏览器验收见 [U17_M3_IMPROVEMENT_VALIDATION.md](U17_M3_IMPROVEMENT_VALIDATION.md)。

## 6. M4：集成执行与成果回收

依赖：M0-02、M2、M3。

- [x] M4-01：单引擎适配支持启动、同会话继续、事件接口、提问及拒答、权限交互、停止和失败状态。每次继续复用 session 与隔离副本，但创建新的执行记录和前后快照；旧结果标记为 `superseded` 且不能应用。无 assistant 响应的短暂 `idle` 保持活动状态；会话 404 可明确收口为停止。
- [x] M4-02：每次执行绑定项目、迭代、文档版本、代码基线及工作目录。启动前核对已接受基线，执行记录保存不可变输入摘要和执行前快照。
- [x] M4-03：按分析、文档、代码任务配置工具和写入范围；以源项目绝对目录的数据库唯一约束协调活动执行，越界结果不能应用。
- [x] M4-04：每次任务复制 Atlas 基线文件到独立工作副本；源项目在显式应用前不变。应用前重验源目录与基线，以暂存、备份、原子替换和失败回滚写回；外部符号链接被拒绝，Git 工作树不充当执行沙箱。
- [x] M4-05：中断或进程重启后核对会话与文件状态，避免盲目重复已经发生的操作。真实验证停止 API/OpenCode 子进程后重启，仍能按旧 session ID 重建已完成状态和命令证据，没有重放任务。
- [x] M4-06：记录固定验证命令、退出码和输出；最终 `ATLAS_RESULT` 按精确需求 ID 集合报告覆盖、未完成项与偏离，缺失或无效报告明确标记。agent 报告、Atlas 文件/命令证据、执行完成和产品验收保持分离。
- [x] M4-07：显式应用后的精确文件状态成为新项目基线；旧基线文档自动标为待复核，新迭代只选择已复核文档。schema 5 导出保留当前基线、应用状态和外部交接路径。
- [x] M4-08：按设计稿 §9.4 模拟旧会话不可访问，从 Atlas 记录生成交接材料；全新会话或验证用适配器能够接收下一项任务，记录未核对的操作，避免自动重放。M0 已通过离线校验；当前 schema 5 项目导出为每个任务附带 Markdown/JSON 交接包和完整执行/应用记录。

验收：完成一次范围明确的代码改动，展示差异和验证证据；中断场景不会丢失产物或错误标为完成；用户在其他工具修改后能继续下一轮。无法访问旧会话时仍可核对项目并交接下一项任务，不能只依赖聊天摘要。

M4-08 依赖 M0-05 的材料定义。首版不因此新增第二个正式执行引擎；验证用适配器只证明交接结构可用，跨真实引擎的代码执行效果不得据此宣称已通过。

复用现有[草稿引擎](../application-atlas-production-pack/drafts_engines/__init__.py)的接入经验；不得直接把它的布尔返回值作为 U17 执行结果模型。

首个真实执行闭环、重启恢复和导出证据见 [U17_M4_EXECUTION_VALIDATION.md](U17_M4_EXECUTION_VALIDATION.md)。

## 7. 核心主线收口

在普通生成对照、价值比较和后端演进评估之前，先确保用户能完成最小真实开发闭环。当前顺序按必要性排列：

- [x] 从类型叶子创建项目、固定完整类型正文并进入工作区；已有当前项目可直接加入类型资料。
- [x] 新想法创建时实际建立工作区；已有项目入口拒绝不存在的目录；起点资料失败时同时回滚项目记录和新建目录。
- [x] 项目路径包含工作区基线、结果应用和迭代完成，并按当前或最近一次迭代计算执行与验收进度，避免历史任务误导新一轮状态。
- [x] 活动迭代至少固定一份当前文档、一条已确认本版需求和一份已接受工作区基线；页面提前解释缺失项，服务端执行相同约束。
- [x] 产品验收失败后允许启动新执行或重新确认验收；已通过或明确免验的任务保持关闭，迭代仍只在全部任务通过或免验后完成。
- [x] 项目删除需要明确确认，活动生成或执行期间拒绝删除，始终保留本地工作区与源码。
- [x] 运行一次最小真实开发冒烟：类型入口 → 项目 → 基线 → 确认需求 → 当前文档 → 迭代与任务 → OpenCode 执行 → 应用结果 → 独立验收 → 完成迭代。
- [x] 修复冒烟中发现的所有主线阻塞并重跑；只影响布局、效率或扩展场景的问题进入后续排序。

代码约束与页面验证记录见[核心主线验证](U17_CORE_PATH_VALIDATION.md)。最终复验项目 `prj_fdee487646e84eb08793d6304ff13f60` 从类型叶子开始，由 OpenCode 在隔离副本完成最小清单 CLI，结果首次应用成功，独立测试和手工验收通过，迭代完成。冒烟发现的嵌套 Git 状态误判、迭代表单默认选择滞后、固定验证证据口径和完成文案问题均已修复并有回归覆盖。下一步进入 M5，并在查看 Atlas 结果前固定简单新想法案例的普通生成对照。

## 8. M5：完整试点与质量核对

依赖：M1–M4。

三个案例：

1. 简单新想法：从搜索开始，完成文档、一个可验收的开发范围及后续修改。
2. 已有项目改进：读取真实代码与文档，完成局部改进，并验证受影响旧行为。
3. 多类型需求：引用多个类型，解释数据归属、流程交接和取舍，不依赖强制单一分类。

执行顺序为：先完成不承担效果评分的最小真实开发冒烟并修复核心阻塞；通过后，为每个评估案例预先固定相同模型/输入的普通生成对照，再依次完成简单新想法、已有项目改进和多类型案例。每个案例发现的来源、范围、项目隔离、写回或验收阻塞问题立即修复并重跑。三个案例完成后统一处理重要体验问题、执行回归并作出后端演进决定。详细输入、证据结构、缺陷分级和完成门槛见 [M5 完整试点计划](U17_M5_PILOT_PLAN.md)。

核对设计稿中的 U17-A1 至 U17-C5 场景，保留发现的问题与处理结果。试点通过意味着两条入口都能持续迭代，不以生成文档数量衡量完成度。

价值评估采用相同输入、相同模型的普通方案生成作为对照，记录：

- 用户发现或开发者指出的重要遗漏与错误建议。
- 开发前仍需追问的关键问题。
- 用户确定范围所需时间及主要修改原因。
- 实际开发中的计划外改动与返工原因。

不以分类打回率、L1 覆盖率或人工改字数量替代产品价值；先记录基线，再决定是否设置量化改进目标。

## 9. 工程验证重点

实现过程中测试真实风险，不为文案和样式修改增加形式化测试。

| 风险 | 必须验证的行为 |
|---|---|
| 来源不足或截断 | 读取完整性与引用定位；未读取链接不被当成证据 |
| 关联文档不一致 | 需求变更影响传播，人工内容保留，旧版本可查看 |
| 基线过期 | 未提交变化与外部修改能触发相关任务复核 |
| 执行中断 | 状态持久化、产物保留、恢复核对、不盲目重复副作用 |
| 引擎会话依赖 | 旧会话不可访问时仍可构建交接材料；项目标识、任务状态及验收证据独立保存 |
| 结果误报 | 会话结束不等于任务验收；失败或未执行的验证不得标为通过 |
| 项目数据混用 | 项目、引用、运行目录及产物关联正确；同工作区写入协调 |

离线行为测试覆盖数据和状态规则；集成验证覆盖真实引擎、工作区与事件；界面验收覆盖从搜索到下一次迭代的实际操作。模型输出质量另用人工样例评估。

现有离线测试、前端类型检查和构建继续作为相关代码修改后的回归检查；真实 OpenCode 验证用于覆盖会话、文件副本、状态恢复和结果应用边界。

## 10. 技术约束与待定项

- 沿用当前 React/TypeScript 前端和本地服务形态；首版不因 U17 引入账号、协作或云端执行平台。
- 项目数据是持久化资产，不写入会被重新导出的语料数据库。具体存储位置、事务和版本格式在 M0-04 确定。
- 研究笔记和源码内容按需读取；索引或摘要必须能返回原始依据，不能代替全文。
- OpenCode 优先验证，具体适配方式以本地版本和能力记录决定；不承诺所有引擎具备一致恢复能力。
- OpenCode 会话 ID、专有事件和配置通过适配层关联；Atlas 的任务定义和持久化状态不采用引擎私有格式作为唯一依据。
- 首版验证任务边界上的交接能力；多引擎产品化与运行中长会话迁移不作为首版承诺。
- 无 Git 项目的文档分析与导出可先工作，代码执行前明确工作副本和差异回收方式。
- 生成文档默认跟随项目语言；保留来源原文，界面沿用现有中英文机制。

当前下一项工程工作是按 [M5 完整试点计划](U17_M5_PILOT_PLAN.md)先固定简单新想法案例的普通生成对照协议，再完成该案例的两轮真实迭代；随后依次完成已有项目改进和多类型需求试点。三个案例完成后再作后端演进判断；严格生成校验的首次通过率与重试成本继续作为文档任务后端演进的依据。

### 10.1 接下来按重要性执行

| 顺序 | 优先级与必要性 | 工作 | 主要产出 | 进入下一项的条件 |
|---|---|---|---|---|
| 1 | P1 · 必须 | 冻结简单新想法试点协议 | 案例清单、固定模型与参数、相同初始输入、来源指纹、计时口径和记录目录 | Atlas 结果尚未生成；普通生成与 Atlas 的输入差异可以复核 |
| 2 | P1 · 必须 | 生成并封存普通方案对照 | 未经 Atlas 工作流约束的原始输入、原始输出、运行信息和耗时 | 原始结果只读保存，后续确认的信息没有反向写入对照 |
| 3 | P1 · 必须 | 完成简单新想法首轮 | 从搜索和阅读到文档、任务、OpenCode 执行、应用、独立验收与导出的完整记录 | 范围可验收，结果应用安全，验收证据与 agent 自述分离 |
| 4 | P1 · 必须 | 完成简单新想法第二轮修改 | 需求变更、影响传播、文档新版本、新基线、第二次执行与验收 | 旧版本可查，受影响内容已复核，第二轮使用首轮真实结果继续开发 |
| 5 | P1 · 必须 | 完成已有项目改进案例 | 现状证据、局部改进、旧行为回归、相关外部变化冲突和下一轮记录 | 外部变化不会被静默覆盖，既有行为与新行为均有验证 |
| 6 | P1 · 必须 | 完成多类型需求案例 | 多来源依据、数据归属、流程交接、取舍、结构化任务和独立交接包 | 结论区分依据、项目假设和待决定项，不依赖强制单一分类 |
| 7 | P1 · 必须 | 修复重要问题并收口 M5 | 缺陷与复验记录、U17-A1 至 U17-C5 证据矩阵、完整回归和状态文档 | 阻塞项清零；重要项已修复或有明确延期理由；两条入口可持续迭代 |
| 8 | P2 · M5 后决策 | 评估执行后端演进 | OpenCode 继续复用、局部替换或局部自研的证据化决定 | 已取得三个案例的首次通过率、重试、恢复、控制能力和成本数据 |

执行中只立即开发阻断当前案例、造成错误状态、破坏项目隔离、写回安全或验收真实性的问题。布局、效率、多引擎、云端执行和通用 harness 能力先记入发现清单，在 M5 证据完整后排序，避免试点变成无边界的平台扩建。

## 11. 后续自研范围的决策要求

对具体任务出现行为控制或部署限制，或实测质量、稳定性、总成本存在可改善空间时，按设计稿 §9.5 评估。先记录当前引擎和适配方案的局限及尝试，再比较继续复用、替换后端和局部自研。

优先评估边界明确的分析、文档更新等任务能否直接调用模型和工具完成；这种演进不要求同时重写代码执行引擎。

每次决策记录工作负载、证据、备选方案、自研范围、维护成本与验证办法。未证明收益的全面重写不进入既定排期，长期复用 OpenCode 本身不构成架构失败。
