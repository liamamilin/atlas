# 试点发现

结论：只靠助手可以走完全流程，但这次试点暴露了 5 个与助手无关的 Atlas 执行链路缺陷，任何一个都会让普通用户卡住：

- 生成越界误报；
- 默认模型已下线且界面不显示原因；
- 父仓库提交使基线失效；
- 长任务永远显示「运行中」；
- 缺少卡住检测。

前 4 个已修复并有回归测试，最后一个列为待办。

助手方面，主要问题集中在「请求体该怎么写」：

- 接口提示不全时，模型会反复猜测重试；
- 提示补全后，同类步骤一次就能通过。

## 已修复

| 编号 | 类别 | 事实 | 处理（提交） |
|---|---|---|---|
| F01 | 生成 | 越界检查把服务自身运行时文件（`oss-catalog.sqlite-shm`、恢复记录、目录 mtime）算作 OpenCode 写入，所有生成都会失败。这是 10-19 引入检查后的回归 | 排除服务自身状态目录，凭据和源码仍受检查（`00f1dfc1`） |
| F02 | 助手 | 批准后又提出同一个写请求，或重复提出应用请求 | 同一轮内已批准的相同请求直接拒绝；操作者发新消息后允许重试（`f793eacf`、`01dcadd8`） |
| F03 | 助手 | 回放全部历史结果、读取整页数据，导致 token 超限 | 只回放最新一次结果；读取支持 `select` 和通配符；大结果给出提纲（`f793eacf`、`01dcadd8`） |
| F04 | 助手 | 没有调用工具却声称「已提交，请确认」；说「我会继续」后停下；全部完成后还反复核实，直到步数用尽 | 虚假声明会被附注标记；批准说明里写明下一步怎么做、何时停（`f793eacf`） |
| F05 | 助手 | 猜错 `item_key`；问题类条目误用 `resolved`（应为 `answered`） | 待决问题路由的提示写明准确字段和状态（`01dcadd8`） |
| F06 | 助手 | 建迭代时 `input_document_versions` 填了 `doc_` 编号，返回 409 | 提示改为使用 `documents.*.version_id`（`dver_…`）（`37c62962`） |
| F07 | 执行/助手 | 执行状态只在调用 reconcile 时推进（网页每 1.5 秒调用一次），助手每查一次进度都要操作者点确认 | reconcile 定为 `sync` 风险，免确认直接执行；执行详情的提示说明它不推进状态（`37c62962`） |
| F08 | 执行 | 默认执行模型 mimo-v2.5 已被 provider 下线，每次代码执行都失败；Atlas 只记录 `provider.invalid-request`，界面不显示 | 保存 provider 原文（脱敏、截断）为 `error_detail`，任务页显示「执行引擎报错」（`002743bf`）；默认模型见 F13 |
| F09 | 基线 | 项目工作区默认位于 Atlas 仓库内，基线指纹包含父仓库 HEAD；Atlas 任意一次提交都会让所有项目报「工作区与已接受基线不一致」 | 工作区不是仓库根目录时，HEAD 和分支不计入指纹。指纹按已存清单重新计算，旧基线无需重录（`0e8ea5e4`） |
| F10 | 执行 | OpenCode v2 消息没有父消息编号，Atlas 只在最新 20 条里找本任务的提示。执行超过约 20 步后提示被挤出窗口，执行永远显示「运行中」 | 窗口里找不到提示时，按服务端上限 200 条重新读取（`30d05032`） |
| F11 | 助手/验收 | 验收提示没写 `condition_results`，助手连续提交 14 次都返回 409；错误信息也没说缺哪个字段 | 提示写明字段、来源（`task.requirement_snapshots`）和 passed/waived/failed 规则；409 信息说明应发送什么（`66db00d9`） |
| F12 | 助手 | 操作者只要求改一个字段，但新消息会取消待确认卡片，模型只能从头重建 22 条条件，结果 token 超限 | 被拒绝或被取代的最近一次请求体会回放给模型，供其在原基础上修改（`66db00d9`） |
| F13 | 执行 | 改用的 mimo-v2.6-flash 只通过了「回复 ok」测试，首次真实执行就挂起（O1）；deepseek-v4.1-flash 完成了本试点和 10 月的多步批处理 | 默认执行模型改为 `opencode-go/deepseek-v4.1-flash`，可用 `ATLAS_EXECUTION_MODEL` 覆盖（本次提交） |

## 未修复

| 编号 | 类别 | 事实 | 建议 |
|---|---|---|---|
| O1 | 执行 | 模型流挂起后没有任何检测：mimo-v2.6-flash 在第二个回合 5 秒后停止输出，Atlas 约 20 分钟一直显示「运行中」 | reconcile 时比较引擎最近一条消息的更新时间，超过阈值（如 5 分钟）标为「疑似卡住」并提示停止或换模型 |
| O2 | 执行 | reconcile 最多读取 200 条消息，超过 200 步的会话仍会卡在「运行中」 | 按 OpenCode v2 游标分页，直到找到任务提示 |
| O3 | 需求/验收 | 决定「不做短休/长休」之后，需求的验收条件仍然包含短休/长休。整体 `passed` 不允许混入 `waived`，只能把这条记为按决定收窄的 `passed` 并写明理由 | 记录决定时，提示修订受影响需求的验收条件（生成新修订版本），而不是放宽验收规则 |
| O4 | 助手 | 流程跳步：只确认 1 条需求就启动生成；未经要求就提议启动执行 | 写操作前先核对前置条件（如生成前所有需求都已确认），或由服务端在提示中返回缺少哪些前置条件 |
| O5 | 助手 | 调用不存在的接口（`GET …/documents` 返回 404、`GET …/tasks/{id}` 返回 404）；重复读取整个工作区；回复里的条数与请求体不一致（说 23 条，实际 22 条） | 为常用读取补充专门路由或 `select` 示例；回复的数字应取自请求体 |
| O6 | 助手 | 同一路由连续出现相同错误时仍会继续换写法重提（在操作者批准的前提下） | 同一路由连续两次返回相同 409 后，停止并把错误原文交给操作者 |
| O7 | 执行 | API 重启会把运行中的执行标为 `unknown`。之后调用 reconcile 可以恢复为 `completed`，本次已验证 | 按设计工作；界面应提示「重启后需要同步」 |

## 设计结论

- 「读取立即执行、写入逐条确认」的助手边界成立。75 张确认卡片都是先经操作者确认、再由服务端校验后执行，没有出现越权写入。唯一免确认的写入是执行状态同步（F07），它做的事与网页无人值守时的轮询相同。
- 助手的可靠性主要取决于接口目录的请求体提示是否准确。F05、F06、F11 都是提示不全造成的反复试错，补全后同类步骤一次即可通过。
- 执行链路的缺陷（F08–F10、O1）比助手本身更影响可用性。这些缺陷都要真实跑一次执行才会出现，说明这条路径需要定期做端到端验证。
