# 执行与验收记录

状态：普通基线、Atlas 分析、六项范围确认、四份文档应用和 T1–T5 当前范围验收已完成；本案例以契约和只读端到端分析为边界，未进入真实 provider 或模拟适配器实现。

## 计划中的最小任务

1. 建立三类记录的主记录与稳定 ID 契约。
2. 建立项目工作项到个人日程事件的单向交接和冲突恢复。
3. 建立交付物到客户审批请求的单向交接、退回和超时处理。
4. 建立审批结果返回项目计划的状态映射、幂等键和人工接管。
5. 导出独立开发文档包并由新会话核对范围、依赖和验收条件。

## 验收条件

- 任何交接都能回答来源 ID、目标 ID、当前状态、责任人和时间戳。
- 审批批准不被误写成项目已完成；项目完成仍由工作项的明确完成条件决定。
- 审批退回、超时、重复回调和日程冲突有可见状态与恢复动作。
- 导出包不依赖当前会话，且清楚区分类型事实、项目假设、推断和待决问题。
- 首轮没有自动双向同步、自动资源排程或客户认证/计费实现。

## 普通方案与 Atlas 对照（初步）

- 普通方案在来源正文可用时正确提取了 backlog、工作项、日历事件、审批请求和审计轨迹，并明确指出“交付物”作为独立实体没有被来源覆盖。
- 普通方案提出了 8 个用户问题和 8 项最小任务，但部分任务把“客户审批回写工作项”“工作项 key / 事件 UID”等实现细节提前假定为系统能力。
- Atlas 分析把候选范围拆成 6 个需求、6 个问题、3 个冲突和 6 个建议，并将项目目标与引用的 project note 作为依据边界；它明确区分审批状态、工作项状态和个人日历事实。
- Atlas 仍有需要人工复核的推断，例如稳定 ID 的具体格式、审批平台是否支持客户外部参与者、以及“日历只读时间块”的实现方式。它们不得直接作为已确认需求。
- 当前初步结论：Atlas 在跨类型边界、冲突和开放问题的组织上比普通方案更完整；普通方案对资料缺口的提示更直接。正式结论要等人工确认首轮范围后再写入需求和决定。
