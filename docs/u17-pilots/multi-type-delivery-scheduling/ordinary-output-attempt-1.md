## 二、产品假设（结合本案例形成）

> 以下假设基于"小型客户交付团队"这一通用场景推演，未经来源正文验证。

| 编号 | 假设 | 说明 |
|------|------|------|
| A-1 | Backlog 是任务的主记录容器 | 所有工作项（需求、缺陷、任务）均挂载于项目 backlog，backlog 记录为主记录。 |
| A-2 | 交付物与工作项一对多关联 | 一个工作项可产出多个交付物，交付物以工作项 ID 为外键。 |
| A-3 | 个人日程独立于项目排程 | 日程记录由用户本人创建，项目排程向个人日程做单向引用。 |
| A-4 | 客户审批请求绑定交付物 | 审批请求以交付物 ID 为锚点，审批状态变更回写交付物状态字段。 |
| A-5 | 任务状态变更采用"推送"模式 | 任务完成时主动向下游传递新状态，不做双向实时同步。 |
| A-6 | 权限按角色划分 | 项目经理可编辑 backlog；开发人员可更新任务状态；客户仅有审批权限。 |
| A-7 | 失败恢复采用幂等重试 | 同步失败时记录失败快照，支持手动触发重试。 |

| 编号 | 推断 | 验证方式 |

| V-2 | 交付物是否需要独立版本管理 | 需确认 `approval-workflow-platform.md` 中审批通过后交付物是否生成新版本。 |

## 六、最小可验收开发任务清单

> 以下任务基于产品假设列出，每项附验收条件。因来源正文缺失，任务优先级与依赖关系需用户确认。

| 任务编号 | 任务描述 | 验收条件 |
|----------|----------|----------|
| T-1 | 设计 Backlog 数据模型（含工作项、状态枚举） | 能通过 API 创建项目并添加工作项；工作项有唯一 ID、类型、状态、负责人字段。 |
| T-2 | 实现工作项 CRUD 接口 | 能创建、读取、更新、删除工作项；返回数据包含稳定 ID 与当前状态。 |
| T-3 | 实现工作项状态流转 | 能按预定义状态（待办→进行中→已完成）推进任务；非法状态流转返回错误。 |
| T-4 | 设计交付物数据模型 | 交付物记录包含 ID、关联工作项 ID、文件/链接、创建时间、状态。 |
| T-5 | 实现交付物挂载接口 | 工作项下可添加交付物；交付物与工作项通过稳定 ID 关联。 |
| T-6 | 实现审批请求创建接口 | 交付物状态为"待审批"时可发起审批请求；审批请求包含交付物 ID、审批人、状态。 |
| T-7 | 实现审批结果回写逻辑 | 审批通过→交付物状态更新为"已批准"；审批退回→交付物状态更新为"退回"，同时回写工作项状态。 |
| T-8 | 实现个人日程视图（只读） | 开发人员登录后可查看分配给自己的任务及其截止日期；数据从工作项负责人字段关联查询。 |
