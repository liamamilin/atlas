# M5 案例三 · 客户项目交付与个人排程 — 开发计划

## 1. 开发策略

采用增量交付策略，按依赖顺序分四个迭代完成。每个迭代产出可独立验证的增量，确保上游文档（产品需求、技术方案）在开发前已确认。

---

## 2. 迭代规划

### 迭代 1：关联表服务与基础集成（第 1-2 周）

**目标**：建立跨系统映射基础设施

**工作项**：
1. 设计并实现 cross_system_mapping 表结构
2. 实现关联表 CRUD API
3. 实现审计事件发布框架
4. 编写关联表服务的单元测试和集成测试

**验收标准**：
- 关联表可正确创建、查询、更新、软删除映射记录
- 映射记录变更自动发布审计事件
- ID 映射可审计且不可变（物理删除被禁止）

**依赖**：PR-002（跨系统稳定 ID 映射）

---

### 迭代 2：审批到项目 Handoff（第 3-4 周）

**目标**：实现审批决定到工作项状态的单向交接

**工作项**：
1. 实现审批决定事件监听器
2. 实现 Handoff 处理服务（含状态映射逻辑）
3. 实现敏捷 PM 工作项状态更新 API 调用
4. 实现交接失败通知和重试机制
5. 编写 Handoff 集成测试

**验收标准**：
- 审批 Approved/Rejected/Return/Withdrawn 四种决定正确触发工作项状态转换
- 交接事件同时记录在审批审计轨迹和工作项历史中
- 交接失败触发通知并可手动重试

**依赖**：迭代 1（关联表服务）

---

### 迭代 3：项目到日历只读引用（第 5 周）

**目标**：实现 Sprint/里程碑时间块到日历的只读引用

**工作项**：
1. 实现 Sprint/里程碑时间变更事件监听器
2. 实现日历只读时间块创建/更新逻辑
3. 实现日历引用同步失败的手动重同步接口
4. 编写日历引用集成测试

**验收标准**：
- Sprint 和里程碑时间变更正确创建/更新日历只读时间块
- 日历引用同步失败可通过手动接口重试
- 用户可在日历中查看、隐藏或删除项目相关时间块

**依赖**：迭代 1（关联表服务）

---

### 迭代 4：权限、失败恢复与端到端验证（第 6-7 周）

**目标**：完成跨系统权限隔离、失败恢复机制和端到端验收

**工作项**：
1. 实现跨系统权限隔离（服务账户最小权限）
2. 实现审批停滞自动提醒和升级机制
3. 实现工作项阻塞告警标记
4. 实现端到端 Handoff 场景测试
5. 实现审计日志查询和关联追踪
6. 编写完整验收测试套件

**验收标准**：
- 服务账户仅拥有 handoff 所需最小权限
- 审批停滞自动提醒和升级机制正常工作
- 端到端场景（审批→项目→日历）可完整执行
- 审计日志可跨系统关联查询

**依赖**：迭代 2（审批到项目 Handoff）、迭代 3（项目到日历引用）

---

## 3. 测试策略

### 3.1 单元测试

- 关联表 CRUD 操作的边界条件
- 状态映射逻辑的正确性
- 审计事件格式的合规性

### 3.2 集成测试

- 各系统 API 调用的模拟和验证
- 跨系统 Handoff 的端到端流程
- 关联表与各系统的一致性

### 3.3 验收测试

- 基于 PR-001 至 PR-006 验收条件的场景测试
- 失败恢复场景的手动测试
- 权限隔离场景的验证

---

## 4. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 各系统 API 不稳定 | 集成测试失败 | 使用 API mock 和契约测试 |
| 审计日志存储增长 | 性能下降 | 设定日志保留策略和归档机制 |
| 跨系统权限配置复杂 | 运维负担 | 服务账户权限最小化，自动化配置脚本 |
| 日历引用同步延迟 | 用户体验差 | 设定同步超时和手动重同步接口 |
