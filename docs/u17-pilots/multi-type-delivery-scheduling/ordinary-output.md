# 开发前方案：客户交付与个人排程整合

---

## 一、类型事实（三份正文直接支持）

### 1. 项目 backlog

- 项目 backlog 是一个**有序的、持续重新排优先级的待办工作列表**，归属于一个**持久团队**（Team）。无团队归属即退化为个人任务管理。(`agile-project-management-application.md:49-55`)
- backlog 永远不会"完成"；在每个节奏边界（iteration 或 pull）重新排优先级是主要规划行为。(`agile-project-management-application.md:107`)
- backlog 中的每条工作项有**所有者（assignee）和状态**，以工作项为单位完成，而非计划完成百分比。(`agile-project-management-application.md:44-48`)

### 2. 工作项（Work Item）

- 工作项是**计划工作的单位**，有所有者和状态。(`agile-project-management-application.md:44`)
- 工作项的生命周期：创建 → 进入 backlog → 被拉入迭代/连续流 → 在看板上从列间移动 → 达到完成状态。(`agile-project-management-application.md:133-140`)
- 工作项可以被阻塞、拆分、复制、链接、重新打开或提升（如缺陷提升为 backlog 工作项）。(`agile-project-management-application.md:254`)

### 3. 交付物

- 资料未覆盖"交付物"作为独立概念的定义。交付物在三份来源中**未作为独立记录类型出现**。

### 4. 个人日程（Calendar Event）

- 日历应用的核心对象是**时间锚定的事件（Event）**：一条记录某事何时发生的事物，锚定于日期，通常有开始和结束时间。(`calendar-application.md:34`)
- 事件归属于**持久排程（persistent schedule）**，以可导航的时间网格呈现（日/周/月），跨会话和设备持久化。(`calendar-application.md:35-36`)
- 事件属性包括：标题、时间锚点、重复规则、提醒、位置、附件和笔记、参与者（组织者与受邀者）、所属日历和可用性状态。(`calendar-application.md:42-51`)
- 事件被分组到**日历（calendar）**中——有名称、有颜色的容器，服务于视觉分隔、可见性控制和共享边界。(`calendar-application.md:54`)

### 5. 客户审批请求（Approval Request）

- 审批请求是**授权请求的结构化记录**：提交后由系统按配置规则路由到指定审批者，每位审批者记录明确的批准/拒绝/退回决定，请求状态随之推进直至产生结果。(`approval-workflow-platform.md:5-6`)
- 审批请求包含：请求者身份、结构化表单捕获的数据（金额、日期、行项目、理由）、通常附带附件（收据、报价、合同）。(`approval-workflow-platform.md:35`)
- 请求有**可追溯的决策历史（audit trail）**：提交、编辑、评论、每次决定（附操作者和时间戳）、升级和最终结果的追加记录。(`approval-workflow-platform.md:45`)
- 审批路径由管理员定义一次，然后应用于该类型的所有请求。(`approval-workflow-platform.md:37`)

## 二、主记录归属

| 记录类型 | 主记录归属 | 来源 |
|---|---|---|
| 项目 backlog | 归属于**持久团队**（Team），backlog、看板和节奏都属于该团队 | `agile-project-management-application.md:51` |
| 工作项 | 归属于**backlog**（再归属于团队），有所有者（assignee）和状态 | `agile-project-management-application.md:44` |
| 个人日程 | 归属于**用户拥有的持久排程**（User-managed schedule），再归属于具体日历容器 | `calendar-application.md:34-36` |
| 客户审批请求 | 归属于**提交它的请求者**，由系统记录作为**授权决策的系统记录**（system of record） | `approval-workflow-platform.md:29` |

> 资料未覆盖：交付物作为独立记录类型的定义及其主记录归属。

## 三、跨域数据传递：稳定 ID、责任人与状态

### 3.1 任务进入个人排程

- **数据来源**：工作项（来自敏捷项目管理）需要进入日历（个人排程）。
- **传递内容**：
  - 稳定 ID：工作项的唯一标识（来源支持工作项有 owner 和 status，但**资料未覆盖**跨系统 ID 映射机制）。(`agile-project-management-application.md:44`)
  - 责任人：工作项的 assignee。(`agile-project-management-application.md:53`)
  - 状态：工作项的工作流状态（如"进行中""已完成"）。(`agile-project-management-application.md:44`)
- **日历侧行为**：日历事件是时间锚定的；工作项进入排程需要确定**开始/结束时间**（日历事件的定义要求）。(`calendar-application.md:34`)
- **资料未覆盖**：工作项状态变化是否自动更新已创建的日历事件。

### 3.2 交付物进入客户验收

- 资料未覆盖"交付物进入客户验收"的流程定义。三份来源中**不存在**交付物作为独立实体的描述，也不存在"客户验收"作为审批请求的直接映射。
- 审批请求的关闭和交付（handoff）描述为：最终审批达到 → 结果记录 → 下游动作触发（采购单、付款、访问授权等）。(`approval-workflow-platform.md:134-142`)
- 审批结果触发的是**执行系统中的动作**，而非"交付物进入客户验收"。(`approval-workflow-platform.md:149`)

### 3.3 客户退回或批准返回项目计划

- 审批请求支持**退回给请求者修改（return for revision）**：退回 → 请求者修订 → 重新提交 → 循环继续，历史轮次在记录中保留可见。(`approval-workflow-platform.md:128-129`)
- 批准后触发下游动作；退回或拒绝不直接触发项目计划中的工作项创建。
- **资料未覆盖**：审批退回后如何在项目 backlog 中创建或重新激活工作项的机制。

## 四、同步策略取舍

### 4.1 复制 vs 引用 vs 单向同步 vs 双向同步

| 策略 | 适用场景 | 来源依据 |
|---|---|---|
| **复制** | 不适用。日历事件与工作项是不同类型的对象，直接复制会丢失语义。 | 三份来源均未描述跨类型复制行为 |
| **引用** | 建议方向：工作项创建日历事件时，日历事件引用工作项 ID，但各自维护自身状态。 | `calendar-application.md:93-94`（事件移动/调整大小）；`agile-project-management-application.md:133-140`（看板移动） |
| **单向同步** | 工作项状态 → 日历事件状态：工作项完成时，日历事件可标记为已完成。方向从项目管理流向日历。 | `agile-project-management-application.md:238-242`（完成状态定义） |
| **双向同步** | **不承诺**。来源明确不支持自动双向同步；资料未覆盖跨系统双向同步的失败恢复机制。 | 用户指令禁止承诺"自动双向同步" |

### 4.2 权限边界

- 敏捷项目管理：团队成员、计划者/产品所有者、团队领导、管理员、利益相关者。(`agile-project-management-application.md:28-32`)
- 日历：组织者控制事件并跟踪回复；受邀者只能更改自己的回复。(`calendar-application.md:167`)
- 审批：只有指定审批者才能做出决定；请求者和旁观者只能查看状态。(`approval-workflow-platform.md:193`)
- **跨域权限**：资料未覆盖工作项系统与日历系统之间的权限边界定义。

### 4.3 时效与失败恢复

- 日历事件有**绝对时间锚定**，改变显示时区会重新渲染排程但不会移动事件。(`calendar-application.md:165`)
- 审批请求有**不活跃管理**：提醒和升级是标准机制，因为审批者沉默是最常见的流程失败模式。(`approval-workflow-platform.md:195`)
- **失败恢复**：资料未覆盖跨域同步失败时的恢复策略（如日历事件创建失败后是否重试、如何记录）。

## 六、需确认的问题（≥8）

### 仍需用户决定的问题

1. **交付物的定义是什么？** 三份来源中不存在"交付物"作为独立记录类型的定义。工作项是计划工作的单位（`agile-project-management-application.md:44`），审批请求是授权请求的记录（`approval-workflow-platform.md:35`），但"交付物"作为可验收对象，其结构和生命周期由用户定义。

2. **"客户验收"对应审批请求的哪个阶段？** 审批请求有提交→路由→决定→关闭→交付的流程（`approval-workflow-platform.md:108-142`），但"客户验收"是否等于"最终审批通过"、"关闭"还是需要自定义阶段，需要用户确认。

3. **工作项与日历事件之间的同步方向是什么？** 是否只从工作项→日历（单向），还是日历事件上的状态变化也应回写工作项？来源未覆盖跨系统同步方向的设计决策。

4. **审批请求退回后，应在项目 backlog 中创建新工作项还是重新激活原工作项？** 审批退回有"请求者修订并重新提交"的流程（`approval-workflow-platform.md:128-129`），但退回与项目计划工作项之间的关联机制需要用户定义。

5. **节奏模型选择：时间盒（sprint）还是连续流（kanban）？** 来源明确存在两种节奏姿态（`agile-project-management-application.md:74-84`），选择影响迭代关闭行为、未完成工作结转方式和度量指标。

6. **个人日历是使用用户现有日历服务（如 Google Calendar、Outlook）还是自建日历？** 日历应用的来源描述了与外部日历服务的集成（`calendar-application.md:77`），但自建日历的范围和复杂度需要用户决定。

7. **审批路径是否需要支持条件路由？** 来源描述了基于请求数据（金额、部门、类型）的路由规则（`approval-workflow-platform.md:39`），但第一轮 MVP 是否包含此功能需要用户确认。

8. **审批请求的审批者是团队内部角色还是客户外部参与者？** 来源描述了审批者可以是"命名用户、角色/组、动态规则、外部参与者"（`approval-workflow-platform.md:39`），但客户作为外部审批者的参与方式需要用户定义。

9. **跨域数据传递的唯一标识如何映射？** 工作项 ID、日历事件 ID、审批请求 ID 是三个系统的标识，如何建立稳定的跨系统引用关系需要用户确认。

10. **第一轮范围中的"工作项同步到个人日历"是否需要实时性要求？** 是即时创建日历事件，还是允许延迟？资料未覆盖跨系统事件创建的时效性要求。

## 七、可验收的最小开发任务清单

| 任务编号 | 任务描述 | 验收条件 |
|---|---|---|
| T1 | 实现团队 Backlog 数据模型 | 能创建团队容器，包含有序的工作项列表，每个工作项有所有者、状态和优先级字段。验收：可通过 API 创建团队 → 创建工作项 → 设置所有者和状态 → 按优先级排序。 |
| T2 | 实现工作项状态流转 | 工作项可定义工作流状态列，卡片可在列间移动，有明确的完成状态。验收：可定义 3+ 状态列 → 创建工作项 → 将卡片从一列移动到另一列 → 标记为完成。 |
| T3 | 实现工作项到日历事件的创建 | 工作项可触发创建日历事件，事件有时间锚点和标题，引用工作项 ID。验收：创建有开始/结束时间的工作项 → 系统创建日历事件 → 事件显示在时间网格上 → 事件可追溯到工作项 ID。 |
| T4 | 实现审批请求提交 | 请求者可填写表单提交审批请求，请求有结构化数据和附件，生成唯一请求 ID。验收：填写表单 → 附带文件 → 提交 → 在"我的请求"列表中可见 → 有唯一 ID。 |
| T5 | 实现审批请求状态追踪 | 请求者可查看请求当前位置和等待的审批者。验收：提交请求后 → 查看当前状态 → 知道正在等待哪位审批者。 |
| T6 | 实现审批者决策（批准/拒绝/退回） | 审批者可查看待审批请求，做出三种决定之一，附带评论。验收：审批者打开请求 → 查看详情和附件 → 选择批准/拒绝/退回 → 附加评论 → 决策记录到历史中。 |
| T7 | 实现审批退回与重新提交 | 退回的请求返回请求者，请求者可修改后重新提交，历史轮次保留。验收：请求被退回 → 请求者看到退回原因 → 修改后重新提交 → 重新进入审批流程 → 历史中可看到之前的退回记录。 |
| T8 | 实现审批决策历史（审计追踪） | 所有操作（提交、编辑、评论、决策）追加记录，含操作者和时间戳。验收：执行一系列操作后 → 查看完整历史记录 → 每条记录有操作者、时间、操作类型。 |

## 八、假设与推断说明

### 产品假设（基于本案例形成）

1. 工作项与日历事件之间的关联采用"引用"而非"复制"策略——日历事件引用工作项 ID，各自维护状态。这是因为日历事件的定义要求时间锚定（`calendar-application.md:34`），而工作项的状态定义不同（`agile-project-management-application.md:44`），直接复制会丢失语义。

2. 审批请求关闭后的"交付"触发项目计划中的工作项状态变化——批准触发执行动作（`approval-workflow-platform.md:139-141`），此动作映射为项目 backlog 中工作项的状态推进。

3. 第一轮范围不包含自动双向同步——用户明确禁止承诺自动双向同步。

### 需要验证的推断

1. 工作项的完成状态是否直接触发日历事件的完成标记。资料未覆盖工作项完成与日历事件状态之间的自动联动行为。

2. 审批退回是否应自动在项目 backlog 中创建待办工作项。资料未覆盖审批退回与项目计划之间的自动关联机制。

3. 个人排程中的日历事件是否需要反映工作项的实时状态变化。资料未覆盖跨系统状态同步的实时性要求。

4. 审批请求的审计追踪是否需要与项目 backlog 中的工作项历史合并查看。资料未覆盖跨系统的统一审计视图。
