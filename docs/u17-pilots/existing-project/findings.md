# 案例二对照结论：本地清单 CLI 安全持久化

状态：首轮实现、Atlas 迭代和独立验收完成；案例已封存，尚未提交 Git。

## 输入与证据

- 原项目：`prj_fdee487646e84eb08793d6304ff13f60` 的本地清单 CLI。
- 冻结基线：`snap_a49ae939134642dcaa5905900a38a5bf`；`todo.py` 与 `test_todo.py` 指纹未变化。
- 普通方案：`ordinary-output.md`，由 OpenCode `opencode-go/mimo-v2.5` 生成。
- Atlas 方案：`atlas-output.json`，运行 `gen_d68ed51ca06b4c50bb16ed5c1fd64ba7` 生成；首轮格式校验失败的运行 `gen_08fd77daf9674c03abb9080f8f7315d7` 也已保留。
- 两次输入并非完全相同：Atlas 额外引用了 `task-management-application` 类型资料；因此以下结论只比较方向和可执行性，不比较模型优劣。

## 一致结论

两份方案都确认当前实现存在两个核心问题：`save_tasks` 直接覆盖文件，写入中断可能留下半写入内容；`load_tasks` 对损坏 JSON 没有用户可理解的处理。两份方案也都要求保持 `add`、`list`、`done` 的输出、退出码和 `{id, title, done}` 字段兼容，并建议补充损坏文件及写入失败的回归测试。

## 差异与取舍

| 主题 | 普通方案 | Atlas 方案 | 本案例判断 |
|---|---|---|---|
| 原子写入 | `tempfile` + `os.replace`，写入失败旧文件不变 | 同目录临时文件 + `os.rename` | 保留“同目录临时文件 + 原子替换”原则；实现时优先 `os.replace`，并验证临时文件清理 |
| 损坏读取 | 返回非零错误，不静默重置 | 备份为 `.corrupt` 后返回空列表，允许 CLI 继续 | **暂不接受 Atlas 的自动返回空列表**；这会弱化 EP2-R2 的“不静默重置”和“不覆盖原始内容”。先定义为错误退出 + 保留原文件，备份是否自动化另行决定 |
| 测试范围 | 失败写入、损坏读取、正常流程 | 损坏读取、原子写入，另建议测试辅助函数同步 | 接受核心测试；不把测试辅助函数改造作为独立需求，除非测试实现确实需要 |
| 错误处理 | 纯文本、非零退出 | 错误信息包含路径和原因，可选日志 | 只做 stderr 的可理解错误；日志文件超出当前小 CLI 范围 |
| 需求数量 | 3 个目标方向 | 3 个需求、2 个问题、2 个建议 | Atlas 的结构化拆解有帮助，但不增加范围 |

## 质量检查

Atlas 文档中把现有测试描述为“7 个测试用例”，而冻结基线实际为 6 项；这是生成内容中的事实错误，不能直接作为开发依据。Atlas 输出还把“损坏后返回空列表”写进期望行为，与本案例已经冻结的验收条件冲突，必须在进入实现前修正。

## 进入实现前的最小决策

1. 保留同目录临时文件和原子替换，失败时旧 `tasks.json` 不变，并清理临时文件。
2. 损坏 `tasks.json` 时：输出包含路径和原因的 stderr，非零退出；不覆盖原文件，不自动把它当作空列表。是否生成 `.corrupt` 备份，作为实现细节单独验证。
3. 扩展 `test_todo.py` 覆盖损坏读取、写入失败旧文件不变、临时文件清理，并保持原有 6 项测试通过。
4. 仍只修改 `todo.py` 和 `test_todo.py`，不新增命令、GUI、云同步或数据库迁移。

前面的对照结论用于确定实现边界；实现结果记录在下方，仍需在正式应用前完成基线核对。

## 实现后复验

按上述最小决策在案例工作区完成首轮实现：`todo.py` 使用同目录临时文件、`fsync` 和 `os.replace`；读取损坏文件时以可理解错误退出并保留原文件；`test_todo.py` 增加 4 项回归。改进后共 10 项测试通过，手工 `add → list → done → list` 输出保持兼容。此次没有采用 Atlas 的“返回空列表并继续运行”建议，也没有新增日志、命令或字段。
