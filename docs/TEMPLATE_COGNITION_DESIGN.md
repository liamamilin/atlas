# 认知模板：产品定义与工厂改造方案

日期：2026-10-17；更新：2026-10-19。状态：导入、阅读、OpenCode 自动研究/生成、独立静态审阅和修订已接入。新增三部分开发包与带冻结适配器的下游容器验收，见[本轮实现与边界](template-factory/2026-10-19-factory-refactor/README.md)；旧包不自动获得运行能力，认知发布仍未开放。以下首版路线保留设计来源，实际状态以上述记录为准。

## 1. 这次改变什么

用户明确提出：模板的核心价值是认知，代码仍需要，但交付不能停留在一套项目源码。目标是补足 coding agent 对成熟同类产品的判断：应做什么、哪些现在做、哪些不适用、如何选型、如何处理边界，以及如何证明阶段结果可用。

模板的使用者是准备开发某类应用的人及其 coding agent。拿到模板后，应能确定首阶段的用户闭环，依据来源与默认决策开始实现，按阶段执行验收，并在真正需要人的选择处停下来。成功不以文档数量、功能条数或生成代码量判断，而以重要漏项是否减少、开发与验收是否可推进判断。

原有代码模板自动生产是：确认场景 → 搜索并选择一个开源仓库 → 固定版本 → 改造源码与参数化 → 冻结 → 独立源码审阅 / 运行验收 → 发布 / 创建应用包。它是已经验证的代码模板链路；新的认知包导入/交接、自动研究/生成/独立静态审阅与修订已接入，认知发布和通用下游运行验收仍未开放。当前场景生产链路继续可用；旧制品及证据保留，不能改名冒充认知模板。

新的主要产物是 **认知模板包**：品类知识、场景需求、工程决策、阶段计划、可执行验收及 agent 工作指令，加上有必要且能验证的代码。默认不再要求找一个仓库并把整套代码改成模板。

## 2. 内容如何复用

生产目录仍是“叶子类型 + 已确认应用场景”，无需另造一套分类。

- **品类底座**：该叶子的定义核心、常见角色与完整能力地图、现有产品和开源方案、惯常边界和选型取舍。绑定资料来源及版本，同一叶子的多个场景可以复用。
- **场景适配**：哪些能力服务当前用户目标、哪些属于后期、哪些不适用；据此形成产品定义、默认架构、路线图与验收。
- **项目决策**：使用者是否采用默认方案、是否改变部署与商业形态、是否接入真实外部服务。项目选择不回写或污染通用品类事实。

这三部分首先作为版本化产物中的逻辑结构实现，不预设新增服务、图数据库或独立 harness。默认生产后端继续使用 OpenCode CLI；provider/model 保持可配置，不静默换模型。

## 3. 一个模板交付什么

下表是交付内容职责，不要求机械拆出同样数量的文件。

| 内容 | 应给开发 agent 的判断 | 可核对的依据 |
| --- | --- | --- |
| 品类认知 | 同类 SaaS 与开源方案分别解决什么、适合谁；复用 / 集成 / 自建的建议与代价 | 来源链接、查阅日期、版本或 commit；许可证名称、原文位置与未知项 |
| 成熟产品定义 | 用户角色、核心与异常流程；从 MVP 到成熟版的功能地图、运营与数据生命周期、非功能需求 | 当前叶子定义、场景和产品资料；每项标注来源、适用性、优先级及理由 |
| 架构决策 | 一个推荐默认方案及理由、关键替代方案和切换条件；数据模型、状态变化、API 与错误约定 | 对应的需求及约束；推荐与事实分开，不把偏好伪装成硬限制 |
| 阶段路线图 | 每阶段交付给谁、完成什么真实闭环、依赖什么、怎样验收 | 每阶段关联功能 ID、验收 ID 和必要决策，避免按“先前端再后端”假装产品增量 |
| 可执行验收 | 每阶段的正常与负向行为检查，运行入口、测试数据、适配方式和实际结果 | 需求到用例的映射；执行环境、目标应用版本及真实日志，未运行明确记录 |
| 人工决策点 | 有哪些选项、推荐默认值、影响、可逆性，以及何时必须暂停询问 | 用户已有决定、真实外部约束或明确待验证假设；已回答的问题不反复询问 |
| 必要代码与参考积木 | 支撑启动和契约的最小骨架；高风险环节有需要时提供可验证的参考实现 | 适用条件、来源与版本、已测范围、许可证记录；不把“常见做法”称为已验证 |
| Agent 指令 | 如何读取资料、分阶段实现、运行测试、记录决策、自检和交接 | 引用包内权威内容；不得自行弱化验收、宣称未执行的检查已通过 |

### 成熟产品地图需要覆盖，但实现需判断适用性

权限、计费、运营后台、审计、导出、备份恢复等必须被考虑，不能被默认遗漏；“考虑过”也不等于“全部实现”。每项记录：`本阶段必需 / 后期适用 / 不适用 / 待用户决定` 及理由。

例如，个人本地书签工具需要考虑持久保存、搜索、导出、删除恢复或备份；多人共享版本需要考虑成员权限、共享撤回与数据边界；商业托管版本还需评估套餐、计费、支持与运营。后两者的能力不应被自动加入个人本地版本的 MVP。具体清单仍需资料和场景支持，这些是划分方式的示例，不是所有书签模板的强制要求。

优先级与成熟度分别表达：某功能可以是成熟商业产品的标准能力，却不适合当前场景；某个异常处理即使代码很少，也可能是 MVP 完成用户闭环的必要条件。不得靠堆积企业功能让清单显得完整。

## 4. 最小产物协议

建议首版目录如下；实际可合并篇章，结构化清单和叙述文档需来自同一份规范数据，不能各自产生相互冲突的答案。

```text
product-blueprint/
  template.json          # 类型/场景版本、产物类型、文件清单、来源、摘要与证据
  README.md              # 谁适用、交付范围、如何开始、哪些部分尚未验证
  CATEGORY.md            # 品类地图、可复用方案、来源与选型依据
  PRODUCT.md             # 角色、流程、分期功能、边界与非功能需求
  ARCHITECTURE.md        # 默认方案、数据与 API 契约、关键取舍
  ROADMAP.md             # 阶段目标、依赖、验收入口
  DECISIONS.md           # 人工选择、默认值、影响与当前决定
  AGENT.md               # 包内开发执行指南
  acceptance/
    plan.json            # 用例、阶段、需求映射、运行方式与所需适配
    tests/               # 与明确目标接口连接的测试程序
    README.md            # 运行命令、数据准备、清理与结果解释
  references/            # 按需：参考模块、来源和已验证范围
  starter/               # 按需：可启动骨架及示例配置
```

`template.json` 建议引入显式产物类型 `product-blueprint`，旧模板保留独立的 `runnable-starter` 类型或兼容版本。不能把旧包的数据结构静默改掉。新版规范使用稳定 ID 关联来源、角色、流程、功能、实体/API、决策、阶段和验收，例如：

```text
来源 S-* → 功能 F-* → 阶段 P-* → 验收 A-*
                 ↘ 决策 D-* → 数据/API 契约
```

字段至少能表达：适用性、阶段优先级、来源/推导/未知、推荐默认值、替代方案及理由、实现状态和验证证据。ID 用于查漏和交叉引用，不要求建立新的知识图谱平台。

不要强制每份模板生成完整 starter；也不能因为没有完整应用就省略可执行验收、关键契约或有价值的参考代码。代码是否加入，取决于它是否缩小关键实现风险或让目标阶段真正可启动，而不是固定代码行数。

## 5. 验收如何做到可执行且不自欺

### 需求到行为

每个阶段需有明确的可执行入口、目标应用地址或 CLI 接口、测试数据、前置条件和结果判据。验收对应可观察行为，不用“文件存在、页面标题出现”代替用户流程成功。

负向用例按风险选择，例如：失败后是否丢数据、重复提交是否重复生效、已撤销权限是否仍可读取、导出范围是否正确。仅在相应能力适用时纳入该阶段。计费、回调、权限等不能只测正常路径；不适用的能力无需生成假测试。

### 需要不同实现时怎样执行

推荐的默认架构应提供一致的 API / CLI / 行为契约，使测试可以通过适配器连接真实实现。必要的浏览器测试应引用明确的交互约定；不能为尚未生成的界面臆造 CSS 选择器，再声称测试已可用。实现选择改变时，记录契约变更并调整适配，不能把验收降为无关的页面冒烟检查。

验收程序可先通过正向/故意错误的测试目标自检，证明它能识别预期失败。这只表示测试工具有效，不证明用户应用已实现。未完成的应用不能靠 mock 代替目标而获得产品验收通过。

### 证据必须分开

分别记录：资料已核对、产品定义独立审阅、结构/契约检查、测试工具自检、参考模块实测、下游应用阶段验收。测试状态可为待实现、待运行、执行失败或通过，并绑定对应版本与证据。

“认知审阅通过”不等于“应用已经能运行”；“参考模块测试通过”不等于“整套产品成熟”。现有代码模板 L0–L3 的历史定义和证明保留。新版若继续使用等级，需要按产物类型明确验收含义后再开放晋级，不直接套用旧代码模板的 L1 规则。

## 6. 工厂生产技术路线

新的主线建议为：

```text
固定叶子 + 已确认场景
  → 多源调研与来源记录
  → 品类底座：事实、惯常能力、差异、未知
  → 场景适配：功能适用性、默认决策、阶段范围
  → 架构/数据/API + 路线图 + 验收联合生成
  → 必要 starter / 参考模块与验证
  → 独立认知审阅 + 确定性一致性检查
  → 修订、冻结认知模板包
  → 按需下游开发试用与真实阶段验收
```

**研究与选源。** 从“必须选一个 GitHub 仓库”改成“建立适用的产品与技术证据集”。SaaS 官方资料用于能力和行为调研，开源资料用于实现与复用判断。引用记录查阅日期、所支持的结论和版本；源码复用记录对应版本及许可证原文，未知项明确保留。没有合适的可复用项目不应阻止有依据的产品定义，不能为交差捏造仓库。需要引用代码时，再取得相应范围的固定源码，避免默认下载全部上游仓库。许可证事实记录不等于已完成所有用途的法律审查。

**联合生成。** 先输出结构化规范，再派生开发文档与测试。跨文件共同使用功能、阶段与验收 ID。独立 agent 检查品类关键能力遗漏、场景适用性、流程与异常闭环、实现/测试一致性、默认方案理由及人为追加的无依据要求。不能只让源码 reviewer 检查“存在这些文件”。

**程序检查。** 核对引用有效、需求与用例映射、决策未决时的执行边界、文件与摘要、可运行入口及结果证据。映射完整不自动等于内容合理；语义判断和真实下游试用仍独立。

**复用现有基础。** 保留工厂队列、批次、版本固定、检查点、取消/重试、制品摘要和独立验收通道；新增产物类型、相应 pipeline 与 reviewer，而非重新开发一个 harness。生产与后续下游应用验收继续分开。

### 现有实现的具体改动点

| 现有位置 | 当前行为 | 新方向所需改动 |
| --- | --- | --- |
| `pipeline.py` | 单仓库发现、固定源码、改造、冻结 | 按产物类型分支，增加多源研究、规范生成、认知审阅；代码改造成为按需步骤 |
| `sources.py` / CLI 读取策略 | 以公开 GitHub 仓库和有限文档来源为主 | 支持研究证据而非仅源码；扩展适用官方资料读取，继续限制不可信输入影响 |
| `artifacts.py` | 应用参数化渲染；禁止上游 agent 配置入包 | 增加认知包规范和一致性检查；区分 Atlas 生成的执行指南与不可信上游指令 |
| `store.py` / 验收记录 | 场景、任务、旧代码制品和验收 | 固定品类底座与场景版本，记录新包类型及实际证据范围，保持旧记录兼容 |
| `/factory` / 叶子页 | 候选代码模板、下载与创建应用包 | 展示能力地图、分期、决策和验收范围；新包入口明确为“创建开发包 / 交给开发 agent” |

当前 `artifacts.py` 对 `AGENTS.md` 等文件有禁入规则，是为避免上游指令被直接带入模板。新需求不能通过直接取消所有检查实现。Atlas 自己生成并纳入审阅、版本和哈希清单的 `AGENT.md` 应与上游文件分开处理；若后续按目标 agent 的习惯导出为 `AGENTS.md`，也必须沿用相同来源和审阅边界。包内指南不得授予外部访问、传送凭据或自改权限的授权。

已有项目导入新包时，先核对现状和项目已有决定，不覆盖现有开发指令或配置。默认方案是可采用的建议，不应让 agent 推翻已经工作的系统重新搭建。

## 7. 人工决策如何影响推进

每个决策写明：问题、候选项、推荐默认值、理由、影响、可逆性和对应阶段。

- 已有用户决定优先，未变化时不反复询问。
- 可逆、不会改变用户核心目标的常规工程选择，使用已声明默认值继续，并记录选择。
- 商业形态、数据归属、角色信任边界等会改变主要需求的选择，在依赖阶段开始前澄清；可先生成不同选项及影响，不因此阻塞所有资料整理。
- 涉及真实支付、生产数据删除、权限扩大或对外发布等操作，不能由模板的默认值代替用户对实际操作的授权。
- 未验证的性能、预算、成功率或时间估计标成假设，不变成阻塞开发的硬门槛。

`AGENT.md` 引导顺序为：核对当前项目与决定 → 选择当前阶段 → 实现用户闭环 → 执行对应正常/负向验收 → 保留实际证据 → 处理失败或报告阶段完成。不能自动跨越未决事项、改写失败判据、用假数据冒充真实验证，或一次展开所有成熟版功能。

## 8. 当前实施顺序与完成标准

以下保留实施顺序。当前样板、产物交接、自动生产与静态审阅已接入；真实应用验收及不同品类泛化仍需逐项验证。

1. **先做一个具体认知模板样板和规范数据。** 沿用已确认的“生活待购与灵感收藏夹”场景，形成可读认知包及阶段验收，核对能力适用性、决策、API 与测试能否相互对应。已有书签代码候选只作为可选参考和已验证范围证据，不冒充全部成熟能力。样板所需的同类产品与官方资料研究已执行，范围见 CATEGORY.md。
2. **接入产物协议与生成流水线。** 引入新类型，在现有 OpenCode CLI、队列与冻结机制中生产规范、文档和按需代码；旧代码模板继续可读取。完成标准是从一个确认场景得到可下载、有来源、可独立审阅的认知包。
3. **接入认知审阅和验收程序检查。** 语义审阅检查关键遗漏与矛盾，程序检查引用/契约/阶段映射；用例能通过明确适配作用于真实实现，错误目标不能被误判为产品成功。
4. **完成用户侧交接并实际试用。** 页面能够阅读核心定义与阶段、查看或填写项目决策、导出开发包。让开发 agent 仅依赖该包、项目现状和已确认决定完成首阶段，执行实际正负向验收，找出模板没有讲清楚或 agent 仍漏掉的关键行为并修订。
5. **样板可用后扩大到不同类型。** 按实际问题改进品类底座复用和场景适配，再逐批生产。先前约 7.5 万 token/叶子的实测只适用于场景草案与审阅，不能作为本方案的用量或成本估计。

首个样板的观察重点是：是否帮助 agent 识别场景必要能力与不适用能力、做出可解释的默认决策、完成阶段闭环及真正验证异常行为。需要时用同一任务和开发 agent 对比“仅给场景”和“提供认知包”的实际结果，不先虚构提升百分比或强制建立评测平台。

初版设计整理阶段未调用新的模板生产任务，没有改动场景状态、旧模板制品或发布记录。后续对外模板研究与生产按其实际资料范围和用途处理；已有“后续场景生成/审阅”授权不扩大解释为模板源码生产授权。

## 阶段与回归覆盖的协议语义

阶段列表按交付顺序排列；能力的 phase 表示首次交付阶段，必须在该阶段有至少一项验收。后期用例可以回归已经交付的早期能力，仍需保持能力/用例双向引用；早期用例不能依赖后期或未分期能力。各阶段 features 列出本阶段首次交付的能力，acceptance 列出本阶段执行的用例；不能为了凑映射复制或重复宣布同一能力。结构规则不代替程序语义检查，P0 代码提前调用 P1/P2 接口仍是缺陷。

## 2026-10-19 跨品类形式分析

预算、设施预约、批量改名已完成无模板、完整附件与相同知识包分层按需的真实对照运行，见[报告与限制](template-factory/ab-tests/cross-domain-2026-10-19/REPORT.md)。共同规格明确时，无模板也能通过主线；分层不是一次交付正确的保证。改名事后探索发现无模板首版的根外回执写入，两模板首版通过同一探针，缺陷经一次修复后关闭；这个有限样本不证明通用收益、安全或最佳形式。

推荐以一个版本化知识源生成完整规划视图与当前阶段执行视图，结合独立真实验收。规划保留品类、成熟能力和阶段路线；编码入口直接展开完整当前旅程、关键不变量、必要回归、已确认决策与契约入口，其余按任务读取。危险代码只作为可选、验证过的积木。详见[形式分析](template-factory/ab-tests/cross-domain-2026-10-19/FORM_ANALYSIS.md)，这是待落实的导出改进建议，不能写成已上线的新结构。

本轮各格仅一次初始生成，作者禁止执行，共同 P0 已给出大部分边界，预算还保留了共同额外 stdin 输入偏差；因此更适合判断实施和交接问题，尚不能充分衡量普通用户说不全需求时的认知补全价值。后续应保持集成契约一致，改用稀疏目标与独立领域检查表，观察适用需求、误加复杂度和真正人工问题，再讨论更稳定的质量/成本差异。新包自带程序未整套执行，候选未发布，旧书签待验收项保持原状态。
