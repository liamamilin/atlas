## 1. 本轮实现

M4 已从底层探测模块进入项目工作台。用户可以：

1. 用已确认的本版需求和不可变文档版本建立活动迭代。
2. 在迭代内创建 `analysis`、`document` 或 `code` 任务，固定允许写入路径和验证命令。
3. 从项目页启动 OpenCode、查看运行状态、处理权限请求、回答或拒绝问题，并停止执行；会话不可用时可明确关闭记录。
4. 让 OpenCode 在 Atlas 管理的隔离工作副本中读写；项目源目录在结果应用前保持不变。
5. 查看 Atlas 自己比较得到的新增、修改、删除与越界文件，不依赖 OpenCode `diff` 是否完整。
6. 查看结构化命令证据：命令、是否属于预先固定的验证、退出码、输出和截断状态。
7. 显式应用范围合规的结果。Atlas 再次核对源工作区和基线，以带回滚的原子文件替换写回，并把精确写回状态记录为新项目基线。
8. 将 agent 执行完成、结果应用和产品验收分开处理；只有记录 `passed` 或明确 `waived` 后，迭代才能完成。
9. 对已完成、失败或停止的最新结果发出后续指令；复用同一个 OpenCode session 和隔离副本，但为新一轮保存独立前后快照。被续作或新重试取代的旧结果标为 `superseded`，不能再应用。

## 2. Atlas 拥有的执行输入

`ProjectStore` schema 升级为 v5。任务记录：

- 任务类型。
- 工作区内的相对写入路径。
- 预先固定的验证命令。

执行记录保存：

- 源项目绝对目录和本次隔离副本绝对目录。
- 项目、迭代、任务、文档版本、确认需求和项目基线的不可变输入摘要。
- 引擎实际能力表；`follow_up` 已按真实同会话验证记录为 `true`。
- `pending`、`applied`、`conflict`、`failed`、`superseded` 或 `not_applicable` 的结果应用状态、应用快照和新基线 ID。

启动前必须满足：任务属于活动迭代，所有绑定需求仍是用户确认的本版范围，存在已接受项目基线，当前工作区内容指纹与该基线一致。检查不通过时不创建引擎会话。

SQLite 局部唯一索引按源项目目录阻止两个活动执行。即使每次运行拥有不同副本、多个 API 请求并发进入，数据库仍是最后一道互斥边界。

工作副本只复制 Atlas 基线中记录的文件。`.git`、`.hg`、`.svn`、`.venv`、`node_modules`、`dist` 和 `__pycache__` 不进入副本；指向项目外部或使用绝对目标的符号链接在启动前被拒绝。若默认执行目录落在源项目内部，Atlas 自动改用系统临时执行根；也可用 `ATLAS_EXECUTION_ROOT` 指定项目外目录。若 `ATLAS_PROJECT_STORE` 本身位于源目录内，启动会直接拒绝，避免执行记录改变待核对的源项目。

## 3. OpenCode 适配与运行时

`opencode_client.py` 新增了待回答问题的查询、回复和拒绝接口；`reconcile()` 现在同时读取会话、状态、消息、引擎差异、权限与问题快照。

`opencode_runtime.py` 优先连接 `ATLAS_OPENCODE_URL` 指定的本机服务；没有配置时，由 Atlas API 进程启动一个绑定 `127.0.0.1` 随机端口的 `opencode serve --pure`。运行时禁用外部目录、Web 和子任务；代码与文档任务可在权限策略下使用 Bash，分析任务禁用写入与 Bash。

SSE 能力仍保留在适配层，当前项目页轮询官方快照端点。这是可恢复性选择：页面断开后不需要重放事件才能恢复状态。

异步提交后，Atlas 记录本轮 OpenCode 用户消息 ID，用它筛选同一 session 内属于当前轮次的 assistant、权限和问题记录。OpenCode 在用户消息已落库而 assistant 尚未开始时会短暂返回 `idle`；Atlas 将这种状态保持为活动中，避免误报 `unknown` 并停止轮询。续作前必须确认源基线未变、隔离副本与上一轮已记录的结束快照完全一致。

## 4. 成果与验证证据

Atlas 从 OpenCode 消息的 tool parts 中提取命令及退出码，并把执行结束时的文件快照与执行前快照比较。因此页面的“验证通过”依据是结构化命令记录，文件变化依据是 Atlas 指纹，不是只显示 agent 的自述。

项目导出 manifest 升级为 schema 5，包含：

- `iterations.md`：迭代、任务、写入范围、验收和执行摘要。
- `execution-records.json`：完整的机器可读执行记录。
- `handoffs/<task-id>.md` 和 `.json`：不依赖旧 OpenCode 会话的任务交接材料。
- manifest 中的迭代、任务、执行计数，活动迭代、待验收任务和未应用/冲突结果。
- 每次执行的隔离目录、结果应用状态、应用快照和新项目基线。
- 经过严格 JSON 形状和需求 ID 集合校验的 agent 完成报告，以及报告缺失/无效的执行 ID。

任务提示要求最终输出一行 `ATLAS_RESULT`，逐项报告绑定需求的 `satisfied`、`unsatisfied` 或 `not_checked` 状态，并列出未完成项和方案偏离。Atlas 只验证格式、ID 完整性和证据字段，不把 agent 自述升级为独立验证或产品验收。

## 7. 已知边界

- 隔离副本保护项目源目录，写入范围仍由任务指令、OpenCode 工具边界和 Atlas 执行后核对共同约束；Bash 不是操作系统级沙箱。任何越界结果都不能应用，工具权限仍需按请求处理。
- 被忽略的本地依赖目录不复制到隔离副本。依赖 `node_modules` 或 `.venv` 的项目暂时需要系统级命令环境，后续可增加只读依赖挂载或按项目配置的准备步骤。
- 需求覆盖、未完成项和方案偏离已结构化并校验，但其内容仍来自 agent；页面和导出明确区分这类报告、Atlas 自有文件/命令证据和产品验收。
- 连接故障不会被猜测成引擎停止；Atlas 保留活动记录并允许重试。引擎明确返回会话 404 时记录为 `unknown`，用户关闭后保存停止状态和最终文件快照。

因此本记录证明“真实引擎在副本修改 → 同会话继续并建立新快照边界 → 源目录保持不变 → Atlas 差异与命令证据 → 冲突安全写回 → 新项目基线 → 独立验收 → 迭代完成 → 独立导出”已连通。结构化需求报告仍属于 agent 证据，不能替代产品验收。
