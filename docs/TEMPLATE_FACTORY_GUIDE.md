# 模板工厂使用说明

## 从目录开始

启动 Atlas 本地 API 和网页后，打开顶部“模板工厂”，或从类型叶子的“应用场景与模板”进入。

自动生成入口位于“生产目录”顶部的 **“生成应用场景”** 区域。默认筛选“未生成”；搜索生产叶子、勾选建议每批 1–3 个叶子，核对模型后，点击区域右上方“生成场景草案（N 类型）”。并发与超时可展开调整。生成后自动转到任务批次，草案自动排入独立审阅。

生产叶子的搜索和下方“查看已有场景”的搜索分别独立。叶子列表显示“未生成 / 已有 N 个场景 / 已调研，暂无场景 / 生成中或排队中”，可按生成状态筛选。归档场景也计入已有场景，完成调研但零新增的叶子不会继续出现在未生成列表。需要主动补充时，切换“已有场景 / 已调研”或“全部叶子”，并勾选“允许补充生成”；它会再次调用模型。正在生成或排队的叶子始终不能重复提交。

叶子选择跨筛选保留；如果轮询发现所选叶子已经有场景、完成调研或进入生成，会按当前模式跳过并提示。新批次在服务器的同一写事务里再次检查：默认模式拒绝已有场景或已完成调研的叶子，同时拒绝仍在排队或生成的同叶子任务，避免两个页面同时误提交。默认模式通过 `skip_generated: true` 传给 API；省略此参数的旧调用保留原有补充生成行为，但仍不能重复排队同一个叶子。

生产目录按“叶子类型 → 应用场景”分组，组头显示场景总数、草案 / 已确认 / 已归档数量及已选数量。所有类型视图默认收起多个分组；筛选单个叶子或搜索时直接展开匹配场景，也可手动全部展开或收起。每组可选择可审阅场景；收起、搜索或切换类型不会清除选择，筛选外的已选数量会单独提示。跨叶子的选择仍可一起送审，模板生产仍只使用已确认场景。

1. 选一个叶子类型，填写场景名称、目标用户、用户目标、核心流程及验收条件。验收应描述行为，例如“添加任务后，刷新仍能看到任务”，而不是“有 README”。
2. 保存草案并审阅；确认后才成为可生产目录项。批量生成时，工厂会固定同类型未归档场景的内容与版本作为对照，输出语言随当前中英文界面一起固定。每个叶子最多提出 3 条新增草案，不要求凑满；已有覆盖充分或没有合适的独立场景时，可以返回零条并说明原因，任务仍正常完成。新增草案自动排入独立 Agent 审阅，再由你逐条确认。
3. 选择已确认场景，填写 `provider/model`、并发和单阶段超时，点击“生产认知模板”。它会研究同类产品、生成认知规范/文档/验收代码并自动独立审阅。需要旧的整套源码改造流程时，另选“生产代码模板”，可指定公开 GitHub 仓库。实际模型调用及联网搜索可能计费。
4. 在“任务批次”查看阶段、事件、错误和计划。暂停只暂停新任务领取；取消会停止本批次排队/运行任务，已有制品与证据保留。中断或失败可以从检查点重试。

批次固定当时的类型正文、场景版本、已有场景对照、模型和输出语言。后续编辑场景或切换界面语言不会暗改已启动任务；重试使用原始固定输入。旧任务没有已有场景快照时仍按旧输入执行，不临时补入可变目录。关闭页面后 worker 继续运行；进程中断会显示已中断，显式重试后恢复已完成阶段，不将未知状态显示为成功。

在任务批次可查看新增草案数量，或“未新增场景”的原因。这个结论表示模型在当前叶子与固定对照范围内没有提出新增项，不表示已证明全部应用场景都已覆盖。若有具体遗漏，可先在目录中手动描述，再送独立审阅。语义去重由生成和独立审阅共同辅助，并非确定性保证。

## 场景独立审阅

生成草案和审阅是两个独立 CLI 会话。每个新草案会自动创建一个审阅任务，使用该批次的模型和输出语言；每个场景会额外调用一次模型。零新增时无需创建后续审阅任务。生成成功后草案即已保存，审阅失败可以单独重试，不重新生成草案。生产与审阅使用独立调度槽位，批次暂停和取消同时适用于它们。

场景按钮按情况显示“发起场景审阅”（首次）、“重新审阅场景”（已有报告，包括过期报告）、“重试场景审阅”（当前版本最近一次未完成）；排队和运行时显示“等待审阅 / 审阅中”并禁用。重新审阅或重试会发起新的独立审阅调用，不重新生成场景，也可能计费。已有草案和已确认场景均可审阅，也可以勾选后“审阅所选场景”。归档场景不送审。

**Agent 审阅结论与人工确认是两个状态。** 分组分别显示草案 / 已确认数量和 Agent 审阅汇总；只统计当前有效结论，过期、未完成、未审阅、排队与运行分别显示。通过审阅的草案卡片显示“待人工确认”，不是“未通过”。点击“编辑 / 确认场景”，将场景状态改为“已确认，可以生产”并保存，才可选择它生产模板。审阅不会自动更改这个状态。模型会收到所选场景、固定的叶子正文，以及同类型未归档场景；审阅会话只读这些输入，不做联网搜索或执行程序。

各阶段还会提供独立的 `leaf.md`，内容与固定叶子正文及指纹完全一致。OpenCode 通过它读取全文，避免 JSON 中的长字符串被读取工具按行截断；必要时按行分页到文末。`input.json` 仍保留原始正文和明确的文件路径。

审阅逐项检查类型匹配、场景区分、流程完整性、验收可验证性、范围与一致性，给出“通过 / 需要修改 / 不建议采用”、具体理由、原文引用及修改建议。新审阅提供 `leaf.md` 的起止行号，Atlas 验证范围后直接提取该版本的原文，避免模型抄漏 Markdown 标记。旧协议的逐字引用仍可校验和展示。重叠场景 ID 必须来自当次对照输入；缺项、越界行号、无效引用或 provider 错误显示失败，不记为通过。只有被判定为实质重叠的场景才列入重叠 ID，仅作为对照但已区分的场景不列入；整体与分项矛盾的报告会失败。检查重点是声明的用户目标与可观察行为，不把普通实现选择和可选打磨变成新要求。审阅说明与建议遵循批次的输出语言，技术名、ID 和原文引用保留原样。

报告绑定场景版本、类型正文指纹和对照场景内容。任一输入更新后，旧报告会显示“已过期”，并保留历史。重复检查仅覆盖当次提供的同类型场景，不代表全库去重。模型判断也不等于用户需求、市场价值或实际运行已经验证。

**Agent 只提供建议，不修改场景、不自动确认，也不触发模板生产。** 由你编辑场景并明确确认后，它才进入生产目录；你仍可根据实际需求作出与模型建议不同的决定。

## 代码模板生产与验收

生产无需 Docker。生产完成得到 **L0 冻结候选**：源码、参数说明、运行计划、来源/commit/许可证、哈希清单与模板包；检查过结构及两个项目名称的渲染，但应用尚未运行。

制品页可分别发起：

- **Harness 审阅**：OpenCode 在独立只读会话查看源码，按固定场景条件逐项引用代码并给出通过/阻断/待确认。它不会安装、启动或执行模板。“审阅通过”只表示审阅范围内未发现阻断问题。
- **运行验收**：需要 Docker Desktop。Atlas 在两个新目录创建不同名称的应用，在受限 Linux 容器安装、构建、启动，并按固定计划运行浏览器或 CLI 检查。会保留具体步骤、环境镜像和结果。不支持的运行环境显示不可用。

二者使用独立于生产的任务队列。等待验收、运行失败、没有 Docker，都不会阻止后续目录项生产。至少一种验收通过可成为 L1；审阅记录和运行记录始终分别显示，不能混淆。

错误记录会给出安全诊断。provider 连接重置、输出不合协议或安装环境失败都不能算通过。可在任务批次重试验收。

## 代码模板发布、修复与创建应用

核对来源、场景覆盖和验收范围，填写人工审阅说明，再发布 L1 或 L2。L2 代表你明确复核了模板完整性；L3 尚未开放。发布不强制运行验收，但必须至少有一种独立验收通过。需要撤回时填写说明并下架。

发现实现问题，在制品页填写修复要求并“生产修订版”。工厂基于冻结版本与已有验收记录创建新生产任务，不覆盖原制品；源码修复默认沿用冻结的运行计划，不再调用模型重写检查。只有计划或运行环境本身有误时，才勾选“同时修订运行验收计划”；此时重新生成技术检查，业务场景与验收条件仍固定为原版本。新版完成后另行送验及发布。生产阶段出错则重试原任务，保留旧尝试。

创建应用可在工厂候选页试用，或从对应叶子的已发布模板卡片操作。应用名称使用小写字母开头，只含小写字母、数字和短横线，例如 `my-task-board`。

“创建应用包”只进行确定性参数替换和打包，**不会调用 LLM，也不会在本机自动安装或启动软件**。下载解压后按包内 README 运行。模板源代码中的许可证及署名保留在应用包内。

## 运行配置与数据

2026-10-19 本项目默认使用 `opencode-go/deepseek-v4.1-flash`；工厂页刷新后的初始选择也优先这个 Go 模型。`opencode-go/longcat-2.5-preview-free` 和 `opencode-go/beam-free` 已通过简短合成输入的真实调用，可在模型输入框选择。历史批次与旧书签实验仍保留当时的模型，不因默认值切换而改写。这次检查仅验证调用与 JSON 输出，不代表三种模型都通过完整模板生产；见 [模型切换实测](template-factory/provider-probes/opencode-go-2026-10-19/README.md)。

- 生产后端：本机 `opencode` CLI，可用 `ATLAS_FACTORY_OPENCODE` 指定二进制路径。沿用用户已有 provider 配置，不在 Atlas 页面收集或展示密钥。
- 数据默认在 `application-atlas-production-pack/atlas/template-factory/`，可用 `ATLAS_FACTORY_ROOT` 指向其他目录；数据库、任务尝试、证据、制品和下载文件都在此处。目录不纳入 Git。
- API 与 Vite 启动方式同项目 README；页面地址 `/factory`。更新后需要重新启动 API 以加载新后端代码。
- Docker 内存/CPU 可用 `ATLAS_FACTORY_MEMORY`、`ATLAS_FACTORY_CPUS` 配置。候选命令不会在宿主执行，但容器默认仍可联网，运行验收应在合适的本地环境进行。
- 首版只有 `project_name` 参数、公开 GitHub 来源和单机调度。复杂参数、私有仓库、多主机、自动上游升级与保留期清理没有在首版实现。

不要把“冻结”“审阅通过”“运行通过”“已发布”和“成熟”当成同一个状态。

## 场景生产用量参考

2026-10-17 两批 6 个新叶子的实测中，每叶子产出 3 个场景并完成独立审阅，平均累计约 7.5 万 token 字段加总（生成约 1.6 万、审阅约 6.0 万），区间约 6.4–8.5 万；其中包含缓存读取、推理、多轮上下文和两次审阅重试。该数用于观察工作量，不是统一价格的计费 token。正文长度、既有场景数量和重试次数都会改变用量。

这两批可见联网搜索和网页获取均为零：场景生产读取本地 Atlas 正文，模板的开源项目调研属于后续独立阶段，不能沿用这个搜索或费用估计。完整统计应读取 OpenCode 会话逐消息用量；本版本 CLI 流日志遗漏最后回答回合的 `step_finish`，直接加总流日志会低估。详见[用量实测](TEMPLATE_FACTORY_VALIDATION.md#2026-10-17第四批场景生产与六叶子用量汇总)。

## 认知模板与开发包

改造后的真实使用示例见 [书签 P0 完整闭环](template-factory/end-to-end/bookmark-2026-10-19/README.md)：重新生产认知库、导出阶段执行包、OpenCode 开发、独立浏览器与真实重启验收、定点修复和复验均已完成。该记录提供新认知模板、开发包和最终应用包，候选仍未发布；不要把它与较早的上游代码改造案例或 A/B 试验混为一份证据。

进入“模板工厂 → 模板制品”，点击“载入书签认知样板”。也可展开“导入其他认知包”，选择兼容 atlas.product-blueprint.v0 的 ZIP；ZIP 根目录必须有 template.json、integrity.json 及必需的文档和验收入口。当前上传上限 1 MiB、展开上限 8 MiB，以适配本地 API 的 2 MiB JSON 边界；超出时拆分无关大文件后重打包。

载入后点击“查看认知内容”，阅读产品定义、架构、路线图和决策。能力地图中的“不适用/后期”不会变成当前实现承诺。包内验证说明只是包作者的历史声明，工厂导入校验没有重新运行应用或模型审阅。正文不会自动加载远程图片，来源链接需要主动打开。

填写开发项目名称，选择当前阶段，再点“创建开发包 → 下载开发包”。将包解压到新目录，从外层 HANDOFF.md 开始，阅读 CURRENT_PHASE.json 和 PROJECT_DECISIONS.json，核对已有项目和已确认决定。当前摘要保留当前及必要前期能力、相应正向/负向验收目标、全部决策触发条件与原包限制；未实现的前期能力仍需核实、补齐或回归。实现相关数据、接口、UI 前查原包架构契约，验收前查对应程序和依赖，不必预读所有后期章节与历史报告。在 PROJECT_DECISIONS.json 记录实际选择。未填写的可逆决策按包内已声明默认值推进；需要用户关键取舍时遵从相应触发条件。导出本身不调用模型、不安装依赖，也不生成一个已经完成的应用。

旧模板的阶段范围不因导出而改变。例如自动书签 v0.1.12 的 P0 不包含归类管理和搜索，必须明确该差距；不能把旧 P0 当作完整场景，也不能静默合并阶段或把摘要当成已运行验收。新生产规范及独立预审现在要求首阶段完成已确认场景的必要核心闭环，后续阶段承接成熟度增量；这项语义要求仍需通过实际新产物检查，不能靠提示词保证。

冻结包可以再次导入；相同内容不重复创建制品。原始认知包放在开发包的 blueprint/ 中，其摘要和历史证据保持；项目选择放在外层。已支持自动认知模板生产、独立静态审阅，以及带冻结适配器的下游容器运行验收；认知模板满足当前固定案例证据、结构检查和独立审阅要求后，可在 V1 工厂发布到正式目录；旧包缺少依据时保持 legacy/unverified。发布不等于下游运行通过，原代码模板流程继续可用。

## 完整认知、当前执行与独立验收

开发包现在有三个入口：`KNOWLEDGE.md` 索引完整冻结认知库，`HANDOFF.md` 与 `CURRENT_PHASE.json` 聚焦当前阶段及必要前期回归，`ACCEPTANCE_CONTRACT.json` 固定独立用例和程序摘要。不要把前期依赖视为已完成，或把建议默认值视为用户已经确认；实际选择记录在 `PROJECT_DECISIONS.json`。`HANDOFF_MANIFEST.json` 可核对全部交接入口和原包字节。

开发完成后依 `APP_DELIVERY.md` 打包应用源码，回到制品“独立运行验收”：选择阶段、上传带根目录 `delivery.json` 的源码 ZIP，确认隔离执行，再提交。冻结包须有 `acceptance/runner.json` 声明逐例参数；旧包没有时界面明确说明不可用，需生成经过审阅的新修订版，不能凭经验猜命令。页面的新认知生产任务会要求生成该协议，旧 API 请求可保留原行为。

验收先检查真实启动，再运行当前与前期冻结用例，显示实际断言、错误输出和清理结果。结果固定模板、源码和阶段，与静态认知审阅分开；调用模型成功或程序退出零本身都不是行为通过。验收不调用 provider。运行环境为受限 Docker、执行时无外网，依赖不足显示不可用；不自动开放网络安装或把缺少的浏览器环境冒充 UI 成功。模板的生成模型仍按配置使用 OpenCode CLI。

压缩源码 ZIP 限 1 MiB、展开限 8 MiB，清单需精确匹配实际源文件；允许一次无歧义 app 前缀归一化并记录，不修改源码或冻结验收程序。不要包含真实凭据。模板仍保持原等级及草稿状态，不自动发布或晋级。协议示例、支持 profile、实际检查与限制见[本轮实现记录](template-factory/2026-10-19-factory-refactor/README.md)。

## 自动生产认知模板与修订

1. 在“生产目录”选择已确认场景，核对模型、语言、并发与超时，可在“认知模板补充要求”写入已有决定、必须支持的用户流程或上次预审意见，再点击“生产认知模板（N）”。补充要求也会发送给所选模型。草案不能直接生产，同一场景正在生产时不能重复排队。公开仓库输入只用于旧代码模板，不限定认知模板的研究来源。
2. 在“任务批次”查看研究、规范、**独立规范预审**、验收文件与冻结状态。预审检查场景、用户主流程、架构契约、阶段验收设计及默认决策；有人机界面要求时，API 存在不代替该用户流程；API/CLI 产品按其声明入口判断。有明确阻断时先反馈给规范作者，在任务限定次数内仍有阻断就停止，不生成后续程序。“待确认”保留在记录中，不自动变成停产门槛。打开“详情”可读各轮理由与建议；修订补充要求后，可重新生产同一确认场景。研究可以联网，之后各步只读固定资料且有检查点；预审也可能计费。无阻断后逐文件生成验收/参考代码，依赖清单需通过 JSON 与字段类型检查；通过解析不表示依赖已安装。主文档、指令与摘要由 Atlas 渲染，研究成功后重试复用检查点。

   规范预审的基础五个维度分别调用模型、分别保存检查点，全部返回后再汇总；某一项调用失败不能算通过，重试复用已完成项。每项只提供同一规范的相关字段、完整架构、调研摘要/未知项及本轮补充/修订要求，记录规范与材料投影摘要。阶段验收项还会读取文件计划；基础五项合计覆盖角色、能力、决策、阶段、案例与限制。不提供历史程序、失败候选或旧审阅结论；完整调研事实与程序交给后续冻结包完整审阅。分项调用仍可能计费，实际用量以记录为准，预审不代替程序审阅或运行验收。

   请求运行适配协议的新任务另加第六项“平台运行协议”预审，读取主机提供的运行事实与完整规范/文件计划，检查镜像、直接脚本导入、逐例参数、只读应用源码、测试临时目录、合法交付 profile 和重启证明。测试容器的 `{data_dir}` 是它自己的 `/state`，不是应用容器的数据库目录；仅共享目标网络，不能假定两个目录互通。需要进程重启证据时，必须有启动同一冻结应用的隔离测试实例、真实停止重启及读回契约；换一个 HTTP 客户端不能代替重启。旧五项汇总不能绕过新检查，既有分项与规范仍保留；未请求运行协议的旧任务仍按原五项处理。

   调研原始响应也有独立检查点。若包含保留/重复编号或不合法外部 URL，允许一次无搜索的模型协议修复，只能请求删除主机能独立判定为违规的来源行，再严格校验；不能改写事实或直接宣称调研通过。失败响应、错误与修复均保留，旧规范化调研检查点仍可恢复，避免重复联网。

   复审后的规范修订采用局部改动，读取当前提案与阻断意见：架构用唯一匹配的原文片段替换；角色/能力/决策/阶段/案例用既有 ID 定位字段，并校验原值或整份提案的准确版本摘要。版本锁定后无需模型重复长旧值，不是模糊匹配；错误/缺失版本、未知 ID 或不允许的字段仍拒绝。主机保留其余字段，禁止修改身份、来源元数据、验收状态和文件清单；冲突有限重试，仍不匹配则停止。原始模型改动、修订前后摘要及修改路径保留；改完仍须独立预审，不凭“修改过”放行。
3. 冻结后自动进入独立“认知审阅”会话。审阅读取文档、规范与验收程序，检查品类证据、场景范围、产品完整性、架构契约、阶段验收、决策默认值、Agent 交接与证据诚实性。它不联网、不执行程序、不安装依赖。来源仍是模型调研报告，未独立逐项复取认证。
   审阅的文件依据必须来自冻结 source 清单，不能引用上下文 `leaf.md`。仅当引用了不存在的文件时，允许一次禁联网的模型协议修复：只能删除主机确认无效的引用索引，每维仍须保留有效依据，随后完整严格校验；原摘要、维度、判定、理由和建议不变，原始响应与修复凭据保留。修复失败仍是未完成，不能据此改判通过。
4. 在“模板制品”查看结论、具体文件依据及建议。八项均通过才显示审阅通过；阻断或待确认如实保留，调用/协议错误显示未完成。按钮区分首次审阅、重新审阅和重试；新调用可能计费。认知审阅通过不表示程序运行通过，也不自动发布或晋级。
5. 有问题时填写修订意见，点击“生产认知修订版”。新任务沿用原确认场景与研究，并读取旧版本及审阅意见，产生新的冻结制品及独立审阅，原包保持不变。修订可按原摘要复用未改文件，窄修改需精确唯一匹配；语义版本的补丁号递增。长修订/审阅意见另提供全文文件。修订不自动刷新研究来源。

程序定点修复的高级 API 参数：在原修订请求中加入 `edit_paths`（如 `["acceptance/ui-p1.cjs"]`），主机只允许修改这些冻结程序，其他程序逐字复用，原文件清单不得遗漏或扩张。若产品规范完全不变，再加 `reuse_spec: true`，主机复用规范与研究，跳过模型规划和规范预审；仍为选中程序调用模型、冻结新版本并完整独立审阅，既有规范阻断不会被清除。该选项目前由 API/试产驱动使用，页面修订表单采用原流程。它不代表程序已经执行或验证通过。
