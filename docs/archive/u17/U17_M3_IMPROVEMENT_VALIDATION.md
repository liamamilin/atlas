# U17 M3 目标驱动改进方案验证

日期：2026-09-13
状态：M3-03 完成；正式代码执行与验收进入 M4。
依据：[产品设计](../../U17_DESIGN.md) · [开发规划](../../U17_DEVELOPMENT_PLAN.md) · [M3 基线验证](U17_M3_BASELINE_VALIDATION.md)

## 1. 用户流程

已有项目和 U17 新建项目现在使用同一个改进流程：

1. 用户通过现有搜索与资料阅读界面收集至少一份类型、研究或应用资料，并写明借鉴范围。
2. 用户建立工作区基线，指定本轮需要读取的代码或测试路径。
3. 在项目页填写“本轮局部改进目标”，请求生成项目改进方案。
4. 系统用已接受基线、基线中的已读文件、固定 Atlas 资料、项目目标、已有需求/决定和文档版本形成不可变输入，再调用 OpenCode。
5. 结果先显示为问题、候选需求、冲突、建议和 `current-state` 文档草案。候选需求仍需用户逐条确认；文档只在用户点击后创建或保存为新版本。

搜索和固定资料仍由用户控制。本轮没有让模型在生成过程中自由浏览或自动扩张资料范围；这样可以定位每项建议使用的正式资料版本。后续可以增加“围绕目标推荐检索词和候选类型”，但采用哪些资料仍需显式记录。

## 2. 固定输入

`improvement` 生成模式新增独立的 `improvement_goal`，不会把项目最初目标误当成本轮修改指令。输入包含最新已接受工作区基线：

- 基线 ID、记录指纹和工作区内容指纹。
- Git 分支、HEAD、dirty 状态和读取错误，不向执行器提供真实工作区根路径。
- 文件数量、重点路径、完整/部分读取范围和四类观察结果。
- 每个已读文件的相对路径、SHA-256、大小、完整性和受限正文。
- 已固定 Atlas 资料、需求、决定及现有文档版本。

准备运行和真正启动执行时都会重新扫描工作区。当前工作区内容指纹与基线不一致时拒绝生成；这样生成器不能在用户尚未检查外部变化时使用过期代码现状。

参考摘录和工作区文件被明确标记为不可信项目证据，其中的文字不能改变生成任务、权限或输出契约。OpenCode 继续在隔离目录运行，禁止 Bash、网络、外部目录和子任务。

## 3. 改进方案契约

改进模式只生成一份 `current-state` 文档，并要求按顺序包含八个双语标题：

1. `Current behavior / 当前行为`
2. `Expected behavior / 期望行为`
3. `Adoption rationale / 采用理由`
4. `Impact scope / 影响范围`
5. `Compatibility requirements / 兼容要求`
6. `Tasks and dependencies / 任务与依赖`
7. `Regression conditions / 回归条件`
8. `Unknowns and required validation / 未知与待验证`

服务端校验文档类型、章节完整性与顺序、至少一个已读工作区路径、基线依据和 Atlas 资料依据。模型不能把 README 声明或代码阅读写成运行验证；没有实际运行的测试和交互必须留在未知/待验证部分。

候选需求仍使用固定 Atlas 资料作为产品建议依据；当前代码事实、影响文件和回归条件集中保存在绑定基线的 `current-state` 文档。该边界避免把分类资料直接转换成项目 backlog，也避免把一次代码观察写回为用户最初产品意图。

## 4. 版本与外部变化

`workspace_baseline` 已成为文档的一等依据。保存文档时记录基线 ID、记录指纹和时间；采用更新基线后，引用旧基线的文档自动进入 `needs_review`，原因包含新基线 ID。

生成结果采用前再次核对：

- 运行输入绑定的基线仍是最新已接受基线。
- 工作区内容仍与该基线一致。
- 若更新已有同类文档，其当前版本仍等于生成输入中的版本。

任何一项变化都会拒绝采用，用户需要重新检查或重新生成；旧文档正文不会自动覆盖。项目导出 manifest 升为 schema 2，导出包现在包含最新 `workspace-baseline.md` 和完整 `workspace-baseline.json`，改进文档离开 Atlas 后仍能定位它所依据的文件证据。

## 5. 自动验证

`python3 -m unittest application-atlas-production-pack/tests/test_reliability.py`：71 项通过。新增覆盖：

- 改进目标、工作区证据和 Atlas 资料进入同一不可变输入。
- 真实路径不进入生成输入，已读相对路径与正文完整保留。
- 八个章节、工作区路径、基线依据和资料依据的严格结果校验。
- 候选需求采用后仍为未确认，文档保存后保留基线依据。
- 生成准备后发生外部修改时，runner 不会启动且运行状态为 failed。
- 采用新基线后，旧 `current-state` 文档自动待复核。
- 项目 ZIP 同时导出可阅读基线和完整证据清单。

`npm run typecheck` 与 `npm run build` 均通过。生产构建仍只有现有的主包体积提示。

## 6. 真实 OpenCode 与浏览器验收

隔离案例使用三个真实文件：

- `README.md`：只声称支持内存过滤。
- `src/views.py`：只有一个 key/value 等值过滤函数。
- `tests/test_views.py`：只有未覆盖行为的 placeholder 测试。

项目固定了 Application Atlas 中 `structured-table-lightweight-database-application` 的 `interfaces` 正式章节，并限定只借鉴 view configuration。第一次真实 OpenCode 运行在约一分钟内完成，返回：

- 5 个影响范围的关键问题。
- 5 个候选需求，其中跨运行持久化因证据不足建议放到以后。
- 一份通过全部结构和依据校验的 `current-state` 文档。

文档引用基线、正式资料和 `README.md`、`src/views.py`、`tests/test_views.py`；明确指出没有执行测试，并把存储方式、调用入口、命名冲突和未知名称行为保留为未知。

随后在真实项目页面填写第二个改进目标并启动 OpenCode，运行 `gen_276759e268f3483892cc1fb8cd5cc69b` 完成且记录引擎会话。页面显示 6 个问题、8 个候选需求、3 个明确冲突、6 个建议，以及针对已有 `current-state` 文档的新版本草案。点击采用后：

- 文档由 v1 变为 v2，没有覆盖旧版本。
- 点击加入一条候选需求后，项目统计更新为 1，状态仍是“待决定”。
- 外部修改 `src/views.py` 后，变化检查只报告该重点文件。
- 采用新基线后，v2 文档立即显示“需要复核”，提示工作区基线变化且正文未自动改写。

API 日志确认生成启动、轮询、两次逐条采用、变化检查、基线采用和项目重新读取都返回预期状态。隔离服务、数据库和工作区随后已清理。

## 7. M4 接口边界

M3 的任务列表仍是文档内容，还不是可执行任务记录。M4 需要在用户确认范围与关键问题后，把任务拆成结构化记录，绑定确认需求、文档版本、工作区基线和独立工作目录，再交给 OpenCode 执行。代码执行的测试结果必须作为新的运行证据写回，而不能因生成方案成功就视为验收通过。
