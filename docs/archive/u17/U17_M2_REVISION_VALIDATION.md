## 1. 用户流程

每份关联文档的版本区域现在同时保留两种修改方式：

1. 用户可以继续编辑完整 Markdown，并填写修改说明后直接保存人工版本。
2. 用户也可以从当前正文中选择一个唯一 Markdown 标题，用自然语言描述修改要求。
3. OpenCode 返回完整文档候选，Atlas 展示当前版到候选版的统一 diff 和候选全文。
4. 用户审阅后显式保存，候选才成为新的 AI 作者版本。未采用候选不进入项目知识。

没有 Markdown 标题的文档会提示先用完整编辑建立章节结构。重复的同名标题不会作为可选目标；后端也要求标题在当前版本中恰好出现一次，避免修改错段。

## 2. 固定边界与校验

`revision` 运行把以下内容写入 schema 2 固定输入和 Atlas 运行记录：目标 `document_id`、当前 `version_id` 与版本号、正文 SHA-256、文档类型和标题、所选完整标题行、用户修改指令。

模型只能修改所选标题下的正文，直到下一个同级或更高级标题为止。Atlas 不依赖提示服从来保证边界，而是在接受结果前校验：

- 结果只能包含固定目标的一份完整文档，文档 ID、类型和标题必须一致；
- 所选标题行及其之前的每个字节必须与当前版相同；
- 章节结束后的每个字节必须与当前版相同；
- 候选必须产生实际变化；
- 新版本沿用目标当前版的固定依据，模型不能替换、删除或伪造依据；
- 应用继续使用运行开始时的 `current_version` 做乐观并发检查，期间出现人工新版本会返回冲突；
- 保存上游文档新版本后，现有依据传播规则会把相关下游文档标为需要复核，不自动重写正文。

用户指令是修改意图，不是外部事实依据。若修改会改变产品范围，用户仍应先修订并重新确认需求，再处理受影响文档。

## 5. 当前边界

- 一次运行只修改一个唯一章节；跨章节调整应拆成连续候选，或使用完整人工编辑。
- Atlas 保证修改范围、依据和版本边界，仍需要用户判断改写内容是否正确。
- 关键问题尚未形成回答后自动重跑流程。
- 价值分析仍未产品化；它只应提供信息和建议，不能自动否决项目。
