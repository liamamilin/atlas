# 三领域自动发现：实际验收与扩量决定

日期：2026-10-23。结论：**技术链路已跑通，质量暂不通过扩量门槛。** 保留三个验证叶子与实际结果，不把缺口补成虚构项目，也不把本轮人工复核当作已具备全库无人值守能力。

## 范围与方法

选择已有分类中的阅读器（02.08）、图表应用（03.05）、密码管理器（15.02）。没有新建分类。原个人知识管理应用的 3 场景、7 项目、12 关联保持原样；旧模板工厂仍从历史入口访问。

这三个叶子的发现流程没有读取 `pilot.json` 或事先写入仓库名单：

1. 从既有分类的定义、用户任务与相邻类型边界生成场景；移除代表产品与来源列表，避免把例子当作发现答案。
2. 以类别名、模型给出的类别同义词、场景任务词执行真实 GitHub 搜索，记录完整查询、时间、结果 ID 与元数据。
3. 模型仅能从搜索结果的 numeric ID 中初筛，最多 6 个候选；排除库、SDK、教程、产品清单和相邻分类工具。
4. 读取 README 与许可证。每条定位、介绍、范围、功能、关联必须带连续原文，引文须存在于本次输入的 README 中。不存在则不入库。
5. 另行核对许可证全文、SPDX 官方模板和 README 许可声明。再逐卡片阅读相关性与陈述支持程度，记录剔除和收窄。
6. 复跑时重新搜索，未变化的资料与模型输入命中缓存，按仓库 ID 更新原记录，保留跨叶子关联与收藏。

分类文本已与公开仓库逐份对照，见 [公开输入核对](PUBLIC_PAYLOAD_CHECK.json)。使用既有 Open Design 配置；配置模型名为 `deepseek-v4.1-flash`，提供方实际回执为 `deepseek-flash`。最终候选首轮共 14 次真实模型调用，**不包含之前失败与改进轮次**。各次真实用量、缓存标记、失败与搜索证据均保留，未估算费用。

## 相关性与真实性复核

[逐卡片复核记录](review/QUALITY_REVIEW.json) 保存了保留项、被撤下项与原因；[来源完整性检查](SOURCE_INTEGRITY.json) 对最终 8 项的 66 条引文逐一验证连续存在、来源摘要一致，并确认复用资料保留实际采集时间。

- **撤下 Quick RSS**：仓库主要是产品说明、订阅源与文档，未找到应用源码及许可证，不能因公开仓库和主题标签就作为开源应用发布。
- **撤下 Bitwarden Android 本轮卡片**：自动填充与认证的依据来自依赖库用途列表，不能用“依赖某库”证明完整产品功能。项目本身是真实应用，但本轮提取依据不足；未靠记忆补写。
- **删除 Liferea 的学术期刊关联**：所附引文只支持泛化订阅源浏览，未说明期刊目录、摘要或原文任务。保留场景，项目数诚实显示为 0。
- **收窄 KeePassDX 范围**：移除所附引文不能支持的扩展名和格式版本号，只保留单文件 KeePass 数据管理。
- **拦截 RSSGuard 卡片**：至少一条引文不在实际输入中；没有发布，也没有覆盖旧事实。本轮及复跑都保留这项提取失败，不把它计入已完成项目。
- **修正 draw.io 许可分类**：LICENSE 单文件匹配会漏掉 README 的资源限制。现已增加许可声明检查，标准许可证正文前置、后置或版权行附加限制也不能被规范化忽略。

`discovery-reviews.json` 是采集后的摘要绑定复核记录，只能剔除、收窄或修正许可范围，不提供搜索候选。复跑仍会执行真实搜索和提取；被剔除来源变化后需要重审，不能自动恢复发布。

**本轮验收时的决定：暂不扩大叶子覆盖。** 图表初筛仍有漏选且依据不足；密码生成任务在本轮资料中没有可证关联。下一步应保留更多候选并分批读取，在 README 过薄时补读有限的官方功能文档。不能用人工补项目名单宣称自动发现质量通过。

**后续用户口径（2026-10-23）：场景重复可以接受，先生成并保留，不以重复为阻塞，也不要求先完成场景归并。** 自动发现的后续重点是减少过早截断/漏选、补足项目事实依据。通用功能对具体场景的合理适用推断，应与直接功能证据区分并说明条件；不能一概要求 README 逐字写出场景名称。原始验收统计保持原样，不把这一口径调整当作已经补采或扩大覆盖。
