# U17 执行后端演进决策

日期：2026-09-22  
状态：已决定，作为当前发布范围的架构基线

## 决策

当前继续通过适配层复用 OpenCode 作为首个执行后端，不建设通用的自研 coding agent harness。Atlas 自己持有项目资料、需求、文档版本、工作区基线、任务编排、权限硬门、隔离副本、验证命令、证据包、结果应用和产品验收状态；OpenCode 只负责在 Atlas 已固定的边界内提供模型与工具执行。

这不是永久绑定。适配层必须保持 OpenCode 的命令、事件、退出码、provider 检查和凭证读取细节在 Atlas 之外；未来如出现明确的行为控制、部署、恢复或成本问题，可以替换单个执行 transport，不能直接扩大成全面重写。

## 证据

- 核心主线已完成从类型叶子、项目、基线、文档、迭代、执行、应用到独立验收的连续路径。
- 简单新想法和已有项目改进案例均已完成当前范围的真实执行、应用、回归和验收；失败、过期基线、外部变化和证据边界均有记录。
- 多类型需求案例已完成来源固定、范围确认、四份契约文档应用和 T1–T5 验收。T5 明确以只读端到端分析为边界，没有把不存在的 provider 集成写成完成项。
- Agent Harness 产品使用案例已完成六份有来源文档、27 项决定、M0 CLI/provider/连通性预检、`.atlas/harness.json` 兼容基线、M1 CLI 适配器、权限门、固定验证、证据保存、显式清理和只读 TUI 路径；变更任务的停止与应用仍单独验收。
- 当前自动化回归为后端 130 项通过，前端 typecheck/build 通过，API 健康检查通过，核心浏览器路径通过。

## 为什么现在不自研通用 Harness

现有证据证明 Atlas 的主要差异化在“研究资料到开发范围的可追溯编排”和“执行前后的安全状态控制”，而不是重新实现模型路由、工具循环或 provider 凭证系统。当前没有足够的成本、吞吐或跨 provider 失败样本，不能据此证明自研循环会改善产品结果。

自研会立即扩大凭证管理、模型路由、工具协议、会话恢复、权限策略、跨平台分发和长期维护范围，反而会稀释已经完成的产品主线。

## 继续复用的约束

1. OpenCode 版本和安装来源写入项目兼容基线；不承诺浮动的 latest。
2. Atlas 只通过受控 CLI 适配层传递 argv、stdin、stdout/stderr、退出码和稳定事件，不依赖未声明的内部 API。
3. 凭证继续由 OpenCode 读取；Atlas 不接收、不持久化 provider 凭证和原始敏感输出。
4. 每次执行仍需经过 preflight、隔离副本、允许范围、危险操作硬门、固定验证和独立产品验收。
5. 适配层错误必须能归一化为可恢复状态，并保留原始证据引用；会话不可用时依靠 Atlas 交接包继续，不自动重放副作用。

## 触发重新评估的条件

只有出现以下可重复证据，才重新比较继续复用、局部替换或局部自研：

- 同一类任务持续被 OpenCode 的行为控制或事件协议阻塞，且适配层无法安全收口。
- provider 或部署限制导致当前目标环境无法稳定运行，并且替换 transport 能明确解决。
- 在相同输入和验收条件下，重试率、恢复失败率或总成本持续高于已记录基线。
- 多个真实案例反复需要同一套 Atlas 之外的控制循环，并且其范围、维护成本和独立验收方式可以被清楚限定。

在重新评估前，先新增针对性案例和指标记录；不因为单次 provider 失败或一次模型输出不理想而启动全面重写。
