# U17 最佳实践案例

这份案例库把真实试点提炼成可复用的操作方式。案例状态必须和证据一致：已验证的案例可以作为操作参考，待验证案例只能作为试点模板，不能当作产品效果结论。

## 案例一：本地优先的个人日计划器

**状态：已验证。** 完整记录见 `docs/u17-pilots/simple-new-idea/`。

### 适用场景

你有一个还不完整的新想法，希望先查清相邻软件类型，再把范围压到一个可以真实开发和验收的纵向切片。

### 推荐做法

1. 从类型叶子页开始，固定一条主要类型资料，再补充少量相邻类型或应用资料。
2. 把“跨项目形成当天承诺”和“本地重启后保持关系”确定为首轮范围。
3. 明确排除外部日历、自动排程、账号、云同步和团队协作，避免首轮被平台能力拖宽。
4. 只确认一条可验收的最小需求集合，生成核心文档并逐份批准。
5. 用一个小任务完成执行、应用和独立验收，再把第二轮的时间块与冲突提示作为后续修改。
6. 对每轮保留普通生成、Atlas 输入、固定资料、文档版本、执行证据和验收结果，不能只保留最终成功状态。

### 这个案例验证了什么

- 类型资料可以作为项目的第一条固定依据。
- “AI 建议 → 用户确认 → 冻结文档 → 执行 → 独立验收”的边界能够连续工作。
- 第一轮实现状态可以成为第二轮的真实输入。
- 失败执行、测试环境限制、恢复和备份安全问题都应进入记录，而不是被成功结果覆盖。

### 不要直接照搬

案例中的 Python、SQLite、页面结构和任务数量只是当时的实现选择。新项目必须重新搜索、固定资料并确认范围，不能把样例文档当成当前项目事实。

## 案例二：已有项目的局部改进

**状态：已验证并封存。** 已选定一个可独立复验的本地清单 CLI；普通方案、Atlas 当前状态分析、差异判断、首轮实现、Atlas 迭代和独立验收均已封存，案例工作区 10 项测试通过。协议与证据见 `docs/u17-pilots/existing-project/`。

### 适用场景

项目已经有代码、文档和回归命令，但你只想改一个可观察行为，不希望 agent 顺手重写无关部分。

### 推荐做法

1. 先建立工作区基线，分别记录文档描述、代码线索、实际运行结果和未检查范围。
2. 固定一个用户可观察的改进目标，同时写明允许写入路径和旧行为回归命令。
3. 先做普通方案对照，再让 Atlas 生成当前行为、期望行为、影响范围和任务依赖。
4. 在隔离副本执行；应用前如果外部目录发生变化，先检查并重新采用基线，禁止静默覆盖。
5. 应用后运行旧行为回归和本次验收，确认“改进生效”与“原有行为未被破坏”是两件事。

### 进入正式案例前必须固定

- 真实项目目录和当前 Git/文件状态。
- 本轮改进不包含的模块。
- 允许写入的文件路径。
- 旧行为回归命令与新增验收命令。
- 普通生成与 Atlas 生成使用的相同目标、模型和事实材料。

## 案例三：多类型需求的交接设计

**状态：已完成当前范围并封存。** 三份来源已固定，普通方案与 Atlas 分析已完成，六项范围确认已写入项目，四份契约文档已应用；T1–T4 已通过契约验收，T5 已通过只读端到端分析验收。真实供应商或模拟适配器不属于本案例当前范围，若要实现需另立迭代。

### 适用场景

一个需求同时涉及项目管理、个人排程、客户反馈等不同类型，容易出现“每个模块都能做，但没有人知道谁拥有主记录”的问题。

### 推荐做法

- 先声明项目、任务、排程、交付物和客户决定各自的主记录归属。
- 为跨模块传递定义稳定标识、状态变化、复制/引用方式和失败恢复路径。
- 把正式类型资料、当前项目假设和仍待决定的信息分开写。
- 首轮只验证一条跨模块交接，不同时引入同步、权限和自动排程平台。
- 导出交接包后，用不依赖原会话的新执行环境核对是否仍能理解下一项任务。

## 案例四：Agent Harness 产品调研与开发文档生成

**状态：已完成真实运行、文档批准、冲突处理、独立界面复核、只读纵向切片和一个受控单文件变更验收。** 这是一个真正的 Atlas 产品使用案例：软件主题是 Agent Harness，工作过程是通过 Atlas 搜索、阅读、分析并生成一套可开发文档；M0 CLI/provider/连通性预检、兼容基线、M1 CLI 适配器、权限门、固定验证、证据保存、清理、只读 TUI 路径以及单文件变更的显式应用和独立验收均已通过。它不等于完整 Harness 已经实现。

### 适用场景

你想设计一个 Agent Harness，但还不清楚现有类型、产品形态、技术边界、权限模型和执行方式。先用 Atlas 把研究资料和开发范围固定下来，再决定是否值得实现。本次运行已验证：从 `AI Coding Agent` 类型固定资料，到 27 项范围与实现决定，再到调研、需求、交互、技术、开发和验收六份文档，可以形成可追溯的文档包；后续路线问题单独保留，不在案例阶段建立代码迭代。

### 推荐做法

1. 从相关类型和应用开始搜索，区分 coding agent、执行编排、工具调用、沙箱、权限控制和交接系统等相邻主题。
2. 阅读正式类型正文、应用文档和产品资料，保存来源版本、章节定位、读取深度和未覆盖范围。
3. 在 Atlas 中记录当前项目假设、资料事实、推断、未知和仍需决定的问题，避免把市场描述直接变成需求。
4. 生成并审阅产品需求、用户流程、技术方案、开发计划和验收计划；每份文档都保留可定位依据。
5. 把“短期集成 OpenCode、长期是否抽象独立 Harness”记录为架构决策输入：短期先复用 OpenCode，长期是否抽象由后续案例证据决定，不提前承诺自研。
6. 固定一个最小可验证纵向切片，例如受限文件范围、权限请求、验证命令和交接包，不一开始建设完整平台。
7. 导出文档包，重新加载项目核对目标、范围、依赖、风险和下一项开发任务；新一轮文档生成后再次导出，避免下载包停留在旧版本。

### 这个案例验证了什么

- Atlas 能否把一个模糊的 agent harness 想法转成有来源、有边界、可开发的产品文档。
- 研究资料、产品判断、技术假设和用户决策是否保持分层。
- 文档之间是否能形成需求 → 任务 → 验收的可追溯关系。
- Atlas 是否能在不替用户做最终架构裁决的情况下，提供集成与自研的证据。
- 默认实现决定能否沿着分析 → 需求 → 交互 → 技术 → 开发 → 验收六份文档保持一致。
- 27 项决定和全部既有冲突能否在当前项目状态中被复核；文档版本为分析 v7、产品/技术/开发/验收 v6、交互 v5。完整生成曾遇到 OpenCode `result.json` 运行失败，拆分后成功完成。

### 当前边界

27 项决定和六份当前文档已经固定首版默认实现，界面确认全部固定依据为当前版本。Atlas 已建立并完成《Agent Harness 首版纵向切片》迭代；M0 已确认 Homebrew OpenCode 1.18.31、默认 provider 配置和最小连通性，M1 已通过 preflight、CLI 执行、权限门、固定验证、证据、清理、只读 TUI 复验，以及一个单文件变更任务的显式应用和独立验收。最新分析保留 5 个后续产品路线问题：并行任务、take-over、任务历史、TUI 配置编辑、多入口路线。停止、取消/超时、失败恢复和回滚仍需另建任务验收。

### 明确不做

- 不把 Atlas 调研案例误称为 Harness 已经实现。
- 不因为发现了某个现有工具就自动确定技术路线。
- 不跳过来源阅读、范围确认和验收设计直接生成代码。

## 案例五：高风险数据恢复与版本迁移

**状态：规划模板。** 这是一个 Atlas 产品使用案例，重点验证涉及覆盖、迁移和回滚的工作是否可以预览、确认、追溯和安全验收。

### 适用场景

已有项目需要升级数据格式、恢复损坏数据或合并两个版本。操作一旦出错，可能造成不可逆的数据丢失，因此不能直接让 agent 在源工作区试错。

### 推荐做法

1. 先建立只读基线，记录数据格式、数量、校验结果、版本和未检查范围。
2. 明确本次迁移或恢复的目标、允许处理的文件、禁止触碰的目录和保留期限。
3. 在隔离副本生成迁移预览，列出新增、删除、转换、冲突和无法解析的记录。
4. 先生成安全快照或备份，再由用户确认预览结果；未经确认不得写回源工作区。
5. 在副本执行迁移，运行旧格式读取、新格式读取、数据完整性和回滚验证。
6. 应用前检查外部变化；发现基线过期或文件冲突时停止覆盖，重新建立基线。
7. 独立验收恢复后的用户可观察行为，并导出迁移前后版本、备份位置、差异和回滚方式。

### 这个案例验证什么

- Atlas 能否让高风险操作先预览、再确认、后应用。
- 备份、版本、冲突、回滚和验收证据是否彼此可追溯。
- 失败或中断后，用户能否安全恢复而不重复副作用。

### 明确不做

- 不把备份存在当成迁移成功；必须验证数据和用户行为。
- 不在没有恢复路径时扩大迁移范围。
- 不用最终成功结果覆盖原始失败、冲突和回滚证据。

## 案例六：中断与会话不可用后的继续开发

**状态：规划模板。** 这是一个 Atlas 产品使用案例，重点验证执行中断、浏览器关闭、旧会话不可用或 agent 无法继续时，项目能否依靠交接材料安全恢复。

### 适用场景

一个开发任务已经产生部分文件变化或验证结果，但原执行会话无法继续。下一位执行者需要知道已经完成什么、哪些副作用已经发生、下一步应该做什么，以及哪些操作绝不能重复。

### 推荐做法

1. 中断前保存任务输入版本、工作区基线、允许写入范围、已执行命令和输出摘要。
2. 明确区分 agent 报告、文件差异、命令证据、应用状态和产品验收状态。
3. 生成交接包，写明已完成、未完成、待确认、失败原因和下一步动作。
4. 新会话先读取交接包和当前工作区，核对基线与外部变化，不直接重放旧命令。
5. 对可能产生副作用的步骤设置确认点，确认后再继续执行或回滚。
6. 继续执行后重新记录命令、差异、应用和独立验收，不覆盖原始中断记录。

### 这个案例验证什么

- 新会话能否只凭交接包理解项目目标、当前状态和下一项任务。
- 恢复流程能否避免重复写入、重复迁移或重复发布。
- 中断、恢复和最终验收是否保持可追溯且互不冒充。

### 明确不做

- 不把旧 agent 会话当作唯一状态来源。
- 不因为任务看似未完成就自动重放全部命令。
- 不用恢复成功覆盖中断时的原始证据。

## 共同验收标准

已进入正式试点的案例都必须满足：

- 固定输入、来源版本、普通生成和 Atlas 原始记录可独立复核。
- 用户确认范围与 AI 建议分开保存。
- 执行报告、文件/命令证据、结果应用和产品验收分开判断。
- 失败、过期基线、外部变化和未观察项被明确记录。
- 案例结论只来自实际证据，不用文档数量、模型自述或开发者估计替代用户结果。

## 候选案例池

下面是用于扩展案例库的候选，不代表已经验证为最佳实践。选择标准是：每个案例都要暴露一种不同的产品或执行难题，并且能产出可复用的教程方法。

| 优先级 | 案例方向 | 主要问题 | 建议覆盖的能力 |
|---|---|---|---|
| P0 | 已有项目的真实 Bug 修复或局部重构 | 如何理解现状、限制写入范围并保持旧行为 | 基线、回归、外部变化冲突、局部应用 |
| P1 | 多类型的客户项目交付与个人排程 | 多个类型之间谁拥有主记录、如何传递状态 | 数据归属、流程交接、取舍和失败恢复；当前范围已完成，真实 provider/模拟适配器另立范围 |
| P1 | 高风险数据恢复或版本迁移 | 如何让覆盖、迁移和回滚可预览、可确认、可追溯 | 安全快照、版本兼容、冲突和独立验收 |
| P2 | 中断与会话不可用后的继续开发 | 执行被停止、重启或旧会话消失后如何交接 | 任务交接包、恢复核对、避免重复副作用 |
| P2 | 纯资料到文档的研究型案例 | 没有代码改动时，如何区分事实、未知、推断和建议 | 资料定位、价值分析、文档导出和决策记录；Agent Harness 案例已完成此方向的当前范围验证 |
| P2 | Agent Harness 架构评估 | 当多个案例暴露相同控制缺口时，是否需要抽象执行控制面 | 仅作为架构决策输入，不作为产品使用案例 |

推荐先完成 P0 和第一个 P1，再决定是否扩展 P2。案例总数不以“越多越好”为目标；当新增案例不再覆盖新的风险或工作方式时，应停止扩展，转而整理教程和验收矩阵。
