# U17 项目工作台设计检查

日期：2026-09-16
状态：第一批至第四批已修复并回归
范围：项目详情页的信息架构、状态语义、操作闭环，以及页面与后端生命周期约束的一致性
依据：[U17 产品设计](U17_DESIGN.md) · [U17 开发规划](U17_DEVELOPMENT_PLAN.md) · `atlas-web/src/routes/project-detail.tsx` · 项目与执行后端实现

## 1. 结论

项目工作台的领域对象划分是合理的：资料、AI 建议、用户确认、文档版本、工作区基线、执行、应用和产品验收彼此独立，没有把 agent 自述直接当成验收结果。

当前主要问题不在视觉样式，而在页面逻辑：

1. 页面把本应有独立状态和处理动作的对象压成了一条九步布尔进度。
2. 多个面板展示同一概念时使用不同的数据来源，数字和文案可能互相矛盾。
3. “需要用户处理”的问题、冲突和建议没有处理闭环，用户看得到但无法在原处完成任务。
4. 部分成功状态比后端事实更乐观，例如“当前文档”不代表人工审阅通过，“已应用”不保证新基线采用成功。
5. 页面强调可追溯，但需求、基线、执行尝试和验收证据的版本或历史展示仍不完整。

因此不建议只给“需要用户回答”增加一个文本框。应先统一工作台状态模型，再围绕“待处理事项 → 决策 → 冻结输入 → 执行 → 验收”重组页面。

## 2. 当前页面实际逻辑

当前页面从上到下依次呈现：

> 项目路径 → 工作区基线 → 资料分析与文档草案 → 一致性信号 → 范围与验收 → 已记录决定 → 文档与版本 → 迭代与执行

这与用户实际完成工作的依赖顺序并不一致。用户生成文档时才发现必须先确认下方的需求；看到 AI 问题时，下方没有与问题直接关联的回答入口；执行和验收阶段又要回到前面的需求、文档和基线判断当前任务依据。

`LifecycleOverview` 在前端从多个对象推导九个布尔值，而不是读取一个明确的工作流状态：

- 有任意一条 `confirmed_scope=current` 的需求就视为“需求已确认”，其他待决定需求不影响该步骤。
- 有任意一份依赖未过期的文档就视为“文档已形成”，不区分 AI 刚保存的草案和人工审阅通过的文档。
- 没有活动迭代时使用最新历史迭代继续推导执行、应用和验收进度。
- 分析任务不论执行结果如何都被视为无需应用。

这组逻辑适合做粗略提示，不适合作为用户判断项目真实状态的权威入口。

## 4. 问题清单

### P0-1：项目切换期间可能显示旧项目数据并向新项目发送操作

`useAsync` 在依赖变化时保留旧 `data`，`ProjectDetail` 只在没有数据时显示加载态；基线、生成运行和 `analysisRun` 等局部状态也不会在项目 ID 变化时同步清空。

证据：

- `atlas-web/src/components/loaders.tsx:10-16`
- `atlas-web/src/routes/project-detail.tsx:79-99`
- `atlas-web/src/routes/project-detail.tsx:421-434`
- `atlas-web/src/routes/project-detail.tsx:544-558`

影响：路由从项目 A 切到项目 B 时，页面可短暂展示 A 的需求、文档、基线或生成结果，但操作函数已使用 B 的 `projectId`。即使多数操作会被服务端归属检查拒绝，这仍会产生错误目标、误导性按钮和不可解释的失败。

建议：项目工作台子树按 `projectId` 设置 `key`，或在项目变化时同步清空所有项目级状态；只有当 `data.project.id === projectId` 时才开放操作。

### P0-2：“需要用户回答”没有回答、忽略或已解决状态

生成结果中的问题只通过 `ProposalList` 展示标题和原因。`GeneratedQuestion` 只有 `question`、`why` 和 `affects`，没有稳定 ID、答案、处理状态或关联决定。后端只允许应用 requirement 和 document，不允许处理 question、conflict 或 suggestion。

证据：

- `atlas-web/src/routes/project-detail.tsx:649-653`
- `atlas-web/src/routes/project-detail.tsx:675-677`
- `atlas-web/src/lib/atlas.ts:541-545`
- `application-atlas-production-pack/project_generation.py:531-555`
- `application-atlas-production-pack/project_generation.py:626-640`

影响：页面要求用户回答，但用户在原处无法回答；使用“记录决定”变通后，系统也不知道该决定回答了哪个问题，无法标记完成或更新计数。

建议：为生成问题增加稳定 `key` 和处理记录，支持“回答并保存为决定”“暂缓”“不适用”。答案应关联来源运行、问题、受影响文档和生成出的决定。

### P0-3：一致性信号不是当前画面的真实汇总

页面只把最近完成的 analysis 或 improvement 运行保存为 `analysisRun`，然后用它计算问题、冲突和建议；用户当前选中的运行以及 value 运行均不参与计算。

证据：

- `atlas-web/src/routes/project-detail.tsx:544-558`
- `atlas-web/src/routes/project-detail.tsx:679-710`

影响：上方生成面板与下方一致性信号可显示不同对象却使用相同名称；计数不能解释、不能逐项清零，也不能作为项目状态入口。

建议：一致性面板改为持久化的“待处理事项”汇总，只统计未处理且仍基于当前输入的项目；显示来源运行和类别，不再依赖某一个前端选中的最新运行对象。

### P0-4：“当前文档”混淆依赖新鲜度与人工批准

文档 `review.status=current` 只表示所依赖的数据未变化。AI 文档一保存即可成为 `current`，并可用于创建迭代；没有独立的 `pending/approved/rejected` 人工审阅状态。

证据：

- `application-atlas-production-pack/project_store.py:1123-1167`
- `application-atlas-production-pack/project_generation.py:592-599`
- `application-atlas-production-pack/execution_service.py:52-60`
- `atlas-web/src/routes/project-detail.tsx:280-303`

影响：页面文案中的“当前”“已复核”“可进入迭代”实际可能只表示技术上的依赖未过期，用户容易把 AI 草案误认为已批准方案。

建议：拆分 `freshness=current|stale` 与 `review_status=pending|approved|rejected`；迭代只能固定人工批准且依赖仍新鲜的版本。

### P0-5：“已应用”可能掩盖新基线采用失败

文件写回成功后，后端即把 `application_status` 设为 `applied`；如果随后采用新基线失败，只写入 `baseline_adoption_error`。页面显示绿色已应用、开放验收，却不展示这个错误。

证据：

- `application-atlas-production-pack/execution_service.py:400-450`
- `application-atlas-production-pack/project_store.py:606-613`
- `atlas-web/src/routes/project-detail.tsx:355-388`

影响：用户可能完成验收和迭代，但 Atlas 接受的工作区基线仍旧，下一次执行才发现不一致。

建议：拆成“文件已写回”和“基线已采用”两个状态；没有 `accepted_baseline_id` 时不得视为应用步骤完成，也不得通过普通验收。提供仅重试基线采用的恢复动作。

### P0-6：验收与执行事实没有可靠绑定

后端验收不要求存在成功执行，也不要求验证命令或结构化完成报告有效；分析任务失败或停止后，页面仍可开放 Pass/Waive。迭代完成主要检查验收标签。

证据：

- `application-atlas-production-pack/project_store.py:570-618`
- `atlas-web/src/routes/project-detail.tsx:386-388`

影响：失败、停止甚至未执行的任务可能被标为通过，迭代显示完成但路径中的执行步骤仍未完成。

建议：每次验收绑定明确的 execution ID 和结果版本。`passed` 要求执行完成、必要应用完成以及证据满足策略；例外使用独立的 `waived`，强制记录理由。

### P0-7：迭代所谓“固定输入”并未完整冻结

迭代和任务只保存 requirement ID，需求内容仍可原地修改；再次确认同一个 ID 后，旧任务执行时会读取新内容。迭代也没有保存创建时采用的 baseline ID，后续执行使用启动时的最新基线。

证据：

- `application-atlas-production-pack/project_store.py:433-445`
- `application-atlas-production-pack/project_store.py:508-533`
- `application-atlas-production-pack/project_store.py:680-686`
- `application-atlas-production-pack/execution_service.py:38-65`
- `application-atlas-production-pack/execution_service.py:105-150`

影响：页面声称迭代固定了需求、文档和工作区依据，实际只有文档版本较完整地冻结。需求或基线变化可静默改变旧迭代的执行语义。

建议：需求引入不可变修订版本，迭代和任务固定 requirement revision；迭代保存 baseline ID，并为活动迭代提供显式 rebase，而不是隐式使用最新值。

### P1-1：物理页面顺序与任务依赖顺序相反

生成和基线位于需求与决定之前。生成文档被阻塞时，修复入口在更下方；生命周期提示只是文本，不能直接定位到阻塞项。

证据：`atlas-web/src/routes/project-detail.tsx:122-145`、`atlas-web/src/routes/project-detail.tsx:629-637`。

建议：页面主线调整为“资料 → 分析与待处理事项 → 范围和决定 → 审阅文档 → 固定迭代输入 → 执行与验收”。基线对已有项目应靠前，对新想法可延后到首次执行准备阶段。

### P1-2：任务可以不关联任何需求或文档

新任务默认选择迭代输入，但用户可全部取消；保存只要求标题、目标和写入路径。

证据：`atlas-web/src/routes/project-detail.tsx:311-327`。

影响：任务可执行、应用和验收，却不对应本迭代任何范围与完成条件。

建议：交付类任务至少绑定一条需求；分析类例外要明确说明。页面显示迭代需求的任务覆盖率和未覆盖项。

### P1-3：验收时看不到验收对象，验收后看不到验收证据

任务卡不展示关联需求正文、验收条件和固定文档内容；验收只是一个自由文本框。通过或免验后，`acceptance_evidence` 不再显示。

证据：

- `atlas-web/src/routes/project-detail.tsx:323-388`
- `atlas-web/src/lib/atlas.ts:299-315`

建议：任务卡直接解析并显示需求和逐条验收条件；验收按条件记录结果与证据。历史验收证据始终只读可见。

### P1-4：重试会隐藏旧执行，历史迭代仍显示无效操作

任务卡只展示最新 execution；旧尝试、失败原因和证据没有入口。历史迭代继续使用与活动迭代相同的交互卡，可显示后端必然拒绝的继续、重试或验收操作。

证据：`atlas-web/src/routes/project-detail.tsx:263-269`、`atlas-web/src/routes/project-detail.tsx:331-388`。

建议：加入执行尝试时间线；历史迭代只读。恢复动作必须根据迭代和执行状态明确给出，而不是先显示按钮再返回后端错误。

### P1-5：资料是基础输入，却无法在工作台中检查和管理

项目详情只显示资料数量和 ID；实际资料内容、备注、读取状态和版本变化位于项目列表页的另一个区域。

证据：`atlas-web/src/routes/project-detail.tsx:115-145`、`atlas-web/src/routes/projects.tsx:196-300`。

建议：工作台加入资料摘要或项目内资料抽屉；所有 reference ID 可点击定位。缺资料时提供项目范围内的明确补充入口。

### P1-6：问题的影响范围被生成却未显示

生成契约要求问题包含 `affects`，但 `ProposalList` 映射时只保留 `question` 和 `why`。

证据：`atlas-web/src/routes/project-detail.tsx:651`、`atlas-web/src/lib/atlas.ts:541-545`。

建议：展示受影响文档、需求或迭代徽标，并在回答改变后将相关产物标为待复核。

### P2-1：生成候选的应用不是跨运行幂等操作

应用标记只保存在当前 run 中；需求创建是无去重的 INSERT。相同内容在另一轮运行中可再次加入。

证据：

- `application-atlas-production-pack/project_generation.py:531-605`
- `application-atlas-production-pack/project_store.py:383-401`

建议：给生成项目建立数据库级 application receipt，以 `(run_id, item_kind, item_index)` 保证事务与幂等；跨运行显示内容重复提示。

### P2-2：文档和基线历史只部分可见

旧文档版本只显示元数据，无法打开任意旧正文；基线只显示最新一份，其余只有数量。

证据：`atlas-web/src/routes/project-detail.tsx:413-516`、`atlas-web/src/routes/project-detail.tsx:877-920`。

建议：历史版本和基线提供时间线、详情和任意比较；任务可从固定版本 ID 直接跳转到对应内容。

### P2-3：导出不包含生成问题、回答、冲突和处理记录

当前导出包含资料、需求、决定和文档，但 generation run 的开放问题与建议不在包中。

证据：`application-atlas-production-pack/project_export.py:35-65`、`application-atlas-production-pack/project_export.py:113-129`。

建议：导出增加 `open-items.md` 或结构化等价物，记录问题、处理状态、答案、来源运行和关联决定。

## 5. 建议的目标页面逻辑

不再让九个布尔步骤同时承担导航、状态和完成证明。页面分为一个状态入口和四个工作阶段。

### 5.1 顶部状态入口

顶部只回答四件事：

- 当前项目是什么，工作区是否可用。
- 当前活动迭代是什么；没有活动迭代时明确显示“尚未建立”，不拿历史迭代冒充当前状态。
- 下一项可执行动作是什么，以及具体阻塞项。
- 有多少待处理事项，按问题、范围确认、过期文档、基线冲突和验收失败分类。

状态由后端返回权威摘要，前端不再从多个对象拼接出近似生命周期。

### 5.2 阶段一：理解项目

包含固定资料、项目目标、工作区现状和生成运行。资料可在当前项目内查看、补充、更新或注明不采用。

新想法默认先处理资料和目标；已有项目同时展示工作区观察与基线状态，不强迫两种模式使用完全相同的面板顺序。

### 5.3 阶段二：处理问题并确定范围

建立统一的待处理事项（Open Items）收件箱：

- 问题：回答、暂缓或标记不适用。
- 冲突：采纳修正、说明不冲突或暂缓。
- 建议：转成需求、转成决定、忽略或稍后处理。
- 候选需求：加入后仍需用户确认范围。

每项保存来源、证据、影响范围和处理状态。用户回答问题时可同步生成决定，但问题与决定保持可追溯关联。

### 5.4 阶段三：形成并冻结计划

文档同时展示两个正交状态：

- 依赖新鲜度：当前 / 过期。
- 人工审阅：待审 / 已批准 / 已拒绝。

建立迭代前显示一份冻结输入清单：需求修订版本、文档版本、工作区基线、未解决问题及例外理由。用户确认后生成不可变迭代输入。

### 5.5 阶段四：执行、应用与验收

每个任务卡先显示任务依据和完成条件，再显示执行尝试时间线。状态顺序为：

> 未执行 → 执行中 → 结果待核对 → 文件待应用 → 基线待采用 → 待产品验收 → 已通过 / 未通过 / 已免验

分析任务可以没有文件应用阶段，但仍要成功完成或明确免验。验收绑定具体执行结果，并逐条对应需求验收条件。

历史迭代保持只读；继续开发通过“从此处建立新迭代”完成，不在终态记录上继续显示无效按钮。

## 6. 状态模型最低要求

| 对象 | 当前不足 | 最低新增状态或关联 |
|---|---|---|
| 生成问题 | 无 ID、答案和处理状态 | 稳定 key；open/answered/deferred/dismissed/superseded；关联 decision |
| 冲突/建议 | 只能展示 | open/resolved/dismissed；处理理由；转需求/决定记录 |
| 需求 | 内容可原地改变 | 不可变 revision；迭代固定 revision ID |
| 文档 | current 同时承担新鲜度和批准 | freshness 与 review_status 分离 |
| 迭代 | 未固定 baseline 和 requirement revision | 冻结输入清单；显式 rebase |
| 执行 | 页面只见最新尝试 | current execution + attempt history + supersession reason |
| 应用 | 文件写回和基线采用混为 applied | files_applied 与 baseline_adopted 分离 |
| 验收 | 不绑定执行结果 | execution ID、逐项证据、reviewer/time、waiver reason |

## 7. 实施顺序

### 第一批：先保证页面不说错

1. 修复项目切换时的旧数据泄漏。
2. 显示问题的 `affects`，并暂时把无处理入口的问题标为“分析提出的开放问题”，不宣称可在页面回答。
3. 一致性信号明确展示统计来源，停止把不同 run 的项目混为当前画面汇总。
4. 显示 `baseline_adoption_error`；没有新 baseline 时不把应用步骤标为完成。
5. 失败或停止的执行不能普通 Pass，只能重试或有理由地 Waive。

### 第二批：补齐决定、审阅与验收闭环

1. 为问题、冲突和建议增加稳定 ID、处理状态及转决定/需求动作。
2. 分离文档新鲜度与人工审阅状态。
3. 任务显示关联需求、验收条件和文档版本；验收证据始终可见。
4. 加入执行尝试历史，历史迭代改为只读。

### 第三批：修正冻结与恢复语义

1. 引入 requirement revision，迭代固定需求修订。
2. 迭代固定 baseline，并支持显式 rebase。
3. 分离文件写回和基线采用，增加崩溃恢复和幂等 receipt。
4. 生成运行增加相对当前项目的 fresh/stale 状态，过期结果不能无提示应用。

### 第四批：重组页面信息架构

在状态语义可靠后，再将长页面重组为“理解项目、确定范围、冻结计划、执行验收”四阶段，并提供统一待处理事项入口。若先重排页面，错误状态只会换一个位置继续存在。

## 8. 验收标准

完成本轮设计修正至少需要通过以下行为验证：

1. 在两个项目间快速切换时，任何旧项目对象都不可与新项目操作同时出现。
2. 每个“需要用户处理”的条目都有明确动作、持久状态和来源；处理后计数立即且可解释地变化。
3. value、analysis 和 improvement 的开放项不会因为切换运行而混淆或假装已经处理。
4. AI 保存的文档在人工批准前不能用于活动迭代。
5. 需求修改后，既有迭代仍使用原修订，或必须显式 rebase。
6. 文件写回但基线采用失败时，页面不能显示完整应用成功，也不能普通通过验收。
7. 失败、停止、未执行和未验证的任务不能被普通标为通过。
8. 验收界面能看到需求、逐条验收条件、固定文档和对应执行证据；验收后证据仍可查。
9. 重试后所有执行尝试仍可查看，历史迭代不显示后端必然拒绝的动作。
10. 导出包可以解释项目仍有哪些问题、已如何回答、哪些例外被明确接受。

## 9. 保留的正确设计

以下方向不应在重构中丢失：

- AI 推荐范围和用户确认范围分开保存。
- 生成内容先作为候选，用户逐项采用后才进入项目记录。
- 上游文档先保存，下游文档固定实际采用的不可变版本。
- 执行、文件应用和产品验收保持分离。
- 越界文件变更阻止应用。
- agent 的结构化完成报告不等同 Atlas 验证或产品验收。
- 工作区变化检查明确区分已检查范围和未检查范围。

这次检查说明底层领域拆分已有良好基础，但页面还没有把这些边界转换成可理解、可完成、可恢复的用户任务流。
