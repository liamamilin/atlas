# U17 M2 关联文档基础闭环验证

日期：2026-09-13
状态：基础闭环完成；自动资料分析与文档生成随后已完成，见 [生成验证](U17_M2_GENERATION_VALIDATION.md)；自然语言修改未完成。
依据：[产品设计](U17_DESIGN.md) · [开发规划](U17_DEVELOPMENT_PLAN.md)

## 1. 本阶段完成的能力

项目工作区现在把固定资料、需求、用户确认、项目决定和关联文档放在同一条可追溯链路中。

- 候选需求使用稳定的 `req_` 标识，记录验收条件和固定资料引用。分析推荐与用户确认分别存储；推荐不会自动成为本版范围。
- 用户可以确认本版、以后或排除，并保存确认理由。需求内容、验收条件或来源发生实际变化后，旧确认自动清除。
- 项目决定使用稳定的 `dec_` 标识，保存决定、理由及资料引用。
- 支持调研分析、产品需求、交互说明、技术方案、开发规划、验收方案和项目现状七类关联文档。
- 文档依据可引用固定资料、需求、决定或另一份文档的具体版本。服务端在保存时重新核对归属并固定来源版本或内容指纹，不信任客户端提供的快照。
- 每次文档保存新增不可变的 `dver_` 版本，记录作者和修改说明。`expected_current_version` 防止旧页面静默覆盖较新的内容。
- 需求含义或上游文档变化会把依赖文档标为待复核。系统保留原正文，用户核对并保存新版本后状态恢复为当前。
- 可以查看版本历史和最近两版统一差异。
- 项目可导出为自包含 Markdown 目录和 ZIP，包含总览、需求、决定、来源索引、固定摘录、当前文档、未决需求、待复核文档、逐文件哈希和整包 SHA-256。

项目库 schema 从 v2 升级为 v3，为文档版本补充 `author` 与 `change_summary`。v1、v2 数据在打开时迁移；既有版本分别使用 `unknown` 和空修改说明，不伪造历史作者。

## 2. API 与界面

新增的项目工作流接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/projects/<project-id>/workspace` | 一次读取项目、资料、需求、决定和当前文档 |
| POST | `/api/projects/<project-id>/requirements` | 创建候选需求与分析推荐 |
| PATCH | `/api/projects/<project-id>/requirements/<requirement-id>` | 修改需求含义、验收与来源 |
| POST | `/api/projects/<project-id>/requirements/<requirement-id>/confirm` | 保存独立的用户范围确认 |
| POST | `/api/projects/<project-id>/decisions` | 记录项目决定与依据 |
| POST | `/api/projects/<project-id>/documents` | 创建关联文档 v1 |
| GET/POST | `/api/projects/<project-id>/documents/<document-id>/versions` | 读取历史或新增不可变版本 |
| GET | `/api/projects/<project-id>/documents/<document-id>/diff` | 比较指定版本或最近两版 |
| POST | `/api/projects/<project-id>/export` | 生成自包含 Markdown 目录和 ZIP |

项目列表新增“打开工作区”。项目详情页显示范围与验收、决定、文档版本和一致性信号。“明确冲突”“需要决定”“参考建议”分别呈现，关联文档复核使用独立信号，不与建议计数混合。“明确冲突”在内容分析接入前显示“未检查”，不会把没有运行分析误报成零冲突。

## 3. 实际浏览器闭环

在临时项目库和实际 Vite/API 服务上完成了下列流程：

1. 创建新想法项目，收藏 `task-management-application#core-model` 的固定资料摘录。
2. 建立候选需求，AI 建议为“本版”，但用户确认保持为空；界面把它计入“需要决定”。
3. 用户确认本版后，未决计数归零。
4. 基于该需求和固定资料建立产品需求文档 v1。
5. 修改需求，增加独立 Markdown 导出要求。旧用户确认被清除，产品需求文档被标为“需要复核”，原文没有被自动改写。
6. 用户重新确认范围，在完整保留旧正文的基础上加入导出要求并保存 v2。
7. 文档恢复“依据为当前”；历史同时显示 v1、v2、作者、修改说明和内容哈希，最近两版差异包含新增要求。
8. 导出成功，页面返回 ZIP 本地路径和整包 SHA-256；包内资料、需求与文档数量和当前项目一致。

这条验证覆盖了 M2 的核心风险：推荐不能代替确认，需求变化不能静默保留旧确认，文档变化不能覆盖人工正文，上游变化必须可定位，导出后不能依赖 Atlas 页面才能解释项目。

## 4. 自动化验证

Python 离线回归共 60 项通过，新增覆盖：

- v1/v2 项目库到 schema v3 的迁移；
- 文档作者、修改说明、固定依据和跨项目引用拒绝；
- 需求变化与上游文档新版本的复核传播；
- 文档乐观并发冲突和不可变版本历史；
- 推荐、用户确认、需求修订、文档版本、差异及导出的 HTTP 完整流程；
- ZIP 自包含内容、AI 推荐与用户确认的明确区分。

前端 TypeScript 检查和生产构建通过。浏览器验证未产生当前服务地址的运行错误；开发服务器历史日志中有一次热更新前后 Hook 依赖数量变化提示，来自开发中替换组件代码，重新加载后的当前页面未复现。

## 5. 后续进展与当前边界

本记录描述的是可信人工闭环落地时的验证结果。固定输入分析与按类型文档生成已在后续阶段完成，具体边界和实跑证据见 [U17_M2_GENERATION_VALIDATION.md](U17_M2_GENERATION_VALIDATION.md)。

- 已能基于固定资料生成分析、关键问题、范围建议和单类关联文档草案；尚不能按依赖图批量生成整套文档。
- 尚未提供章节级编辑或用自然语言修改指定文档内容。
- 一致性面板会使用最新完成的固定输入分析报告内容冲突；没有完成分析时仍显示“未检查”。
- 价值分析仍按需提供，不参与自动放行或否决。
- 导出包含当前文档版本及其版本标识，旧版本保留在 Atlas 项目库中；外部修改文档的重新导入安排在后续迭代。

下一步继续完成自然语言文档修改和已有项目基线。人工修改、用户确认、项目知识及验收状态继续由 Atlas 独立保存。
