# U17 M5 完整试点计划

日期：2026-09-13  
状态：核心主线最小真实开发冒烟已通过，评估型试点尚未开始
依据：[U17 设计稿](U17_DESIGN.md) · [开发规划](U17_DEVELOPMENT_PLAN.md) · [M4 执行验证](U17_M4_EXECUTION_VALIDATION.md)

## 1. 目标与顺序

M5 不继续预设新的产品模块。前置的最小真实开发冒烟已经证明“搜索阅读 → 固定资料 → 确认范围与文档 → 工作区基线 → 迭代与任务 → 执行和应用 → 独立验收”可以连续完成。现在使用三个真实案例检查完整流程、产品价值和后端选择。

执行顺序按必要性排列：

| 顺序 | 优先级 | 工作 | 完成条件 |
|---|---|---|---|
| 1 | P0 | 最小真实开发冒烟（完成） | 已连续走通类型入口、项目、基线、需求、文档、迭代、执行、应用和独立验收 |
| 2 | P0 | 修复核心阻塞并重跑（完成） | 已修复冒烟发现的错误状态和证据口径问题，并从头完成最终全绿复验 |
| 3 | P1 | 固定试点协议与逐案例普通生成对照 | 核心冒烟通过后，在每个评估案例开始前固定模型、输入、来源版本、计时边界和记录位置 |
| 4 | P1 | 简单新想法完整闭环 | 从搜索开始完成一个可验收开发范围，再修改要求并完成下一轮 |
| 5 | P1 | 已有项目改进完整闭环 | 读取真实代码与文档，完成局部改进、旧行为回归和外部变化冲突核对 |
| 6 | P1 | 多类型需求试点 | 使用多个类型形成可执行范围，明确数据归属、流程交接和取舍，不强制单一分类 |
| 7 | P1 | 修复试点重要问题并重跑 | 来源真实性、范围、项目隔离、写回安全、验收真实性和主要可用性问题均有处理结果 |
| 8 | P1 | 汇总 M5 验收与发布检查 | U17-A1 至 U17-C5 均有证据或明确的未通过记录，相关回归和浏览器流程通过，状态文档一致 |
| 9 | P2 | 作出执行后端演进决定 | 根据首次通过率、重试、恢复、控制能力和成本，记录继续复用、局部替换或局部自研的选择 |

最小核心冒烟只验证功能可用性，不承担效果比较。普通生成对照在核心冒烟通过后与每个评估案例同时开始，不能在该案例的 Atlas 结果已经可见后补做。后续修复也保留原始失败记录，不用最终成功结果覆盖试点过程。

## 2. 固定记录协议

每个案例开始前建立独立记录目录，建议使用 `docs/u17-pilots/<case-id>/`，至少包含：

- `manifest.json`：案例 ID、开始时间、模型及版本、Atlas 版本、来源 ID 与指纹、项目和工作区说明。
- `ordinary-input.md` 与 `ordinary-output.md`：不使用 Atlas 工作流约束的普通方案生成原始输入输出。
- `atlas-input.json` 与 `atlas-output.json`：Atlas 固定输入、运行 ID、原始模型结果、校验结果和重试原因；凭据不进入记录。
- `scope-and-timeline.md`：开始和结束口径、关键追问、范围确认、人工修改及耗时。
- `execution-and-acceptance.md`：文档版本、迭代、任务、执行、差异、验证命令、应用、产品验收和后续修改。
- `findings.md`：重要遗漏、错误建议、计划外修改、返工原因、严重度、处理结果和复验位置。

普通生成和 Atlas 生成使用相同模型、用户目标、项目材料及来源正文。两者允许使用不同的流程提示，因为结构化约束本身就是待评估方案；记录必须保存提示差异，不能把 Atlas 后续确认的需求反向加入普通生成输入。

统一记录以下观察项：

1. 首次结果是否通过现有结构和依据校验；失败时记录校验项、重试次数及新一轮是否改变了输入。
2. 用户或开发者指出的重要遗漏、无依据结论和错误建议。
3. 开发前仍需回答的问题，以及问题来自资料不足、需求未决还是实现约束。
4. 从固定初始目标到确认首个开发范围的耗时和主要修改原因。
5. 开发中的计划外改动、回退和返工原因。
6. Agent 报告、Atlas 文件与命令证据、结果应用和产品验收四种状态是否保持分离。

没有真实用户参与的观察项标为“未观察”，不能用开发者估计冒充用户结果。M5 先建立事实基线，不预设提升比例。

## 3. 案例一：简单新想法

使用现有[本地优先个人日计划器样例](u17-samples/new-idea/package.json)作为起点，但在正式试点中从网页搜索、阅读和收藏重新建立项目记录，不能直接把静态样例当作端到端证据。

建议把范围分为两轮：

1. 首轮确认并实现“从多个项目选择当天承诺任务，并在本地持久保存”的最小纵向范围，对应现有样例 NI-R1、NI-R3。
2. 后续修改增加“手动时间块和冲突提示，系统不自动移动用户输入”，对应 NI-R2、NI-R4。

本案例必须展示关键引用可定位原文、资料深度与未知清楚区分、范围修改触发下游复核、旧文档版本可查看、独立文档包可导出，以及第二轮使用新的项目现状继续执行。主要覆盖 U17-A1、U17-A3、U17-A4、U17-C2、U17-C3。

## 4. 案例二：已有项目改进

从一个包含真实说明、实现和回归命令的本地项目开始。优先选择当前 Application Atlas 的受控副本或另一个可以独立复验的小型真实项目；具体改进项必须来自现状检查，并在生成方案前固定用户可观察行为、允许写入范围和旧行为回归条件。

流程必须包含：

1. 建立工作区基线，区分文档声称、代码线索、运行证据与未检查范围。
2. 固定改进目标和 Atlas 资料，生成并确认局部范围。
3. 在隔离副本执行修改，运行预先固定的旧行为回归和本次验收命令。
4. 应用前制造一次相关外部变化，确认过期基线或冲突会阻止无提示覆盖；审阅并采用新基线后再继续。
5. 应用合规结果、记录独立产品验收，并从新基线创建下一轮。

已有 M3/M4 记录可以作为单项能力证据，但不能代替这次从接入到下一轮的完整案例。主要覆盖 U17-B1、U17-B2、U17-B3，并复核 U17-C1、U17-C4。

## 5. 案例三：多类型需求

候选案例为“客户项目交付与个人排程”：项目管理资料描述客户项目、交付项和任务，时间安排资料描述个人可用时段与时间块，客户门户或审批资料描述外部反馈与验收。正式采用哪些类型和应用以实际搜索、正文深度和边界说明为准。

文档和确认范围必须回答：

- 哪个模块持有项目、任务、排程、交付物和客户决定的主记录。
- 任务进入个人排程、交付物进入客户验收、客户反馈返回项目计划时传递哪些标识和状态。
- 复制与引用、同步及时性、权限边界和失败恢复之间的取舍。
- 哪些结论来自正式类型资料，哪些只是当前项目假设，哪些仍需用户决定。

该案例至少走到确认范围、关联文档、结构化任务和独立导出/交接；选择代码范围后使用与前两个案例相同的执行和验收边界。主要覆盖 U17-A2，并再次检查 U17-C2。

## 6. 缺陷处理顺序

试点发现的问题按影响处理：

| 级别 | 判断 | 处理要求 |
|---|---|---|
| 阻塞 | 伪造或错引依据、自动改变确认范围、跨项目混用、覆盖外部修改、越界结果可应用、失败被标为验收通过、项目状态无法恢复 | 暂停对应案例，修复后从受影响步骤重跑；保留原始失败证据 |
| 重要 | 默认文档难以使用、需求与人工编辑关系不清、关键未知没有暴露、严格校验反复失败、开发任务缺少必要上下文 | 三个案例完成前修复，至少在一个受影响案例中复验 |
| 优化 | 文案、布局、非关键步骤数量、bundle 大小和更深的实例资料 | 记录实际影响，M5 收口后排序 |

隔离副本目前不复制 `node_modules` 和 `.venv`。每个代码案例在正式执行前记录依赖和验证命令可用性；若真实任务被阻塞，先评估项目级准备命令或受控的只读依赖复用，再决定是否扩大执行环境能力，不预先建设通用环境编排平台。

## 8. 后端演进决策

M5 完成后再更新长期执行架构：

- OpenCode 在代码执行、会话续作、恢复和权限控制上满足三个案例时，继续作为首个执行后端。
- 分析、文档生成或章节修改因结构约束产生明显重试和成本时，先评估这些边界明确的任务直接调用模型，再与 OpenCode 方案比较。
- 只有具体任务持续出现无法通过适配层解决的行为控制、部署、恢复或总成本问题时，才提出局部自研 agent 工具循环，并写明替代范围与长期维护成本。

完整自研 coding agent harness、多引擎产品化、云端执行和运行中长会话迁移不进入 M5 既定范围。

## 9. M5 完成门槛

- 最小真实开发冒烟已从头连续通过，主线阻塞均有修复和复验证据。
- 三个评估案例均有固定输入、普通生成对照和 Atlas 原始记录。
- 简单新想法与已有项目两条入口均走到成果核对和下一轮；至少一次后续修改真实执行。
- U17-A1 至 U17-C5 均有可定位证据或明确的未通过结论。
- 阻塞问题全部修复并复验；重要问题有处理结果或清楚的延期理由。
- Python 离线回归、TypeScript 类型检查、生产构建及关键浏览器路径通过。
- README、设计稿、开发规划、路线图和 M5 验收记录状态一致。
- 形成一份有实测依据的 OpenCode 继续复用、局部替换或局部自研决定。
