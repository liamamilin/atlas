# 电商图谱 v0.6 · 可理解性检查与三项门禁记录

依据技能提交 `067aafa`，重写[电商图谱](e-commerce-platform.md)，保留 v0.5 原文件作对照。检查假设读者只有日常购物经验，未预先学过电商或软件术语。本页是作者审查记录，不是新读者测试报告。

## 先找出“准确，却仍然读不懂”的表达

以下旧句直接取自 v0.5；新版状态和变化在正文相邻呈现。问题不是这些术语一定错误，而是它们要求读者先掌握未解释的对象或关系。

| v0.5 原句 | 读者可能卡在哪里 | v0.6 怎样建立所指 |
| --- | --- | --- |
| 同一商家的商品 P 在店面甲的分类 C 中出现，在店面乙的分类 C 中不出现（PrestaShop 8）。 | “店面上下文”“P”“C”“关联”没有让人看到一本书在哪个网站展示。 | 改用一本书、两个网站和同名分类；先说只加入甲会怎样，再保留按网站分别展示的关系。 |
| 已配置的搜索别名按目标词查找已索引商品（PrestaShop 9 文档情形）。 | 不知道别名是谁的别名、索引是什么，也不知道顾客实际输入了什么。 | 先写顾客误输 palyer 仍按 player 搜索；解释指定错拼纠正、为搜索准备商品资料后，再命名别名与索引。 |
| 一个商品变体有自己的售价（WooCommerce）。 | “变体”可能被理解成另一件完全不同的商品。 | 先给同款 T 恤的蓝色 M 码与红色 L 码，再命名商品变体；价格仍属于具体款式。 |
| 客户的商品报价采用其客户组折扣（PrestaShop 8）。 | U、G 和“客户组报价”需要读者自行还原人物与计价关系。 | 改用小林只属于一类顾客、100 元按该类九折变成 90 元；保留单组、无税及无其他优惠的条件。 |
| 交易款项进入可出款余额，但尚未因此成为银行到账款（WooPayments）。 | “可出款余额”没说明钱在哪里，为什么还不是商家银行里的钱。 | 先说明收款服务向银行转钱，再分别描述等待期、可以安排转出和银行在途。 |
| 支付争议可记录为发卡行审查中的 Under Review（WooPayments）。 | 若不知道发卡行与争议，Under Review 只是又一个外语标签。 | 先说明持卡人向办卡银行质疑扣款，再说商家回应后等谁决定；保留过程与最终结果的差异。 |
| 取消尚未发货的预留数量会释放相应可售量（Adobe Commerce）。 | “释放”像动作，但没说谁释放什么；“补偿”也可能被误读成赔偿顾客。 | 写清软件增加抵消占用的记录，使尚未发的两件能重新接单，再命名预留补偿。 |
| 同一订单含不同库存源的发运记录（Adobe Commerce）。 | “源”“已开票”“发运结果”需要多项先验知识，且容易混成仓库备注。 | 改写为甲仓发 1 件、乙仓发 3 件；解释发货前的订单款项销售单据，再给 Invoice 名称。 |
| 开启付款后授权时，顾客可在订单 Processing 阶段获得所购文件资格（WooCommerce）。 | Processing 本身不能说明为什么顾客已能下载、纸书却还没到。 | 先写付款后下载设置及已收款待交付的业务含义；保留关闭设置时等待标为完成的区别。 |
| 一份退货授权中只有部分申请商品获准退回（Adobe Commerce）。 | “部分授权”和 RMA 不能告诉新读者授权谁做什么。 | 直接写商家允许商品甲退回、拒绝乙；随后给产品术语及排除的商品范围。 |
| 同一订单是否计入某日报表可随日期口径改变（WooCommerce Analytics）。 | “日期口径”不说明到底哪天进入报表。 | 明确 1 日创建、2 日付款，切换以哪天归类后，1 日报表是否包含这笔购买发生改变。 |
| 非 SuperAdmin 员工的菜单编辑权限可以未被授予（PrestaShop 8）。 | SuperAdmin、配置档、View、Edit 互相说明，主语与许可对象不易恢复。 | 先写一组员工能看商品却不能改；再写管理员增加编辑许可，最后才给英文对应名称。 |

## 认知覆盖：没有为了易读而删除难领域

**作者检查：通过本轮范围的覆盖核查。** [覆盖表](COVERAGE.md)保留 v0.5 的 18 个主要领域及三类遗漏原因；下表逐项对应原有状态与变化，防止改写时丢掉复杂机制。数量只用于查漏，不是质量分数。三套产品资料继续并列，不把一种产品当成类型上限。

尚未研究的推荐效果、积分预存款、换货、运输丢损、利润等仍未补成已知能力。并发下单、重复付款通知、游客订单归属和外部文件控制仍因证据不足保留未知。多卖家市场、企业采购、周期购买为中心的完整模型仍未纳入本轮。

## 语言精确性：对象、条件、前后结果仍能判别

**作者检查：保留条目通过本轮精确性复核。** 每条都检查动作的主体、受影响对象、前后结果、近似反例和来源范围。具体产品、版本和开启设置等条件保留。没有把“读起来顺”当成“所有商城都会这样”。详细反例逐条列在下表。

### 术语首次出现的位置与解释次序

这不是放在文末替正文补救的术语表；对应解释都已写在正文首次使用处或紧邻的具体例子之后。检查顺序是“先看到对象与变化，再给名称”。

| 术语或标签 | 正文如何先建立所指 |
| --- | --- |
| B2C、订单 | 标题先写商家直接卖给个人；开头把保留的购买记录称为订单。 |
| 汇率 | 先写金额 100 按比例 2 变为 200，再命名该换算比例。 |
| 搜索别名、搜索索引 | 先写指定错拼按原词查找；再解释为搜索准备的商品资料，非用别名解释索引。 |
| 商品变体、缺货预订 | 先给颜色尺码的具体款式；先说明现在无货仍先接单，再给名称。 |
| 商品小计、客户组 | 先给所选商品的合计；先说小林被商家分入同一类顾客，再给名称。 |
| 购物车、结算、订单摘要 | 分别解释为暂存待买商品、提交前填写核对阶段、这次购买的简要清单。 |
| 配送区域 | 先说商家按地址划范围并规定每个范围的送货方式。 |
| Draft、Processing | 分别先说明提交前临时购买记录、钱已确认但仍待交货的订单；没有用一个英文状态解释另一个。 |
| 出款、Pending funds、Available funds、Pending、In Transit | 先说明收款服务向银行转钱；款项等待期、可安排转出、某笔转账未提交银行、某笔转账在途分别说明，并区分余额与转账记录。 |
| 支付争议、Under Review、支付授权 | 先说明持卡人质疑扣款、办卡银行尚在判断、银行卡同意之后可扣款；没有混为商城自行决定的结果。 |
| 库存预留、可售数量、预留补偿、库存源 | 从 10 件留 2 件、新订单还能订 8 件、取消后抵消占用、从哪个实际位置扣货分别建立所指。 |
| 履约、Invoice | 先说兑现交付约定；先解释订单款项销售单据，再给产品名称，不直接用税务发票替代。 |
| 下载授权、Completed | 先说允许这笔订单购买者取得文件，再给授权名称；标为完成有紧邻中文，没有暗示系统已验证实物签收。 |
| RMA、Partially Authorized、虚拟商品 | 先说退哪些商品、谁允许退；先写甲允许乙拒绝；将无需实物配送的商品说明后再命名。 |
| 支付网关、客服会话、Open、Closed | 先说连接收款服务的组件、一次联系的一组消息、待处理与标为已处理；非重复英文标签。 |
| 游客结算、订阅、匿名化 | 分别先说明不注册仍留订单、按周期继续购买、姓名邮箱被替换而订单保留。 |
| 净销售额、日期口径 | 先给扣除哪些金额、选创建日还是付款日的实例，再命名。 |
| View、Edit、Shop Manager、角色 | 先说允许看和改什么、哪类用户可退款；英文名称只供核对具体产品。 |

### 标题与其余核心段落

| 检查对象 | 检查结论 |
| --- | --- |
| 标题与开头 | 标题不要求先懂 B2C；购买记录给订单锚点。期望状态和变化各有一个明确问题，不用术语互相定义。 |
| 概览四行 | 纸书和电子书、甲乙网站、可选语言、货币金额均有日常对象；没有 P/C 符号或店面上下文。 |
| 17 个领域标题 | 直接说顾客找什么、买什么、商家记录什么；发货、下载、钱款等段落标题自身不依赖正文的术语解释。 |
| 六条关系 | 区分展示与授权、付款与交货、退货与退款等对象；跨资料组合与对象关系仍标为归纳。 |
| 覆盖与遗漏 | 原来的“并发竞态”“支付重复通知”“获客归因”等改为多人同时抢货、同一次付款多次通知、顾客从哪里来等实际问题；没有把未知改成事实。 |
| 专业深度 | 保留条件依赖、两种库存数量及抵消记录、分批与分来源发货、钱款阶段、退款记录与服务确认、报表计算与日期归属、角色许可范围。没有退化成按钮名称清单。 |

### 修订后仍需留意的理解负担

英文状态名保留是为了核对来源，其旁已有中文含义；理解结果不需要记住这些名称。多产品规则继续署名，避免读者拼成所有商城通用的顺序。高级缺口只说明问题与缺证原因，不编造一个看似简单的答案。

以上是作者逐条复述的结果，尚未让真实的新读者独立阅读并回述。因此不能报告“普通人读懂率”或声称三项门禁已证明学习效果。作者若仍发现未解释的关键所指，需继续改正文，不能仅在本页追加解释。
