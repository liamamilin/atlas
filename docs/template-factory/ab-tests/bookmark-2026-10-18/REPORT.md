# 认知模板开发 A/B：书签收藏夹

2026-10-18。本轮两组开发与独立评测均使用 **OpenCode CLI → `commandcode/deepseek/deepseek-v4.1-flash`**，reasoning effort=high。

**本次观察：基础用户闭环两组都能完成；模板组保留了更多边界规则，但开发交接明显更重，而且本轮 CLI 没有正常完成。可以看到具体认知价值，还不能据此认定模板带来普遍质量提升或批量产线已经稳定。**

最终独立评测前只使用匿名 X/Y，完成后揭盲：**X＝不使用模板；Y＝使用自动认知模板 v0.1.12**。原始[独立配对评测](evaluation/independent-comparison.json)、[完整结果与源码摘要](RESULT.json)、[事先冻结的评测规则](evaluation/rubric.md)均保留。

## 实际结果

任务是完整实现“生活待购与灵感收藏夹”：保存 URL/标题/备注，默认未分类，新建并选择归类、移动、按归类浏览、关键字搜索、打开原网页、刷新及服务重启后保留。没有要求账号、支付、协作或运营后台。

| --- | --- | --- |
| 预先冻结的九项核心需求 R01–R09 | 全部有直接运行证据，独立评测判定通过 | 全部有直接运行证据，独立评测判定通过 |

| 中文、引号、HTML 字符与本地无害脚本标记 | 已测；未观察到脚本执行 | 已测；未观察到脚本执行 |
| 长备注补充探索 M02b | 完整提交 3,420 码点并得到 201，刷新只读回 **2,000**，没有截断提示 | 同样的逻辑输入，刷新完整读回 **3,420** |

| OpenCode 开发调用 | CLI 退出 0 | CLI 退出 **1**，保留 provider 流错误 |

M02b 是在 X 首次独立审阅指出“长备注可能截断”的风险之后，给双方增加的**事后补充探索**。它不改变九项事先冻结的核心需求判定，也不作为新的合格门槛。源码与实际提交体共同证实 X 的备注截断，属于真实的已接受文本丢失；这里不能把标题输入框的 maxlength 限制混称为同一种保存后丢失。

HTML textarea 的表单传输把 LF 转为 CRLF：Y 原始提交为 3,600 码点，逻辑 textarea 值是 3,420；读回按原逻辑 LF 比较。工具同时保留原始和逻辑提交值，没有 trim、截短或忽略丢失字符。X 的 JSON 直接提交 LF 3,420。证据：[X 补充记录](blind/X/initial/supplement/result.json)、[Y 补充记录](blind/Y/initial/supplement/result.json)。

独立评测将 X 的备注丢失、Y 的生成调用失败分别记为 material 问题。超限输入拒绝策略等部分结论还有源码依据，但本轮**没有实测超过 10,000 码点备注或 500 码点标题的 Y 拒绝路径**，不把静态规则冒充运行通过。回收站等额外功能存在于 Y 源码，也不代表所有分支已经运行验证。

## 实验如何执行

- 相同自然语言场景、相同模型与 effort、独立新会话、相同 Python 3 标准库＋SQLite 环境和入口。只有 Y 获得完整冻结认知包：产品定义、调研、决策、阶段、架构、Agent 指令及验收材料。
- Python 环境是共同控制条件，会覆盖模板推荐的 Node/Fastify 栈；模板组需要做适配。这限制了耗时比较的解释，不能当作原推荐技术栈的直接表现。
- 两组由 OpenCode 在各自 app/ 中写文件，禁止 shell、执行程序、联网、跨组读取和访问其他项目。测试者未手工修改任何应用源码。开发 agent 自述检查均未运行；实际运行证据在后续独立步骤产生。
- 另一 agent 在接触实现前制定 [rubric](evaluation/rubric.md)。测试工具最初由独立子 agent 准备，遇账号用量限制后由主代理执行。使用真实 Chromium、HTTP 和专用 SQLite 数据目录；正常重启、强制结束与新目录隔离只操作本轮进程。
- 不要求某组特有的 API、错误码或 testid。两种 UI 各有操作适配器，共同断言一致，运行工具主文件的摘要完全相同。
- 外链验证捕获真实浏览器导航请求和完整链接/服务端 Location。正式运行使用本地拒绝代理及浏览器拦截，禁止外网连接。旧联调的 option 等待、外链记录及补充工具 CRLF 问题另存旧记录，修正工具后完整重跑，未归罪于应用。
- 最终配对评测是独立、只读的新 OpenCode 会话，未收到映射、开发提示词、生成日志或 X 的首次评测结论。评测者审查实际运行记录和源码，自身没有执行程序，也没有视觉查看截图；主代理查看了页面截图。相同模型可能有共同盲区，源码风格也可能暴露条件，因此不称严格双盲。
- 评测完成后才由 `finalize.py` 读取映射，核对输入、规则、冻结源码与评测源码摘要，确认测试进程结束，生成源码 ZIP 和 RESULT.json。两组都没有再做反馈修复，保留首版差异。

## 对模板产品的判断

这次验证支持“认知模板可以指导 coding agent 实现真实应用”，也找到了具体边界价值：已接受备注的完整保留、重复保存的明确策略。基础保存/归类/检索流程仅靠需求描述也做出来了；不能把所有功能都归功于模板。

当前认知包接近 1 MB 未压缩材料，带有完整精确契约和全部阶段验收。模板组本次大量读取和静态修订，墙钟时间更长；其交付可靠性还有真实失败。这些都是产品交接需要解决的问题，而非追加更多功能的理由。

建议优先做两项：

1. **把 P0 定义为完整的核心用户旅程，再按需加载成熟度材料。** 现包把保存放 P0、归类管理放 P1、搜索放 P2；本场景要完成最初需求就得走到 P2。保留成熟版认知，但开发入口先提供与当前场景相关的短包，详细 API 和全量验收分阶段读取。这是待验证方案，本次未修改原模板来追求更好成绩。
2. **补交付状态与续跑。** 调查长调用的 provider 流中断和收尾，把“完整候选源码已交付”“CLI 失败”“运行验证通过”分别记录；利用检查点继续，避免失败后一律重新灌入全部材料。非零退出仍保留失败状态，不能靠找到几个文件自动放行。

这是一个场景的一次配对。没有验证真实持久化写入故障、真实并发、长期使用、其他品类或原包完整 A01–A33 验收；不证明安全认证、规模化成熟度、认知模板已发布或通用工厂运行验收已集成。所有新增试用结果与旧手工样板 P0 成绩独立，冻结模板内 not_run 状态未被改写。
