# 工程与产品决策记录

记录实现中真实采用的默认、理由、被否决的替代方案、明确排除的范围，以及仍需人来决定的问题。
不虚构已答复的问题，也不为日常选择而阻塞。

## 已采用的默认与理由

1. **并发用 SQLite `BEGIN IMMEDIATE` 写锁**
   预约创建/取消在显式事务中先校验再写入，利用数据库写锁串行化"检查重叠 + 插入"，
   保证同一设施重叠时段至多一笔成功。理由：单进程多线程与多进程场景都成立，无需额外依赖，
   也无需自建内存锁（内存锁在多进程下失效）。不同设施不会被彼此"弄失败"，最多短暂排队。

2. **预约时间以 epoch 秒存储，输出统一 UTC ISO8601**
   输入要求带时区偏移，按真实时刻比较；存储数值使比较与排序稳定，避免字符串时区歧义。
   理由：跨时区比较正确、半开区间判断简单。`Z` 后缀在 3.10 的 `fromisoformat` 不支持，
   已在解析层归一为 `+00:00`。

3. **会话为服务端持久化的不透明令牌 + HttpOnly cookie**
   理由：满足"角色/归属不可由请求参数伪造"，且重启后无需重新登录。会话不设过期，
   属当前范围的简化（见待决问题）。

4. **创建接口成功返回 200 而非 201**
   理由：契约只写 `-> {id}`，200 是各类客户端都接受的保守选择；失败一律非 2xx 且带
   `{"error": ...}` 中文说明。

5. **可用性接口只回占用区间**
   `GET /api/availability` 只返回 `{start,end}`，不返回预约人、备注等个人信息；
   管理员的全量信息仅通过 `GET /api/bookings` 提供。

6. **取消采用"状态置为 cancelled"，重复取消幂等**
   理由：满足"保留状态记录并释放原时段"。释放通过可用性查询只统计 `status='active'` 实现，
   不做物理删除，从而保留历史。

7. **静态资源白名单下发**
   仅服务 `index.html`、`app.js`、`style.css` 三个已知文件，不做任意路径拼接，避免目录穿越。

8. **演示账号用 `INSERT` 幂等补建**
   仅当用户名不存在时创建，绝不重置已有账号的密码或删除任何记录，满足"重启后一致"。

## 被否决的替代方案

- **在内存中保存全部状态**：无法满足真实重启后一致，否决。
- **用数据库唯一约束表达时段重叠**：普通唯一索引无法表达区间重叠，需触发器且可读性差；
  改用显式事务内校验，语义更清晰。
- **明文或简单哈希口令**：不满足"使用口令哈希"，否决。
- **把角色或 owner 放在请求体/查询参数**：违反服务端强制权限，否决。
- **为通过测试而添加隐藏端点或硬编码夹具**：违反契约精神，否决。

## 明确不在范围内（及原因）

- 邮件通知、真实住户目录、支付、公网身份服务：契约明确排除，属外部集成。
- 账号注册 / 口令找回 / 多租户：超出"封闭名单内两个居民 + 一个管理员"的演示目标。
- 预约改期、候补队列、审批流：非本任务工作流所要求，属成熟功能，避免为"看起来完整"而引入。
- 任意文件访问、子进程、安装依赖：超出本地演示与安全边界。
- 前端日历 / 时区偏好：契约允许文本 ISO8601 输入，浏览器本地化可能改写时间，故不使用
  `datetime-local`，避免隐式时区转换。

## 仍需人决定的问题（未擅自定论）

1. 会话是否需要过期/吊销策略，以及演示场景下是否可接受无限期会话。
2. 管理员是否应能代表居民创建预约，还是严格只管理既有记录（当前实现允许管理员以本人身份预约）。
3. 设施是否需要可预约时间窗口、容量或启用/停用状态（当前仅名称）。
4. 预约是否允许修改时间（改期）而非取消后重建。
5. 数据留存与清理策略（当前保留全部历史，含已取消记录）。
