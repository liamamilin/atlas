# DECISIONS

工程与产品默认决策，含理由、被否方案、范围外内容与仍需人工确认的问题。

## 已做出的默认决策

1. **金额以整数「分」存储。**
   理由：货币必须是两位小数且要求「不静默取整或裁剪输入」。整数分可保证加减汇总精确；
   在 API/UI 边界用字符串 `format_money` 输出（如 `"0.10"`）。

2. **超过两位小数的输入直接拒绝，而非四舍五入。**
   理由：request/CONTRACT 明确要求不静默取整或裁剪。`parse_money` 只接受
   `^\d+(\.\d{1,2})?$`，`"10.999"`、`"1e3"`、`"1,000"`、负数均返回 400。

3. **支出金额必须 > 0，预算允许为 0。**
   理由：request 规定支出须为正数；预算为 0 是合法「暂不打算花」的取值。

4. **金额类型接受字符串与整数，拒绝浮点 JSON 数字。**
   理由：浮点无法可靠表示分，接受会导致隐性误差；字符串与整数可无歧义转换。

5. **SQLite 单文件，每个 HTTP 请求打开一个连接。**
   理由：本地单用户、写入量小；连接随请求建立/关闭最简单，避免跨线程共享连接的坑。
   在 `init_db` 中启用 `PRAGMA foreign_keys=ON`。

6. **同月分类名唯一（`UNIQUE(month,name)`），重复返回 409。**
   理由：CONTRACT 要求拒绝重复、「不制造隐藏的第二个分类」。按精确名（去除首尾空白后）判定，
   大小写敏感。分类名两条记录不会因空白差异重复。

7. **`PUT /api/categories/{id}` 只更新预算，忽略请求体中的 month。**
   理由：分类由全局唯一 id 定位，month 由该分类决定；忽略 month 可避免「意外改动到别的月份」。
   返回更新后的完整条目 `{id,name,budget,spent,remaining}`。

8. **支出日期必须与所属分类的月份一致。**
   理由：CONTRACT 明确要求；否则状态查询与导出都会跨月泄漏。

9. **导出使用 Python `csv` 模块，纯 UTF-8（无 BOM）。**
   理由：标准 CSV 引用即可让中文、逗号、引号、换行往返；不引入 Excel 公式等非核心行为。

10. **月份输入变化即重新加载状态；月份切换会重置编辑状态。**
    理由：保证 UI 始终显示数据库中该月的真实数据；避免把上一月的记录误改到新月份。

11. **失败输入不破坏旧数据。**
    理由：校验在写库前完成；SQLite 事务在异常时不提交，DELETE/PUT 先查存在性再写入。

12. **UI 使用 CONTRACT 给定的 `data-testid`，其余布局自由设计。**
    理由：这些是通用集成契约控件；分类下拉选项 value 等于 `category_id`。

## 被否方案

- **JSON 文件存储**：并发写与部分写失败会破坏数据，SQLite 更稳。
- **浮点数金额**：与「两位小数、不静默取整」冲突。
- **带 BOM 的 CSV / 主动处理 Excel 公式**：CONTRACT 明确不作核心要求，避免画蛇添足。
- **登录 / 多用户 / 银行或支付同步**：超出「单个本地用户、不连接外部服务」的范围。
- **在服务端自动阻止超支记账**：request 要求超支可见但不自动阻止。
- **分类改名以规避重名**：会引入未要求的复杂迁移逻辑。

## 范围外及原因

- 无网络、无遥测、无子进程、无任意文件访问、无依赖安装（受运行契约限制）。
- 不做货币换算、不做多币种；固定人民币两位小数。
- 不做账户/对账/预算提醒推送；request 未要求。
- 不做跨月预算结转；未要求，且需要人工决定结转规则。

## 仍需人工确认的问题

1. 分类改名、删除（及其支出如何处置：级联删除 / 迁移 / 阻止删除）尚未定义。
2. 是否需要「复制上月预算」以及结转时超支/剩余如何处理。
3. 备注是否需要长度上限与多行输入的展示策略。
4. 是否提供 CSV 导入与备份；若提供，冲突（同名分类、重复记录）如何判定。
5. 超支是否需要在 UI 上以更强提示（颜色以外）呈现。

未对上述任一问题擅自实现，以免引入未获授权的成熟功能。
