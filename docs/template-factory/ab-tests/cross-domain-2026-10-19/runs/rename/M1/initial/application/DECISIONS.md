# 工程与产品决策记录

本文件记录实际采用的默认值及其理由、被否决的备选方案、明确排除的范围，以及仍需要人来决定的问题。
所有条目都是本次实现真实采取的做法，不是待办愿望。

## 已确定的默认值（均已落实在代码中）

### DEC-01 陈旧计划证据 = `dev + ino + size + mtime_ns`
采用文件身份与元数据组合，不计算内容哈希。理由：改名是同文件系统元数据操作，计划与执行间隔极短，
元数据组合已能覆盖「内容被改写」「被删除」「被替换为目录」等被验收的陈旧情形；哈希在大批量或大文件上
有明显额外 I/O 成本。对应 D01。此选择存在极窄的漏检窗口（同 inode 上同大小同纳秒时间戳的替换）。

### DEC-02 同文件系统原子改名 + 跨挂载拒绝
假定根目录位于同一本地文件系统，`os.rename` 原子；跨文件系统会返回 EXDEV 而失败，失败时尽力回滚并
非零退出。理由：Python 标准库不暴露可移植的原子替换。对应 D02，限制已在 README 声明。

### DEC-03 整批预检 + 每步执行前再次 `lstat` 核查
执行前先整批检查冲突与源身份；每个改名动作前再核查目标不存在、源身份未变，遇目标出现即拒绝、不替换。
理由：不依赖 Linux 专有 `renameat2(RENAME_NOREPLACE)`；明确接受一个极小的 TOCTOU 窗口，并在文档写明。
对应 D03（default-adopted）。

### DEC-04 环与内部覆盖在预览阶段整批拒绝
新名落在本批源集合内（含 a↔b 环）一律视为计划内部冲突，预览时整体拒绝，不引入临时名两阶段交换。
理由：交换需要平台专有能力，超出本场景确认范围；「不覆盖」比「尽量成功」优先。对应 D04（default-adopted）。

### DEC-05 回执每步更新 + flush/fsync
执行过程中每完成一步改名即原子重写回执并 `fsync`，状态在 `applying`→`applied` 间演进；撤销成功后写
`undone`。理由：让崩溃后仍能核对已完成步骤；但不承诺断电级精确恢复（不记录计划文件的内容哈希，
也不做目录 `fsync`）。对应 D05，属尽力持久化。

### DEC-06 替换全部字面出现
对文件名中**所有**匹配的查找串做字面替换，逐条列入计划供审阅。理由：「替换」语义下行为可预测，且
预览可见；`util-linux rename` 默认只替换第一处被作为备选而非默认。对应 D06（default-adopted）。

### DEC-07 回执命名由计划文件名派生
回执固定命名为 `receipt-<计划文件名去扩展名>.json`，与计划同处状态目录。理由：不需要修改「不可变
计划」，即可用「回执是否存在且状态为 applied」判定重复执行；计划文件本身用排他创建、绝不覆盖。

### DEC-08 空匹配允许生成空计划
若没有任何文件名包含查找串，`preview` 成功返回 `operations: []`，`apply` 亦为空操作成功。理由：
这不是操作失败，且保持命令语义一致；避免把「无匹配」误报为错误。

## 被否决的备选方案

- **正则/递归/模式驱动**（brename、RnR 风格）：能力更强但需额外安装、作用域更大，与「字面替换、单目录、
  非递归」的确认范围冲突。只借鉴其「默认预览、冲突整体拒绝、journal 撤销」的设计思路，不复用代码。
- **无保护式改名**（`util-linux rename` 默认）：会直接覆盖目标，与本场景「冲突整批拒绝、绝不覆盖」相悖。
- **内容哈希作为默认证据**：见 DEC-01，成本与收益不匹配，改为文档化的扩展项。
- **临时名两阶段交换以支持环**：见 DEC-04，需要平台专有能力，超出范围。
- **依赖 `renameat2` 等 Linux 专有系统调用**：Python 标准库未暴露，且需保证 macOS 上可移植。

## 明确排除的范围（本阶段不做）

- 递归子目录、正则/通配匹配、目录与符号链接改名。
- 删除/回收站、复制、移动跨目录、云或网络同步。
- GUI/桌面文件管理器、多用户权限模型、计费与多租户、审计后台。
- 可选备份、多轮 undo/redo 链、跨平台大小写/Unicode 等价冲突保证。
- 对真实 Downloads/HOME 或应用源码目录的任何操作；工具只作用于显式指定的一次性根目录。

## 仍需人工决定的问题（未擅自作答）

1. **是否启用内容哈希**：当根目录位于低时间戳分辨率文件系统（如 FAT 2 秒）或存在同大小同时间戳
   的极短替换风险时，需要决定是否为陈旧判定增加哈希。影响预览/执行开销与漏检窗口。
2. **网络文件系统语义**：当操作者把根目录放在 NFS/SMB 上时，需决定是否允许以及如何核对「失败即未改名」。
3. **并发写入与锁**：当目录可能被其它进程并发写入时，需决定是否加目录锁或改用平台原子能力，
   以消除 DEC-03 所述的 TOCTOU 窗口。
4. **断电级恢复协议**：若需要崩溃后精确回滚（生产级或超大批量），需决定目录 `fsync`、计划留痕与
   恢复流程，而不是当前的尽力持久化。
5. **替换次数策略**：当替换串包含查找串（如 `a→aa` 可能级联）或用户只想改第一处时，需决定是否提供
   「仅首次替换」选项。

以上问题均不阻塞当前 P0 核心旅程，故按上列默认值实现并在 README 中声明为限制。
