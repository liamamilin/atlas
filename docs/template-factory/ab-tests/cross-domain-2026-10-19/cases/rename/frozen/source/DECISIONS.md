# 决策与默认值

## D01 · 陈旧计划判定的证据强度：仅用 dev/ino/size/mtime，还是额外计算内容哈希？

默认采用 st_dev+st_ino+st_size+st_mtime_ns 组合（平台不提供 ns 字段时回退秒级）；默认不计算内容哈希，因为哈希在大批量或大文件上有成本，且纳秒字段可用性未获文档逐字确认（S02、S03）。

When to ask / 询问条件: 当同一路径可能在预览与执行极短时间内被同大小、同时间戳的内容替换（仅哈希能发现），或根目录位于时间戳分辨率低（如 FAT 2 秒，S03）的文件系统时，需询问是否启用哈希。

影响 F03/F06 拒绝过期计划的能力与预览/执行开销；不启用哈希时存在极窄的漏检窗口。

open

## D02 · 根目录位于 NFS 等网络文件系统时，是否仍保证『失败即未改名』？

默认假设本地同文件系统原子改名（S03、S05），跨挂载返回 EXDEV 时拒绝；不承诺网络文件系统上的失败语义，并在帮助与文档中声明该限制。

When to ask / 询问条件: 当操作者明确把根目录放在 NFS/SMB 等网络挂载上时，需人工决定是否允许及如何核对。

影响 F05/F09 的失败安全承诺与回执核对策略。

open

## D03 · 执行期目标存在性的 TOCTOU 窗口如何处理？

采用执行前整批预检 + 每步执行前再次 lstat 核查，遇目标存在即拒绝且不替换；不依赖 Linux 专有 renameat2/RENAME_NOREPLACE（Python 标准库未暴露，S05），并在文档中明示极小窗口存在。

When to ask / 询问条件: 当目录可能被其它进程并发写入（多进程或后台同步）时，需人工决定是否加锁或换用平台特性。

影响 F04/F05 的免覆盖强度与并发场景下的行为。

default-adopted

## D04 · 换名环（如 a↔b，新名落在源集合内）如何处理？

默认把环与内部覆盖一律视为计划内部冲突，在预览阶段整批拒绝，不引入临时名两阶段交换；理由：交换需 Linux 专有 RENAME_EXCHANGE，超出确认范围（S05）。

When to ask / 询问条件: 当用户确有交换两个文件名或环状改名的需求时，需人工决定是否引入临时名方案。

影响 F04 冲突判定范围与 F15 的推进时机。

default-adopted

## D05 · 计划/回执的崩溃持久化语义与 fsync 策略。

默认每完成一步改名即更新回执并 flush+fsync 落盘，使崩溃后可核对与恢复；但抓取文档只显示存在 dump/日志文件而未确认其持久化与崩溃语义（S08、S09），故不承诺断电精确恢复。

When to ask / 询问条件: 当需要断电/崩溃后精确回滚保证（生产级或大批量）时，需人工决定持久化与恢复协议。

影响 F03/F05/F07 的恢复完整性与 I/O 开销。

open

## D06 · 同名内多次出现查找串时替换的次数。

默认替换全部字面出现并逐条列入计划；理由：『替换』语义下行为可预测，且可供用户在执行前逐条审阅；备选（util-linux 默认只替换第一次，S06）可作为后续选项。

When to ask / 询问条件: 当替换串包含查找串（如 a→aa）可能级联，或用户只希望改第一处时，需人工决定替换次数策略。

影响 F02 计划生成与 A02/A03 的预期操作数。

default-adopted
