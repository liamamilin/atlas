# Atlas 认知模板的推荐形式与证据边界

日期：2026-10-19。本文是三品类对照实验的探索性分析与设计建议，实际结果以 [REPORT.md](REPORT.md) 和原始证据为准；不是“普遍最佳形式已经得到证明”。工厂导出格式尚未按本文修改。

## 推荐：一个完整知识源，两个面向任务的视图，独立的验收证据

Atlas 的主产物应继续是可追溯的产品认知。规划时需要看完整的品类、场景、成熟产品定义与阶段路线；编码时需要先看到当前完整闭环、不能违反的规则、已确认决策和实际契约。两者从同一个版本化结构生成，避免两套相互矛盾的需求。

默认编码交接采用阶段执行视图；完整规划视图仍可下载和按主题读取。这个默认值是设计判断，当前实验没有证明分层形式稳定胜出、稳定节省计费 token，或无模板无法完成任务。

## 这轮证据支持到哪里

- 预约：三组共同 API、真实并发与浏览器流程全部通过，独立认知审阅也大体相当。明确 P0 下没有运行结果级胜者。
- 预算：无模板首轮通过；完整形式因两次文件清单路径协议错误未完成规范交付，不能据此断言源码业务能力差；分层形式出现启动错误，经一次 OpenCode 修复后通过。知识包不能替代启动与真实运行门禁。该品类原始四次调用均收到同一段额外宿主脚本，偏差保留，不能包装成严格干净输入的实验。
- 改名：单看预先冻结的核心检查可能看不出目录边界缺陷。独立 Agent 在源码审查后补充了单独冻结、对三组统一使用的 EP01，验证恶意计划标识符是否造成根目录外回执写入。其完整结论见报告；这项事后探索不改写原有核心成绩，不构成安全认证。
- 所有条件同样要求交付 README、DECISIONS，且共同需求已明确大量边界。对照组已经得到一份较强规格，本轮主要测实施支持，尚不能充分衡量 Atlas 最重要的“补全普通用户说不全的产品需求”的价值。

## 建议组织

| 内容 | 默认放在哪里 | 作用与限制 |
| --- | --- | --- |
| 品类认知、现成产品、开源复用/自建、许可证与未知项 | 完整认知库，规划时读取，编码时按主题引用 | 区分事实、推断、未核实项，绑定来源与版本；不用开源星数代替适配判断 |
| 角色、核心旅程、MVP 到成熟版能力、边界、非功能要求 | 结构化产品定义 + 可阅读的规划视图 | 每项标记适用性、阶段、来源/理由；个人工具不硬塞企业计费、多租户 |
| 当前完整旅程、明确不做、关键不变量、必要前期回归 | 当前阶段执行入口 | 必须先读，保留金额/权限/数据不丢失/根目录边界等关键规则，不能靠压缩把风险删掉 |
| 已确认决定、默认值、采用理由、真正需要问人的触发条件 | PROJECT_DECISIONS + 阶段入口摘要 | 内部实现选择由 agent 自行处理；会改变用户权益、成本或不可逆行为时再按明确条件询问 |
| 数据模型、API/CLI 契约、权限边界与持久化策略 | 可定位的主题参考，关键约束同时进入阶段入口 | 使用稳定 ID；避免同一契约在原始 JSON、多个文档和摘要里漂移 |
| 阶段目标与退出标准 | 路线图 + 当前阶段执行视图 | 首阶段完成已确认场景主线；不能把保存做在 P0、恢复/纠错等必要闭环拖到未来 |
| 正向与关键负向用例、运行命令、环境 | 独立验收包；入口先列必验行为，执行时读取程序 | 程序经过真实测试后才能称可用；不把作者的“已实现”或静态审阅当运行证据 |
| 危险部分的参考实现 | 可选、单独版本化的积木 | 只收小范围、已验证、说明边界与许可证的组件；不把整个上游仓库当模板核心 |
| AGENT 指令、当前阻塞与交接检查点 | 明确指定的入口文件 + 机器可读清单 | 告知先读什么、如何分阶段、自检及停止条件；不假设不同 harness 自动发现同一种文件名 |
| 构建物与验收结果 | 与规范分开的不可变证据目录 | 绑定源码、套件、运行时、输入哈希；记录 passed/failed/unverified/not_run，不循环自证 |

一种具体目录可以是：

```text
cognition/               # 版本化事实、产品定义、完整路线和来源
  template.json           # 单一结构化知识源；不是默认整份塞给编码 agent
  CATEGORY.md
  PRODUCT.md
  ROADMAP.md
execution/               # 从同一知识源按当前任务渲染
  HANDOFF.md
  CURRENT_PHASE.json
  PROJECT_DECISIONS.json
  AGENT.md
  references/             # 数据、API/CLI、权限等按主题定位
acceptance/              # 独立版本、真实跑过才标注证据
components/              # 可选、验证过的危险积木
validation/              # 与源码/模板版本绑定的实际结果与限制
```

这是推荐结构，不代表本轮已经实现新的工厂导出布局。现有导出保留原包和阶段入口，建议进一步去重与明确读取职责。

## 如何让执行包轻，而不损失认知

当前三个导出包各 21 个文件，原始文件合计约 146–183 KB；既有结构化 template.json，又有渲染文档、CURRENT_PHASE 和验收程序。完整合并形式会把这些表达一并提供。文件多本身不是缺陷，但不应要求编码 agent 每次都重新消化同一事实的多份表达。

建议执行入口只直接展开：阶段目标、完整旅程、关键不变量、必要依赖/回归、已生效决定、契约入口、必验行为和当前缺口。品类调研、后续成熟能力、完整验收代码按任务引用。不要靠任意 token 上限或裁掉负向行为伪造“轻量”。一个关键约束即使只出现一行，也应明确为必须验证，而非藏在长篇参考材料里。

本轮分层条件仍实际读取了较多参考与验收程序，因此“分层”不能自动等同于“模型上下文更小”。完整形式通过原生附件进入会话，不会产生等量 read 事件；比较 read 次数不能判断谁读得更多。实际会话导出证明提供了什么，仍不能证明 provider 最终如何预处理或暴露全部内容。

## 验收与 harness 同样决定模板是否可用

1. 先做可启动性检查，再做真实用户流程、数据保留与负向测试。真实可自测的开发 agent 可以更早发现启动错误；本实验为隔离作者与测试，故意禁止作者执行，不能直接当作正常开发完成率。
2. 套件分别记录 API、浏览器、CLI、源码观察和未验证项。核心检查通过不代表所有危险边界都安全；EP01 就是本轮反例。事后发现的测试应保留其时间与统一应用范围。
3. 规范交付失败不能冒充应用业务失败。宿主应可靠处理文件清单：明确相对 app 根路径，必要时只做有边界、可追溯的路径归一化，仍拒绝绝对路径、越界、未知文件；不要仅因可消歧的前缀就重新付费生成整套应用。此处是后续 harness 建议，本轮失败未被追改。
4. CLI 必须显式隔离 stdin，记录实际输入、附件、模型、权限、退出状态和检查点；失败、正常交付与运行通过是三个状态。本轮修正仅在实验驱动落地，未宣称通用工厂驱动已经完成同样改造。
5. 机器可读交付应使用一个完整一致的 schema 与示例；本轮改名首版审阅两次缺少后追加要求的 exploratory 字段，严格协议失败，原文和有效核心/认知子集保留，不补造数组。这也说明格式可靠性需要单独记录，不能掩盖成一次成功。
6. 独立审阅有价值，但同一模型家族可能有相似盲点；还需要真实执行。评测会话未获得条件映射，原始文档仍可能暴露模板来源，因此不能称严格双盲。

## 下一轮怎样检验 Atlas 的核心价值

优先做“稀疏想法到产品定义”的实验：给三组相同、较短的用户目标，隐藏一份独立冻结的领域需求与风险检查表，比较能否补全适用的角色、失败恢复、权限、数据生命周期、导出与运营需求，同时统计不必要的复杂度和错误人工提问。可执行集成契约仍保持一致，但不要在共同提示里提前把领域认知答案列全。

届时应让正常 coding agent 在同样权限和预算下执行自检，并分别比较认知补全、首次交付、修复负担和最终运行。增加重复样本后，才有资格讨论更稳定的质量或成本差异。本轮提出默认形式，不宣布已经找到普遍最优模板。
