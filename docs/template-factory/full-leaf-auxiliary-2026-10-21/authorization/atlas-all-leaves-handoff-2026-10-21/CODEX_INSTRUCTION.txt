五、在生产前修正已知的两类失败

来源引用分区：
- Atlas 叶子文件、场景需求属于分类/需求依据。
- 固定上游仓库的 README、源码等属于案例观察，必须带仓库、完整 commit、路径及可核查定位。
- 面向新产品提出的功能、技术选择属于设计推断，明确标注为推断。

提示材料、模型输出 schema 和宿主校验应保持这三类边界。生成阶段只允许引用当前固定案例/场景视图中实际可用的 source IDs。不要把 Atlas 路径登记成上游源码，也不要简单删除失败引用再把原结论标成事实。合法已有研究可形成新的、可追溯修订供后续阶段复用。

研究 JSON：
研究阶段优先输出足够选定仓库和固定依据的紧凑结构，使用完整合法示例、字段和转义约束；避免把大段源码、无必要长说明塞进一个 JSON 字符串。读取模型完整原始输出后解析、做 schema 校验，记录错误位置与原始文件。不得用截断、拼接、补引号或静默丢字段让坏输出变成通过。对纯协议错误允许上述有限的新尝试；新尝试必须通过完整 schema 与来源检查。

prompt/profile 更新必须版本化；新的尝试绑定新版本，旧成功包和旧失败证据保持原样。

六、不要把所有叶子硬套成同一种应用

整个目录覆盖许多产品类型。当前书签/看板式 Web CRUD 交付形态不能代表全部叶子。

为每个叶子选择一个能体现核心用途、范围足够小的真实场景。允许适合该叶子的 Web、桌面、CLI、库/服务或其他合理交付形态；模板明确目标、技术约束和验收方式。不要求本轮构建这些应用，不为每种形态先开发一套完整运行执行器。

尽量使用少量可复用 profile 表达差异；避免无条件写死 Python HTTP/SQLite、浏览器入口或同一套九文件内容。若某类当前导出合同确实不能表达，先做小范围兼容改造；仍不支持的记录具体原因及所缺能力，不得用无关的通用管理后台凑数。

“unsupported”不能用来批量跳过陌生领域；必须有逐项依据。目录错误/别名排除、尚未研究、已研究但来源缺失、生成后失败应分别统计。

七、单项生产步骤与可用标准

按现有服务和合同走正式路径：
1. 读取叶子与已固定场景，确定一个核心用户旅程及必要能力。
2. 优先检索兼容的共享案例；没有合适案例再查找真实开源项目、固定完整 commit，并提取与该场景相关的证据。不能仅凭项目名称或模型记忆声称有该功能。
3. 规范案例经现有合法入库路径进入共享应用实证；同一仓库/commit/研究内容可被多个兼容场景复用，不为凑新增数复制案例。每个场景的依据关联必须真实存在，固定引用不得随案例更新漂移。
4. 生成范围小而完整的模板：用户、问题、核心操作、数据/接口或交互合同、开发分期、可验证验收、限制、来源与推断。
5. 使用新的独立审阅上下文，审阅完整材料与精确内容摘要。可以使用同一已授权模型，但不能拿作者自评充当独立审阅。
6. 通过后使用现有辅助制品服务入库、进入 Atlas 的叶子/场景/案例回查路径，导出可独立阅读的标准开发包，并提供从 HANDOFF.md 开始的 Codex 说明。

这些是操作步骤，不代表每步都要新增模型调用。沿用现有合法的研究/生成/独审协议；若共享案例与模板在同一次独立审阅后才登记，按该合同执行。已接受且固定的案例不为增加步骤而重复审阅。

允许的 70 分状态：功能少，样式普通，没有云同步/附件等扩展能力，只覆盖一个核心场景；限制明确。不要要求非核心特性齐全或为风格差异重复审阅。

本轮仍必须阻断该项的情况：来源伪造/错绑、核心合同互相冲突、关键计算或状态转换明显错误、验收与承诺相反、审阅未读全、包损坏或缺必要交接、没有有效独立审阅却标通过。它们只阻断该项，不应使整个计划停止。

证据无法证明上游运行、目标应用运行或 strict G1 通过时，不得补写这些状态。新模板显示“静态审阅通过、应用未运行”，缺口单独可见。

独立审阅发现内容问题时按剩余额度进入一次修订+复审。复审必须针对修订后摘要。仍不合格则 needs_revision，保留最后可审查产物和问题，不发布为可用模板，不继续无限修复。

八、验证应随实际风险执行

宿主代码改动完成后运行仓库规定的相关检查及要求的 CI；关键回归覆盖：来源分区、无效 JSON 原样保留、失败后继、完整审阅材料、跨旧 500 门槛的作用域授权、并发预留不超支、断点恢复、成功重放零新增调用、变化包拒绝错误复用。

不要为每份纯内容模板重跑整套后端/Docker/浏览器大门禁。每项执行必要的 schema、引用存在与范围、合同一致性、包文件及内容摘要校验即可。源码再次改动后按改动风险补跑相关检查。

全量统计、source manifest、标准包与下载入口需相互对得上。仅把模型返回保存为 JSON、生成 zip 文件或通过 fixture，不算该项可用。

实际使用完整长文本审阅，不以被工具截短的预览代替完整文件。错误下载/未通过审阅制品继续保留既有门禁。仅审阅内容不通过时，不通过降低门禁使其变绿。

九、持续执行、失败隔离与暂停恢复

实现并验证必要改造后，立即登记授权、启动首个真实批次，再继续全量。不要开发完 runner 就结束本轮而没有真实启动。

如果全部完成需要跨越本次交互，使用当前机器允许的持久任务方式继续运行，并交付真实启动回执、进程/队列标识、日志、状态命令与恢复命令。只有确认进程/队列实际活动、至少一个真实阶段有回执后，才能说“已开始全量运行”。仅创建计划或文件时应写“已准备，尚未开始”。不得虚构后台任务。

不能保证进程脱离当前会话后存活时，明确说明运行方式的实际限制，保持可恢复检查点，并尽可能完成当前可执行工作；不要假称后续会自动运行。

每 20 项结束或每 30 分钟至少更新一次持久进度文件，阶段完成即写检查点。用户查看状态不应打断生产。不需要每批请用户再次批准。

单项失败：保存阶段、原因、原始输出摘要、是否已消费调用、可复用检查点和建议，进入修订/失败队列，继续其他项。
全局 provider/网络故障：遵守服务速率限制；无在途任务时持续故障应正式暂停并保留待处理队列，按已有合法机制有限恢复。不要把同一次认证或全局服务故障扩散成 1,000 个“产品失败”，也不要绕过限流。
自动处理不得超出本轮已登记额度/模型/范围。额度或授权窗口用尽时真实暂停并报告未处理项；用户停止时立即停止派发，安全收尾已在途调用。

十、报告、提交与完成定义

为每个冻结叶子保留独立状态，至少区分：
- reused：已验证并复用已有可用模板；
- ready_not_run：新增辅助模板静态审阅通过、包可消费、应用未运行；
- needs_revision：已生产但仍需内容修订；
- failed：该叶子已经实际执行，但研究协议、生成或宿主构造等阶段失败，且该叶子在本授权内允许的恢复动作已经耗尽；记录 failure_stage、failure_code、尝试谱系、调用数和原始证据，计入已处理失败，不计覆盖；
- source_unavailable：已真实进行限定研究但没有可用固定案例；
- unsupported：有具体证据说明当前交付合同不能表达，单列原因；
- pending/running/paused：尚未完成生产处理，不能算成功。

仅因全局预算、时间窗口或公共服务故障而尚未完成的叶子，继续保留 pending/paused，不能转成 failed 伪造全量完成。

“全部已处理”与“全部已通过”分开。报告同时列出：原始叶子总量、正式范围、排除项及理由、复用数、真实尝试数、新增通过数、失败数、unsupported 数、仍未开始数、在途数和暂停数。不能靠缩小分母、把旧版本算作新覆盖或把 pending 改为 unsupported 达成 100%。

正式范围内没有 pending/running/paused，且每项有可追溯结果时，可报告“全量处理完成”；有失败则标 completed_with_failures。覆盖率只按不同叶子的可用模板计算；全部通过才可称全量模板覆盖。未完成则如实交付进度与持续任务状态。
