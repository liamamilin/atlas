## 4. 已观察到的可读性缺陷与修复范围

### 4.1 事实边界

原冻结独审 input.json 约 524 KB，source_inventory 27 个文件，source 合计约 1.11 MB。若干差分又在 input 与 source 中重复出现。

原 events.jsonl 有 68 个事件：
18 step_start、17 step_finish、33 tool_use。
33 次工具均为已完成的 read，没有执行测试/安装/shell。
原 input.json 读取返回中的 program_diffs 五个字符串被标记为 line truncated to 2000 chars；R7 增量差分中的若干 program_diffs 也发生同样截断。
input 和若干大 JSON 文件还存在未读完的后续分页。

这证明材料呈现有缺口；不证明它是超时唯一根因。最后一个未完成步骤约 260 秒没有后续事件，无法分解为模型推理、provider 等待或其他内部耗时。不得编造确定根因或声称 1800 秒保证成功。

### 4.2 优先使用最小呈现补修

保持原 input.json、leaf.md、source/ 及 source_inventory 完全不变。

在 attempt 的 source/ 之外新增一个只读目录，例如 review-materials/：
- INDEX.md：短索引与阅读入口，不写评审结论；
- manifest.json：派生原文到原始文件/JSON pointer 的完整映射；
- 从原 JSON 字符串解码后原样写出的 .diff/.md/.txt 文件。

优先直接展开原有换行，形成普通逐行文本。先实测实际物理行长度；若所有派生行均低于原工具截断阈值，就不要为本案建立新的分块协议、检索平台或复杂缓存系统。

至少覆盖实际截断的：
1. 累计 aggregate_repair_diff.program_diffs 中的全部键（当前共六项，其中原读取有五项发生截断，runner.json 这一项也须保留）；同时与 frozen source/inputs/aggregate-repair-diff.json 的同源值核对。
2. source/inputs/r7-incremental-diff.json 中的全部程序差分及仍作为长字符串的 old/new 正文。

已核对原 source/template.json 不含 artifact 的 provenance。旧六项/aggregate 的建议和判定保留在正式 artifact 及历史审计记录中，供 Codex 核对和交付报告使用；不能声称它们原来都在独审 source 中。本轮派生材料仅来自原 input.json、leaf.md 和冻结 source/，不额外注入外部历史 passed/blocked 判定或自行编写的问题摘要。原文件中实际存在的问题保持可见，由新的独审自行判断。

## 5. 精确身份：哪些保持，哪些明确变化

保持以下摘要与原失败调用一致：
- artifact ID/digest/归档；
- snapshot、冻结 source tree；
- 原 input.json 字节、完整 payload、预算规范化 payload；
- leaf 内容、scenario、language、review_rules_version、模型；
- 预算 operation 与 logical scope；
- 九份交付程序及全部已有审阅结果。

明确新增并绑定：
- 新授权原文、路径/来源与 SHA256；
- 无损呈现 manifest/tree；
- 原 prompt 后的窄追加、新 prompt SHA256；
- 只读 ACL 的明确增量与新规范化 config identity；
- 本次 timeout_seconds=1800；
- 同 job 恢复 attempt 2 的 recovery/grant/request 身份；
- 实现本机制的宿主源码 commit/tree 和精确 CI。

“冻结字节不变”不能被写成“整个模型输入完全不变”。原 payload 不变，但 prompt、可见派生材料和 ACL 已有明确的呈现增量，必须如实记录。

pipeline.agent 会为 leaf 写 companion 并注入 leaf.content_file，再计算 payload 摘要：
- input_sha256 是写出后 input.json 的字节 SHA256；
- full_payload_digest 包含 language；
- budget_input_digest 去掉顶层 language；
- operation 使用预算 digest 前缀。
prepare 与实际 worker 复用同一纯构建/序列化逻辑，不能各实现一份。
仅 language 变了即使 operation 未变，也必须因 raw/full 摘要不符拒绝。

本案保持原 payload，因此不得把呈现修复改成新 operation，声称这是免费首次审阅。

### 6.3 reserve、spawn 和消费

沿用已有事务保证：
- reserve 使用有效 token/lease，在事务中核对身份、预算与 grant 后原子占用；
- Popen 前 durable spawn_intent；
- 成功启动后 durable started；
- 实际启动后，无论通过、超时、协议错误、取消，都计为已使用 1/1；
- 只有可证明根本没有启动的 pre-spawn/OSError 失败才允许归还同一资格；

每次身份与材料复核应尽量在 reserve 前完成，并在 spawn 前防止 TOCTOU。
预算边界必须强制保护已登记此恢复的目标 job：它的任何新模型 reservation 都必须携带该未消费 grant 并完全匹配 effective call。省略恢复上下文/grant、retry=None、换 stage/scope/operation/payload 均拒绝，不能因走普通 agent/retry 入口而绕过单次限制。

该 operation 的局部 retry 序号与跨 operation 的历史 scope 计数不是同一概念，分别展示，不改历史序号伪造余额。

## 16. 本轮成功的定义

恢复机制成功：
原冻结字节保持，呈现可完整核对，同job首次恢复到attempt2，只消费一次已授权模型会话，取得有效独立报告，历史记录和预算完整。若随后仅做合法host-only提交，单列宿主attempt并继续绑定原模型attempt2，模型调用仍只有一次。
这可以是passed，也可以是真实blocked/uncertain；合法执行不等于产品通过。

冻结独审通过：
新的真实报告八维全部passed，正式acceptance与当前attempt、候选和调用绑定正确。

模板生产主链走通：
同一条真实链上取得合法冻结审阅、正式发布、标准交接实际消费、真实P0交付、冻结套件/独立浏览器/精确phase proof，并由宿主正式评估G1 passed。

批量里程碑完成：
在G1 passed后，按固定T08三场景及原预算实际执行并交付结果；失败与未运行不能换样本或隐去。

不要把上述四种成功混成一句“已全部完成”。
