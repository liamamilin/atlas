# 改造后书签工厂：真实端到端试用

日期：2026-10-19。状态：**本次书签 P0 端到端验证完成，通过。** 使用已确认的“生活待购与灵感收藏夹”r2，重新生产认知模板，再由 OpenCode 开发首阶段应用，经独立 agent 验收、定点修复和复验。模板保持 L0 / draft，未发布。

模型固定为 `commandcode/deepseek/deepseek-v4.1-flash`，单次显式 high reasoning，不改全局配置。真实工厂任务在主库中，可通过 `run.json` 查到批次及任务编号。生产使用工厂现有版本化队列、规范预审、生成、冻结和独立认知审阅；不手写一个样板冒充生产结果。

## 预先固定的范围

- 完整认知库、当前阶段执行包、独立验收契约来自同一冻结版本。
- P0 完整核心：保存、默认归类、独立创建归类、移动、浏览、检索、打开原链接和真实进程重启保留。
- 默认单人本地、Python 标准库 + SQLite + 服务端 HTML 表单，满足无外网依赖环境；实际架构与接口由模板规范确定。
- 应用源码由 OpenCode 生成，宿主只校验、原样写入、归档与测试；不人工修补应用源码或削弱冻结验收。
- 冻结用例的运行结果与独立浏览器用户流程分别记录；不把模型自报、静态审阅或退出零当成行为通过。
- 独立 agent 在应用开发前冻结 `evaluation/PLAN.md`。原计划和哈希不变，`SCOPE_NOTE.md` 另行明确重复提交是未承诺时的风险探索，不能强加产品偏好。

## 真实失败、修复与工具纠偏

1. 首次调研完成，但输出包含工厂保留的 `S01` 本地输入项，被严格外部来源协议拒绝。原任务 attempt-1 的响应及日志保留。没有制品或通过结论。
2. 为这一真实失败补原始响应检查点和有界协议修复；原始调研重放会记录原文件摘要，不重复联网调研，不自行删除来源后标为通过。
3. 五维预审通过后，独立 Sol reviewer 对照真实容器协议发现：A09 计划读取的 tester `/state` 并非应用数据库；交付示例还使用非法 profile `web`。在继续编写程序前主动中断任务，保留原规范、五维预审与已开始的程序尝试。为带运行协议的任务补平台协议预审，再由模型修订规范；不把独立审阅发现的矛盾改成通过。
4. 独立验收 agent 的合成环境探针先发现 Docker internal 网络未实际发布端口。使用单独 bridge、仅 127.0.0.1 发布端口、只读源和专属数据卷后，真实 Chromium 可访问并完成受控 fixture 导航。该浏览器环境不声称容器出口封锁；工厂运行器的 network-none 是另一份独立证据。环境探针不是产品应用验收。
5. 修订后的工厂 A09 用例验证新 HTTP 客户端能读取已保存记录，不等同于进程重启或磁盘耐久性证明。真实重启由独立浏览器验收另行执行；没有该结果前，不宣称持久化闭环通过。
6. attempt-3 冻结候选后，独立认知审阅引用了上下文 `leaf.md`，而非冻结制品中的文件；严格校验拒绝整份报告，工厂记录为 `unavailable`。原始响应及关卡停止状态保留；只允许有界模型协议修复删除不存在的引用，不能改写原意见、结果或有效引用。
7. 在真实应用产生前，独立 Sol 审阅发现并关闭了浏览器验收 harness 的精确 URL、重复保存后快照、跨导航 XSS 观测、环境错误分类和跳转返回应用问题。原验收计划及范围哈希未改。相关合成证据只验证测试工具，详见 `evaluation/HARNESS_REVIEW.md`，不计入产品通过数。

8. 初版工厂运行遇到 Docker Desktop 镜像可见性与创建容器超时，尚未执行产品用例。保留中断证据；确认没有运行容器后正常重启 Docker Desktop，未重置或清理数据。环境探针通过后重试，初版实际 10/10 通过。见 [环境恢复记录](runtime/docker-desktop-recovery.json)。
9. 浏览器首轮遇到临时 HOME 下找不到 Chromium、默认归类选项假设错误；早期追加 HTTP 探针的 HTML 正则也错误识别归类。这些是验收工具问题，原记录与分类纠正保留，不算产品失败或通过。最终采用正确浏览器路径、正常默认归类操作和 HTMLParser，并核对原始 HTML。有效初版为 `initial-retry-3` 与 `posthoc-http-3`，不用已作废的 posthoc-1/2。
10. 独立源码审查及有效追加 HTTP 探针确认：初版允许含 CRLF 的 URL，跳转时出现注入响应头；共享 SQLite 连接的并发事务造成 20 轮中 6 轮已响应成功的归类丢失。这些是初版真实缺陷，尽管原冻结用例通过，仍需修复。
11. 将固定失败证据交给 OpenCode，仅修改 `app/server.py`、`app/storage.py`、`app/validation.py`：拒绝控制字符、保护跳转头、用锁覆盖共享连接的读写与整段事务。其余六个文件（含 delivery.json）逐字不变。宿主没有人工修补应用代码，也没有修改冻结测试。见 [修复范围审计](gates/app-repair-scope-audit.json)。
12. 修复版重新执行工厂 10 个用例、独立浏览器、真实 Docker 重启及两项追加探针，均通过。独立 Sol 再次只读核对结论与制品绑定，关闭两个源码问题和验收工具状态聚合问题；该复核没有冒充再次执行测试。

## 本轮同时补齐的工厂可靠性

- 调研原始响应检查点与有界修复：只允许模型提出删除宿主可独立判定无效的来源索引，不改事实或把失败直接标成成功。重放原响应不重新搜索。
- 带运行协议任务增加第六维平台协议预审，独立检查 profile、字面量启动参数、脚本导入、应用数据与 tester 草稿隔离；旧五维缓存不能绕过新增关卡。
- 认知审阅的无效文件引用最多修复一次，仅删除无效索引，意见、结果与有效引用不变；该修复会话明确禁止联网。
- 本次下游开发驱动绑定模板、开发包、反馈、基础 ZIP 和源码摘要；限定修复路径，拒绝源码篡改、反馈变化或输出覆盖基础包。每份文件由模型产生，宿主严格校验并原样交付。
- 独立验收工具保留阶段日志、真实重启和清理证明，环境错误与产品错误分开。七项工具单测通过，合成工具检查不计入产品通过数。

最终后端常规回归共 442 项：434 项执行通过，8 项容器 opt-in 默认跳过。见 [回归日志](backend-regression.log)。本案例真实 Docker 执行另有上述报告，不能用常规跳过项替代。最终 checkout 的实现摘要仅描述收尾时文件内容，不追溯冒充早期尝试所加载版本。
