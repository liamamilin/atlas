# Independent browser adapter revision 2

This is a versioned execution-contract supplement for the frozen plan dated 2026-10-19. `machineplan.json`, its selected scenarios, acceptance snapshots, and `PLAN.sha256` stay byte-identical at `5e352e1cdbad18d5dbf827e37e9e0f394f0e7fbf919b0dd18713f7affb6ebb3a`. The frozen seven bookmark journey IDs remain verbatim and mandatory. Revision 2 strengthens how those existing capabilities are proven and adds the P0 UI actions already promised by the current template contract; it does not replace a target or change a planned journey.

The adapter version is `bookmark-independent-adapter/2.0.0`. Browser actions use the stable semantic selectors specified by the generated acceptance suite README:

- Category management: `a[data-testid="category-manager"]` and `form[data-testid="category-create-form"]`, `category-rename-form`, and `category-delete-form`; rename/delete forms carry `input[name="category_id"]`.
- Save: the existing `form[action="/bookmarks/new"]` exposes URL, title, and category fields; the adapter submits the chosen `待购` category as part of the saved record.
- Category search: `form[data-testid="category-search-form"]` carries `input[name="category"]` plus `input[name="q"]`; it is reached by clicking the selected category link, and the submitted URL must preserve both values as `?category=<name>&q=<term>`.
- Move, soft-delete, and restore: `record-move-form`, `record-delete-form`, and `record-restore-form` carry `input[name="record_id"]`; the move form has `select[name="category_id"]` whose value is the selected category ID.
- Error and count semantics: `[data-testid="form-error"]` must be visible after an invalid submission, the submitted value must remain available for correction, and `[data-testid="category-count"][data-category-id="…"]` displays active-record count.
- Original URL opening: `tr[data-testid="record-row"][data-record-id="…"]` contains `a[data-testid="record-open-link"]` with `href` exactly equal to the saved original URL, `target="_blank"`, and `rel` including `noopener`; the adapter clicks it and verifies the actual controlled Chromium popup reaches the same exact URL. The existing `/go/{id}` HTTP redirect remains a separate frozen-suite API assertion.

Category create, rename, delete, move, search, error/recovery, soft-delete, and restore are submitted through their rendered HTML controls. API requests only prepare independent contrast records, verify persisted state, and apply concurrent-write pressure. The search fixture includes the same token in a different category: category-only results include a same-category control, keyword-only results include the cross-category control, and combined category+keyword results must include the target while excluding both controls. Thus a query-only implementation fails the helper assertions. The browser checks category count against the active API result and verifies deleting a category moves both active and soft-deleted records to the default category before a migrated record is restored. Malformed URL submission is performed in the UI; the failure must retain the entered URL and create no row, and correcting that form must recover successfully. The existing JSON API invalid-input assertions remain separate.

`ui_contract_fixture_test.cjs` runs the same adapter UI contract validator in real Chromium against two local malformed-product fixtures. Both fixtures retain a working category-plus-keyword JSON query and move endpoint. One omits the rendered move control; the other renders a selected category field that is disabled and therefore omitted from the submitted search. The adapter must reject each fixture. A fixture pass is preparation evidence only; it is not an application run, scenario pass, or phase proof.

## Runtime deadline context

Real runs require a host-pinned response from `GET /api/factory/v1/jobs/{job_id}/effective-budget` for the actual runtime job. The invocation supplies its file, SHA-256, and expected `campaign_id`, `plan_id`, `product_id`, `job_id`, and `segment` (`G1` by default; `T08` is explicit). Before local setup, Docker preflight, each Chromium phase, container restart, and proof creation the runner rechecks the pinned bytes, exact binding, official schema, and absolute `effective_deadline`. It refuses missing, altered, mismatched, unactivated-amendment, or expired snapshots. T08 must use a base deadline; it cannot inherit the G1 amendment. The amended deadline is the official API result; the historical base deadline is preserved in the context and is not used to reject a properly activated G1 extension. No deadline is accepted from an application model or inferred from the former phase deadline.

The revision is prepared only with synthetic local browser fixtures and budget-context unit fixtures. These checks do not use or produce the real downstream target binding, Docker application run, phase evidence, or G1 result.
