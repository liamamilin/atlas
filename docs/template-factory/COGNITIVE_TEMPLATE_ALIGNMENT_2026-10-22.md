# Atlas 认知模板目标与执行偏差记录

记录日期：2026-10-22。用途：保留本次用户纠正、目标产物定义、实际完成状态与后续工作边界。本次只记录，不启动模型调用、恢复全量或继续开发。

## 用户目标与工厂职责

Atlas 要建立能够持续、批量生产软件产品认知模板的工厂。主线为：叶子类型 → 明确场景 → 固定版本的真实开源案例研究 → 认知模板 → 独立审阅 → 冻结入库 → 用户选择开发范围并交给 coding agent 使用。

核心价值是成熟同类产品的具体判断：完整产品形态、实际用户流程、角色与权限、数据生命周期、异常和恢复、必要的运营与长期维护，以及开发取舍。不同品类应有不同设计；不强制所有产品都包含账号、管理员、计费、审计或复杂后台。

OpenCode 负责研究、生成和独立审阅；宿主 workflow 负责固定输入、状态、预算、检查点、有限恢复、失败隔离、证据与入库。Codex 负责建设及修复宿主，不应长期逐叶盯守或通过手工补齐制造自动生产成功。

## 认知模板的正确产物

内容标准以用户提供的[三份产品参考样稿](../../atlas-reference-examples-2026-10-22/README.md)和[生成器指南](../../atlas-reference-examples-2026-10-22/GENERATOR_GUIDE.md)为准。样稿包括个人收藏夹、团队项目看板和团队活动报名，分别展示单人、多角色协作及运营交接；它们是目标设计样稿，不是已完成模型生产或应用运行的证据。

一份认知模板应形成适用边界清楚、关系完整的产品参考系：

- 产品定位、目标用户、使用形态、完整范围和明确排除项。
- 角色职责、实际操作权限和数据可见范围。
- 业务对象、关系、关键字段、状态与生命周期。
- 页面或其他使用入口：目的、信息区块、操作、成功去向、空状态、错误、冲突及恢复。
- 贯通首次使用、日常操作、管理、跨角色交接、异常和长期维护的用户旅程。
- 跨页面共同遵守的业务规则及可观察的声明式验收目标。
- 从同一完整参考中选出的 P0/P1 等开发范围及必要依赖。
- 需求依据、固定案例观察、目标设计、推断、未知和不适用说明。

这些内容必须具体。例如收藏夹的搜索字段与分类组合、删除分类后各状态收藏的去向、归档收藏从回收站恢复的目标，以及保存失败和旧版本覆盖的处理，都需要明确。

完整参考先于开发切片。P0 从完整参考中选取，并补齐必要依赖；P1 在尚未开发时仍保留在参考全景中。不能用一个小场景的最小实现合同替代完整认知模板，也不能把不同品类全部压成同一种 CRUD 系统。

参考阶段可以只提供声明式验收；不必提前为全部未来能力生成可执行测试、选定技术栈或写实现代码。产品参考、标准开发包、模板静态通过、正式发布、上游运行及下游应用运行应分别表达。章节齐全、字数多或 JSON 合法不能代替产品认知的具体程度与一致性。

## 本次执行偏差与责任

用户指出本项目长期反复尝试、迟迟没有获得稳定的生产能力，并质疑 Codex 能否完成项目。Codex 已承认以下偏差：

1. 反复将完整产品认知参考缩成小场景合同，混淆了完整参考与当前开发切片。
2. 把较多工作投入门禁、授权恢复、形式化校验与审阅机制，却未充分推进目标内容质量及自动生产可靠性。
3. 在两样本未完整通过时，提出由 Codex 直接手工收尾；这只能增加一份辅助成品，不能证明 OpenCode 工厂已经可靠。
4. 多次给出新方案或继续试验的建议，未及时建立以实际交付为依据的收敛方式。

上述问题属于 Codex 的执行和判断偏差，不能归因于用户需求不明确，也不能仅推给模型、provider 或预算。当前结果不足以证明新认知模板生产能力已经稳定完成。

## 尚未解决的问题

- 阅读要求仍主要依赖模型执行，宿主在会话结束后才能发现漏读，已消耗的调用不能撤销。
- 结构与显式引用检查不能充分发现自然语言中的隐含依赖、隐私冲突或不可达恢复路径。
- 内容修订仍可能扩大影响范围，修复旧问题时引入新的规则、界面及验收不一致。
- 审阅输入、历史父版本、研究及派生分页存在重复，增加负担；具体改造方式尚未确定。
- 当前新认知参考修订入口仍是两个样本的专用串行路径，不能据此声称统一后台全量流程已稳定。
- 内容结论、审阅资格、宿主故障和预算停止应分别呈现，不能只用一个失败原因概括。

这些判断来自当前样本和代码，不能据两个样本断言某个模型普遍不可靠。

## 后续交接边界

用户提出了“多次模型调用，每次只分析少数事情，再整合”的思路。该思路仍处于讨论阶段，没有形成新的已批准执行计划或调用授权。先前 Codex 提出的六阶段流程及手工收尾建议，也不能写成已经实施或已经验证的方案。

参考指南现有建议是研究、产品建模、独立审阅三个主要会话，其中角色、对象、页面、权限、状态等在产品建模会话内分层共同推导。后续如调整调用拆分，应明确如何保留这些紧密关系，并以真实产物验证；不能机械拆成多个会话后依赖整合重写来恢复一致性。

继续工作时应先读本记录与原样稿，对准目标产物，再处理实际缺陷。不能用减少核心合同、删验收、复制旧 pass、手工补齐冒充自动成功，或把 CI 通过当作稳定生产完成。应保护已有成果与数据，保持全量暂停；本次“先记录下来”不授权重新开始开发、生产、试跑或自动跟进。
