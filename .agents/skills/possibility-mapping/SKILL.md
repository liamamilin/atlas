# Possibility Mapping · 可能性图谱

## 目的

输入 ATLAS 中的一个具体软件类型，输出该类型的**期望状态**和**期望变化**，帮助人或 Agent 认识这类软件能够是什么，以及相关状态如何形成和改变。

这是一项认知梳理 Skill，不是虚拟导师、需求生成器、架构设计器或开发流程工具。

## 输入与资料

- 必需：ATLAS 类型名称或稳定标识（优先复用现有分类叶子）。
- 可选：关注的子类型或场景。
- 优先阅读仓库现有类型正文、研究笔记、已关联的真实开源项目和来源记录；只引用实际读到的资料。
- 不足时明确说明资料缺口，不凭空声称已覆盖全部可能性。

## 两个核心概念

**期望状态（Expected State）**：在此软件类型中，可以追求或观察到的有意义的结果、能力或状态。既可为软件整体能力，也可为业务对象的具体状态。不要仅列功能标签。

**期望变化（Expected Change）**：某种状态如何产生、保持、转变或终止；描述触发事件、必要条件、规则及结果，并关联所影响的期望状态。不是开发步骤、技术选型或 SOP。

例如电商软件：
- 状态：一笔订单已支付且等待履约。
- 变化：支付服务返回成功且交易被系统确认，订单由待支付转为已支付；异常、重复回调等情况可能影响确认规则。
- “先建数据库再写支付 API”是开发流程，不属于这里的期望变化。

## 工作方式

围绕指定类型阅读真实材料，辨认主要的期望状态，再辨认使这些状态形成或变化的机制；不断对照具体软件，补充遗漏、合并重复、纠正不准确的概括。

不强制固定数量、固定分类维度或统一的操作顺序。以认知的准确性、代表性和可迁移性为准。重要断言应能追溯来源；综合推断须标明。不要为了形式完整制造条目。

## 输出

以一份易读的 Markdown 文档为默认产物：

# {软件类型} · 可能性图谱

## 期望状态
用具体、可理解的描述呈现主要状态及其关联，必要时给例子。

## 期望变化
描述重要变化的起点、触发条件、变化机制、结果，关联相应状态；不写开发步骤。

## 参考依据与边界
列出实际参考的 ATLAS 类型、开源项目或文档，说明尚未验证的部分。

## 质量检查

- 读者能回答“这类软件可以是什么、能达到哪些结果”。
- 读者能回答“这些状态如何形成或变化”。
- 状态与变化有明确联系，且不是空泛的功能清单。
- 具体案例与来源可核对；未知与推断不伪装成事实。
- 不增加现实差距分析、导师教学、执行规划或图谱可视化。

## 第一批验证

仅对 ATLAS 现有分类中最接近的两个叶子做人工审查试点：B2C 电商商城、个人任务管理软件。先确认实际叶子名称与标识，不创建重复分类。各生成一份 Markdown，审查后再决定是否接入网页或批量生产。
