# Possibility Mapping · 可能性图谱

## 目的

输入 ATLAS 中的一个具体软件类型，输出该类型的**期望状态**和**期望变化**，帮助人或 Agent 认识这类软件能够是什么，以及相关状态如何形成和改变。

这是一项认知梳理 Skill，不是虚拟导师、需求生成器、架构设计器或开发流程工具。

## 输入与资料

- 必需：ATLAS 类型名称或稳定标识（优先复用现有分类叶子）。
- 可选：关注的子类型或场景。
- 优先阅读仓库现有类型正文、研究笔记、已关联的真实开源项目和来源记录；只引用实际读到的资料。
- 不足时明确说明资料缺口，不凭空声称已覆盖全部可能性。

## 两个核心概念

**期望状态（Expected State）**：在此软件类型中，值得认识的可能结果。至少留意两个不同尺度：①**软件整体形态/能力组合**（例如单商家商城、多商家平台、数字商品商城），回答“这种软件可以是什么”；②**软件内部的业务结果/对象状态**（例如订单已支付、商品可售），回答“它内部能达到什么状态”。两者都是期望状态，不能用一组业务状态码代替整个可能性空间。整体形态不要求互斥分类，也不必强制穷举。

**期望变化（Expected Change）**：使期望状态得以形成、扩展、维持、转变或终止的变化。既包括**整体能力/形态的变化**（例如从单商家经营扩展到多商家入驻，需要新增商家身份、商品归属、平台治理与结算关系），也包括**局部业务状态变化**（例如付款确认后订单由待支付转为已支付）。解释变化的含义、条件与机制，关联所影响的期望状态；不是开发步骤、技术选型或 SOP。

例如电商软件：
- 状态：一笔订单已支付且等待履约。
- 变化：支付服务返回成功且交易被系统确认，订单由待支付转为已支付；异常、重复回调等情况可能影响确认规则。
- “先建数据库再写支付 API”是开发流程，不属于这里的期望变化。

## 工作方式

围绕指定类型阅读真实材料，先辨认**软件整体可能形态及能力**，再辨认对理解该类型真正重要的**局部业务状态**；梳理相应变化的含义与机制。不断对照具体软件，补充遗漏、合并重复、纠正不准确的概括。不要因为现有参考项目只覆盖一种形态，就把这种形态当成整个软件类型的上限。

不强制固定数量、固定分类维度或统一的操作顺序。以认知的准确性、代表性和可迁移性为准。重要断言应能追溯来源；综合推断须标明。不要为了形式完整制造条目。

## 认知覆盖门禁（v0.5）

语言精确性与认知覆盖是两个独立的质量条件。先发现领域内的主要可能性，再进行语言验证。不得只选取少量容易表达的局部状态，就宣称完成了整个软件类型的可能性梳理。

### 发现与核查

1. 先明确 ATLAS 类型的研究范围，区分整体软件形态与内部业务状态。
2. 阅读已有类型资料、真实项目与研究笔记，识别主要业务领域。领域分组是发现线索，不是新增的核心概念，也不是固定模板。
3. 在每个主要领域中梳理期望状态与期望变化，记录其关联；允许不同软件形态组合。
4. 交叉检查是否遗漏重要领域。例如电商应检查商品发现、商品与规格、购物车、结算、订单、付款、库存、交付、售后、客户、经营、权限及整体经营形态等可能性；这些不是所有商城的必备功能。
5. 对未覆盖领域说明原因：超出当前类型边界、尚未研究、或证据不足。不能把这三种情况混同。
6. 最后对每条内容执行语言精确性门禁。不能因为某个状态容易写清楚就赋予它过高的重要性，也不能因复杂而直接忽略重要领域。

### 验收

- 主要领域有实质内容或明确的覆盖缺口，不以条目数代表覆盖质量。
- 能解释为什么包含某种能力而遗漏相邻的重要能力。
- 至少交叉参照不同来源，避免单一产品决定整个类型的上限。
- **覆盖与语言分别验收**：任一未通过，产物保留为草稿。
- 不要求穷尽所有理论可能性，不引入现实差距、SOP、架构或导师功能。

## 语言精确性门禁（v0.4，强制）

本 Skill 交付的是可理解、可区分、可迁移的认知，而不是听起来专业的短语。**语言精确性高于概览整齐、篇幅简短和条目数量。** 采用操作性定义、受控自然语言、状态转换表达的思想，但不强制照搬某一形式语言语法。

### 每个核心陈述都必须过关

1. **明确所指**：指出具体主体/对象，以及说的是它的什么属性、关系、行为或结果。诸如「完整」「持续」「管理」「相接」「赋能」「协同」「闭环」「智能化」「一体化」等抽象词不能单独承担认知含义；如果使用，须在同一处展开可辨认的事实。
2. **单一主张**：一句核心陈述只表达一个可以辨认的主张。若两个主张可以独立成立（例如商城交易与文章导购），拆开，不用「以及」「同时」「也可以」硬拼。
3. **状态可判别**：期望状态要说明何时算成立，并给出至少一个具体例子或可观察结果；不要把「支持 X」「管理 Y」当作完整状态。
4. **变化可追踪**：期望变化须指出原有情况、触发/条件、改变的对象或关系、改变后的结果；整体形态变化同样要说明前后差异，不可只写「扩展能力」。
5. **边界可反驳**：至少能举出一种看似相近、但不满足该陈述的情况。无法区分正反例时，进一步定义或拆分；资料不足时标记未知，不能用抽象词掩盖。
6. **证据不越界**：精确表达不意味着捏造机制。区分参考产品确实实现的行为、跨产品归纳和设想；缺乏证据时收窄断言。

### 写作与检查示例

**拒绝**：「持续管理周期事务」。

**可接受的状态**：「用户为每周一要做的任务设置重复规则；本周任务完成后，软件仍能显示下一次需要处理的任务及其日期。」这是一个具体可辨认的例子，并非所有软件都采用同一任务记录实现。

**可接受的变化**：「在重复规则仍有效的条件下，用户标记本周任务完成，软件按该规则确定下一次日期，使下一次待办可被查看。」与手工复制任务区分；是否新建任务记录取决于具体产品。

**拒绝**：「商家经营自己的完整商城，内容阅读与购买也可以相接」。

**拆成两个独立状态**：
- 「顾客能够在商家的商品页面选择商品、提交订单；商家能够查询订单并继续处理付款和交付。」（明确这里讨论的交易能力，不宣称覆盖所有商城能力。）
- 「顾客阅读介绍某件商品的文章时，可以通过文章中明确的商品入口打开对应商品页面并发起购买。」（明确内容与购买的连接；仅有不相关的广告链接不算。）

### 自检方式

生成后逐条执行「所指—判别—变化前后—反例」检查。对不能回答的条目**重写、拆分或删除**，不要只在末尾添加一段解释，也不要把模糊标题留在概览而把精确定义藏在后文。标题与概览本身也必须准确；必要时允许标题稍长。

抽样检查不能替代逐条检查。检查结果不必作为额外章节展示给读者，但每条最终保留的状态与变化都应经得起追问「这到底是什么意思，什么情况不算？」。

## 输出组织（v0.3）

以一份易读的 Markdown 文档为默认产物。**先让读者看见主要可能性，再展开理解**；这只是阅读组织方式，不是强制的认知分类或生产流程。

开头提供简短的「可能性概览」，把最有代表性的整体期望状态与相应期望变化并列展示。优先使用简洁表格或紧凑段落；不强制每种形态都对应唯一变化，也不要求填满固定数量。概览不是功能清单，每一项都应表达可理解的结果与变化。

展开时突出**可能性之间的关系**：哪些可以组合、哪些彼此替代、哪些只是不同观察尺度、哪些跨越了相邻软件类型边界。只讨论真正影响理解的关系，不增加第三个核心概念或机械关系标签。

删去重复叙述；正文深度由重要性决定，不以条目数量、篇幅或表格完整度作为质量指标。

建议产物结构：

# {软件类型} · 可能性图谱

## 可能性概览
以简洁方式呈现最重要的期望状态及对应变化，让读者快速把握可能性空间。

## 期望状态
先呈现主要的整体形态/能力可能性，再呈现关键的局部业务状态及其联系；根据主题自然组织，不强制固定数量或层级。

## 期望变化
兼顾整体能力/形态如何形成或扩展，以及关键局部状态如何变化；说明必要条件、机制与结果，关联相应状态；不写开发步骤。

## 参考依据与边界
列出实际参考的 ATLAS 类型、开源项目或文档，说明尚未验证的部分。

## 质量检查

- 所有核心标题、概览条目和正文主张通过语言精确性门禁；无法明确所指或判别条件的条目不得发布。
- 读者能回答“这类软件可以是什么、能达到哪些结果”。
- 读者能回答“这些状态如何形成或变化”。
- 状态与变化有明确联系，且不是空泛的功能清单。
- 检查是否只列出了业务对象的状态机、遗漏软件整体形态的可能性；也检查是否只列软件类型名称、缺少具体内部机制。
- 读者能否先快速看见主要可能性，再理解它们的组合、区别与边界；避免重复和过长铺陈。
- 具体案例与来源可核对；未知与推断不伪装成事实。
- 不增加现实差距分析、导师教学、执行规划或图谱可视化。

## 第一批验证

仅对 ATLAS 现有分类中最接近的两个叶子做人工审查试点：B2C 电商商城、个人任务管理软件。先确认实际叶子名称与标识，不创建重复分类。保留 v0.1、v0.2 两组基线。保留 v0.3 样本作为对照，按语言门禁修订两份案例，重点检查模糊标题、复合主张、缺少前后差异的变化；不以更长的解释掩盖问题。审查后再决定是否接入网页或批量生产。
