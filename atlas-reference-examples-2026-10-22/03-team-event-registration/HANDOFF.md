# 团队活动报名：使用与开发交接

## 使用授权边界

本目录默认用于**校准 Atlas 生成器的产品参考规格**。仅作为生成器参考时，借鉴 `PRODUCT_REFERENCE.md` 的结构、关系和深度；不要因此创建应用、启动服务、登记生产预算或修改 Atlas 正式数据。

**只有用户明确选择“实现此产品”时，才执行以下 P0 开发交接。** 该选择授权实现这里定义的产品，并不授权部署到公网、向真实成员发送消息或导入真实用户数据。

## 开发目标

请完整读取 `PRODUCT_REFERENCE.md`，实现“单组织内部免费活动报名”的 P0。产品至少涉及成员、负责运营和管理员三种实际上下文；可由三个测试账号体现。一个账号允许组合角色，但管理员不自动获得业务运营权限。

P0 必须实现文档中 P01–P10 标注的 P0 能力、J01–J06 旅程、R01–R10 规则和 A01–A10 验收。不得只做活动列表与报名按钮后宣布交付。P1 的批量归档、CSV 导出、批量标已读不进入本次默认实现，也不要放置伪可用按钮。

## 技术落地方式

优先沿用目标仓库现有 Web 技术栈与可靠认证。若是独立新项目，采用单机 Web + SQLite + 本地账户/服务端会话的 profile 即可，无需引入消息中间件、微服务或云账号。密码用成熟实现进行哈希，禁止明文保存；提供一次性的交互式管理员初始化命令，避免密码出现在命令历史和日志中。

数据库至少表达成员与角色、活动及版本、每成员每活动唯一的当前报名、报名状态历史、通知事件/收件记录及必要的权限变更日志。报名容量检查与写入必须原子完成，不能仅依赖前端禁用按钮；所有入口重新校验当前权限与活动状态。

统一使用服务端时钟与时区转换。测试可注入时钟，覆盖截止/开始恰好相等的边界；页面展示全部为北京时间。不得通过浏览器本地时钟决定是否允许报名。

通知使用最小持久 outbox（待投递事件表）及轻量后台处理即可，可复用应用进程或本地任务，不要求外部队列。业务提交记录事件后独立投递站内消息，失败可见、可重试；重试不得重复执行发布、报名或取消。待投递记录不能只放内存；应用启动时及运行中恢复扫描未完成事件，停机重启后继续投递并去重。可以提供仅测试环境启用的投递故障开关，用于验证 A08；不能将测试记录当作真实送达。

按 R04 持久记录操作 ID、请求摘要和业务回执。同一业务意图的网络重试复用操作 ID，真正的新报名/取消生成新 ID。返回原操作回执时同时读取当前报名状态，避免迟到的报名/取消响应把界面恢复成过期状态。

活动编辑用版本校验，保存冲突给出恢复入口；负责人转交和撤权必须在同一事务或等效原子操作中完成。P0 不要求复杂多人协同编辑。

## 建议开发顺序

1. 建立数据结构、认证和管理员初始化，跑通管理员建运营/成员及唯一管理员保护。
2. 完成活动草稿、发布、成员列表/详情和按角色的数据范围，形成可访问的真实入口。
3. 实现报名/取消事务、重复请求、最后名额竞争及全部时间边界；再接入列表和名单计数。
4. 完成活动修改/取消、归档历史、通知持久化及失败恢复。
5. 完成负责人交接、撤权后的旧页面拒绝、筛选/空状态/错误恢复，并走三角色完整旅程。

每步可以迭代 UI，但不能缩小 P0 的业务闭环。开发过程中发现合同不清时，先记入明确问题并给出最小解释；不得用一个新默认值悄悄覆盖已有 Rxx 规则。

## 必须提供的验证证据

按 A01–A10 记录执行结果、实际命令或浏览器步骤、关键响应/截图及所用数据目录。使用隔离测试数据，不触碰用户原有数据库。

至少进行以下真实验证：

- 三个独立会话完成初始化建人、运营发布、成员报名、运营查看名单及成员取消。
- 容量 1 的两个并发请求只产生一个有效报名，重复请求不会改变人数。
- 截止、开始及取消边界通过可控制时钟的针对性测试；正常浏览器能显示对应状态。
- 发布/报名/取消已经成功时，模拟通知投递失败并重试，业务记录保持正确。
- 撤回运营权限后，原来打开的编辑页和直接请求都不能继续管理；新负责人能接管。
- 刷新与同数据目录重启后，活动、报名、历史和待投递事件正确保留。

代码解析、静态审阅或合成测试不能代替这些实际应用结果。未执行项写“未执行”；局部通过不能汇总为全部通过。

## 交付物

提供完整源码、依赖说明、管理员初始化/启动/停止/重启命令、数据目录与备份说明、P0 页面入口、测试账号创建方法、A01–A10 结果及已知缺口。源码包不包含真实用户数据、明文密码或会话凭据。

交付报告说明 P0 实现情况和 P1 尚未实现项；区分应用是否经过运行验证与服务当前是否在线。只有实测后才能写“可运行”或“通过”。
