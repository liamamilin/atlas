# 如何用三份样稿改进 Atlas 生成器

## 1. 生成目标

目标是一份适用边界清楚的产品参考规格：能回答谁使用、在哪里完成什么、数据与状态如何变化、流程如何贯通、错误怎样恢复，以及如何选择开发版本。

三份样稿是内容示例，不是三个通用产品壳。不同叶子应根据自己的用途生成不同角色、页面、对象、规则和旅程。不能把所有品类都填成同一种 CRUD 管理系统。

## 2. 从样稿提取公共结构

建议采用版本化 ProductReference 结构，并将正文、来源绑定和宿主状态分开。

| 结构 | 从样稿提取什么 | 关联要求 |
|---|---|---|
| product_shape | 目标用户、价值、使用形态、范围与排除项 | 定义完整性的边界 |
| roles | 职责、目标、权限、数据范围 | 对应可完成的旅程与实际操作 |
| objects | 业务对象、关系、关键字段、生命周期 | 操作和规则引用明确对象 |
| capabilities/actions | 行为、前置条件、效果、限制、失败恢复 | 关联角色、入口、规则、断言 |
| surfaces | 页面／命令／API 等入口、信息区块、导航与状态 | 核心操作可发现，成功后有去向 |
| journeys | 触发、参与者、逐步操作、跨角色交接、结束条件 | 步骤引用实际入口与操作 |
| rules | 权限、计算、状态转换、跨页不变量 | 一个规则只维护一个规范定义 |
| assertions | 给定条件、操作、可观察结果 | 可同时关联多个页面、角色和对象 |
| scope_options | P0/P1 或其他开发选择及依赖 | 不因裁剪导致当前旅程断裂 |
| basis/gaps | 需求、固定观察、设计理由、未知、不适用 | 不把设计建议写成事实 |

`passed`、发布状态、调用身份、内容摘要、运行状态等由宿主管理，不能由作者模型自评赋值。

页面中的 Pxx、旅程中的 Jxx、规则中的 Rxx 和验收中的 Axx 是本样稿的局部编号。生产结构应给这些对象稳定 ID；跨文档引用由同一规范生成，不要求从任意 Markdown 文本反向猜测。

## 3. 产品参考与开发包分别建模

产品参考规格承载完整产品形态。开发切片选择其中的旅程和必要依赖，再产生技术设计及验收程序。

参考规格默认含声明式验收，不必提前为所有可选和后期能力生成 `probe.py`。现有开发包仍应遵守原来的程序与交接合同。新增参考产物应有独立类型和校验入口，不放空程序伪造开发包完整性。

切片不能简单选择几页就结束，也不能看到一个共用页面就将页面所有能力都纳入 P0。计算依赖时以选中旅程的动作和规则为核心，补齐相关对象字段、状态、权限、入口和恢复路径，保留未选能力为明确延期项。

## 4. 生成流程

常规参考生产先保留三类主要会话：

1. 研究：按产品问题读取固定案例，形成事实、材料覆盖和缺口。
2. 产品建模：在一次会话内分层推导角色、对象、能力、页面、旅程和规则，输出统一规格及声明式验收。
3. 独立审阅：读取完整规格、证据和派生视图，检查缺漏与矛盾。

宿主在模型调用之间执行结构／关系校验、摘要绑定、阅读视图生成、持久化、复用和导出。新的尝试必须绑定 profile 版本，不能原地替换旧冻结输入。

不要为角色、页面、权限、状态各建一个模型会话；它们关系紧密，先共同建模，再独立检查。发现具体知识缺口时可以有界补读，不以固定文件数量充当研究完成证明。

## 5. 让生成内容达到样稿深度

作者必须写出具体语义。例如：

- “支持搜索”应明确匹配哪些字段，以及怎样与分类／状态筛选组合。
- “可以导出”应明确当前筛选结果、当前页还是全部数据，失败时怎么反馈。
- “管理员可管理”应明确管理成员与配置是否包含读取业务内容，不能默认全部权限。
- “取消报名”应同时说明成员记录、名额、运营名单、历史和通知如何变化。
- “支持编辑”应说明权限变化、并发冲突、未保存输入和保存失败如何处理。
- “可恢复”应说明恢复到什么状态，父对象不存在或无权限时怎样处理。

图表和长篇介绍不能替代上述判断。无需所有产品都提供复杂导出、批量操作或后台，适用性必须有理由。

## 6. 关系校验与审阅分工

程序适合检查 ID 唯一、引用存在、枚举有效、能力有入口、步骤能定位、对象状态合法、断言关联和摘要一致。

独立审阅负责判断流程是否合理、权限是否矛盾、关键异常是否遗漏、来源是否支持结论，以及“不适用”是否被滥用。审阅者应先依据产品范围和角色目标构建自己的核对问题，再检查作者规格，避免仅沿作者目录打勾。

需要阻断的是核心流程断裂、来源错绑、权限／状态冲突、关键规则错误以及没有有效审阅。非核心扩展、视觉偏好、次要便利功能可以记录为缺口或建议，不能无限扩大当前规格。

未知核心规则不能仅标“后续确认”就获得完整参考通过；应先做有限修订或保持待完善。非核心未知可以明确保留。

## 7. 最小落地顺序

1. 在现有后端新增版本化参考规格与关系校验，保留旧 blueprint 合同。
2. 用样稿的结构建立少量开发 fixture，先把读取、关联跳转和导出做通。fixture 不等于真实生产通过。
3. 接入真实研究、生成和独立审阅；复用原案例库、账本与阶段检查点，不新建通用调度平台。
4. 在现有工厂和叶子／场景／案例入口增加参考规格类型，展示角色、页面、旅程、规则、证据和实际状态。
5. 选择不同形态的小批真实输出，与这三份样稿对照；达到内容目标后将未启动项切到新 profile，持续批量。

已有核心场景模板继续保留原类型与状态。参考规格的通过、开发包的通过以及应用运行通过分别显示，不能合并成一个“已验证”。

## 8. 不要复制样稿中的特定产品决定

收藏夹的 URL 搜索规则、看板的固定状态、活动报名的容量和通知策略，都是各自产品形态的设计决定。新的叶子需要作出自己的决定，并记录理由。

本包不授予新的调用额度，不修改当前运行计划，不指定更换模型。使用实际有效的授权和正式版本修订流程；不要把旧全量计划的完成数量直接作为“完整产品参考规格”的覆盖数量。
